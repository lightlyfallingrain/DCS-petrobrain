Session 1 — Ground start Know the mission's briefed QNH before you start (kneeboard, briefing, or mission editor weather page) so you have something to check against.
1

Does the window move on its own?

Do
Start the mission on the ground (parked is fine — engines don't need to be running). Watch the operator's barometric pressure window in the centre console for about 15 seconds. Don't touch the knob yourself.
Expect
The window steps itself toward the mission's briefed QNH, settling within about 15 seconds, with no input from you.
Record
2

Cross-check: the body-layer log

Do
Watch the body-layer terminal around mission start for a line starting mission-start altimeter QNH sync armed: qnh=....
Expect
Logged within a second of mission start, with qnh matching the briefed value and a target_mmhg reading.
Record
3

Precise check (optional)

Do
From the Mac/WSL, once settled: curl -s -X POST http://<windows-ip>:7791/query/read_args -H 'Content-Type: application/json' -d '{"args":[834]}'. Pressure = 670 + 120 × the returned value.
Expect
Within 0.3 mmHg of the briefed QNH.
Record
4

What does Petrovich say?

Do
Listen through the whole settling window.
Expect
Silence — success is designed to be quiet, matching every other mission-start housekeeping step. Only a failure speaks: "Unable, operator altimeter not responding" (the knob never moved) or "Unable, altimeter pressure not set" (it moved but never converged).
Record
Session 2 — Air start Straight and level, any seat. This session also checks the interaction with the takeover fix.

Same settle check, airborne

Do

Same behaviour — the sync doesn't care whether the aircraft is on the ground or already flying.

6 the prize

Does "Request Aircraft Control" still misbehave?

Do
Once the altimeter has settled (or ~15 s have passed), from the operator seat, press "Request Aircraft Control" — the same binding the takeover-fix cards used.
Expect
The AI's barometric target should now be sane on the first toggle — not the wild +740 m target the earlier takeover probes measured. If the altimeter is set right, the takeover fix's own correction loop should find nothing to correct.
Record

Bring back

  1. Did the window move on its own, both ground and air start, and settle near the briefed QNH?
  2. Did the log line appear with the right qnh/target_mmhg each time?
  3. Did the knob respond the same way regardless of which seat the human player was in? If not, which seat failed.
  4. Silent on success, or which "unable" line — and does the log explain why.
  5. Did "Request Aircraft Control" produce a sane altitude without the correction loop having to do anything?

Anything that surprises you is worth more than anything on this list.
