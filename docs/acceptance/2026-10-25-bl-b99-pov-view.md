# Acceptance: BL-B99 — Petrovich POV debug view (`--pov-view`)

**Branch:** `feature/pov-view`, DoD-passed at tip `4dad8d9dfb046c8c55c6d1da04d5d8950a47a782`. After
merge this lands on `main` — on your own machine: `git checkout main && git pull`.

**What this is.** A live, redrawn-every-poll ASCII rendering of Petrovich's forward point of view —
azimuth (heading-relative, `0` dead ahead) on the x-axis, elevation (horizon-relative, pitch/roll
removed) on the y-axis — showing the current optic's field of view and what he detects, the
forward-looking twin of `--eyesight-view`'s top-down plan view. Debug/calibration tool only: it
shows ground truth as well as belief, deliberately, same exemption `--eyesight-view` already has.

**Run command.** From `run-scripts/` (the scripts use paths relative to that directory):

```sh
cd run-scripts
./run-body-layer-debug-view.sh --pov-view
```

This script already passes `--eyesight-view` — adding `--pov-view` gives you both frames together
(Test Case 6 below). For POV only, use the plainer script instead:

```sh
cd run-scripts
./run-body-layer.sh --pov-view --eyesight-view-radius-m 5000
```

--help` lists `--pov-view` with the description below, and that `--pov-view` is additive and a
no-op when absent (mechanically, via the test suite) — but I have not watched a real frame render
against live DCS telemetry.

```
--pov-view            print a live forward-POV ASCII view of the current
                       optic's field of view/boresight and what Petrovich
                       detects through it ... Ignores units outside
                       the player bubble. Defaults off, a true no-op when
                       absent. When combined with --eyesight-view, the two
                       frames share one terminal's line budget and print
                       together.
```

**How to read a frame.** Columns = azimuth (°, airframe-relative, every 30°), rows = elevation (°,
horizon-relative, every 10° from +10 to -20). Legend line printed above the grid:
`believed=bold, watched=orange, ground truth: · seen / × not seen, eyes=green ‖ sector, optic=dim
., grid=dim |`.

## Test Cases

1. **Naked-eye sector edges sweep as the gaze moves.** With no scan/watch command active (free
   scan), watch the two green `‖` vertical edge-lines. **Record:** do the two `‖` lines visibly
   move left/right together as Petrovich's free-scan gaze sweeps, staying the same angular width
   apart the whole time?

2. **Binocular tint.** Say "use binoculars" (or whatever currently triggers `BINOCULAR_OPTIC`).
   **Record:** does the optic's field of view now paint as a blue background tint (not green, not
   gray) rather than a dot-disc?

3. **9K113 wide and narrow tints.** Switch the sight to wide, then to narrow. **Record:** is the
   wide-mode tint a distinct gray, and the narrow-mode tint a distinct brown/olive, each visibly
   different from the binocular blue and from each other?

4. **Markers keep their glyph inside a tint.** Get a believed contact (e.g. `AR` for armour)
   sitting inside the current optic's tinted area. **Record:** does the contact's label stay fully
   readable (its own bold/yellow-or-orange letters) on top of the tint, rather than being
   overwritten or blanked out by the tint?

5. **True positions and believed labels.** With a target in view that Petrovich has not yet
   admitted to belief, and one he has: **Record:** does the not-yet-admitted one show as `×`, the
   admitted one show as a labelled marker (e.g. `AR`), and do both sit at plausible azimuth/
   elevation for where you can see them through the canopy?

6. **Nothing beyond the player bubble.** Fly near several distant units well outside normal
   engagement range (tens of km). **Record:** do they stay completely absent from the POV frame
   (no marker, no `×`, nothing) even though they might appear elsewhere (e.g. in logs or on
   `--eyesight-view` if it draws past its own radius)?

7. **Stacking with `--eyesight-view`.** Run with both flags together (the debug-view script already
   does this). **Record:** do both frames print together in the same redraw cycle (top-down frame,
   then the POV frame below it) without one obviously starving the other's share of the terminal?

8. **Horizon-relative elevation holds a ground target still while banking.** Pick a fixed ground
   target and bank the aircraft left/right (and pitch up/down) while keeping the target roughly in
   view. **Record:** does the target's row on the POV canvas stay visually steady (not jumping up/
   down) as you roll, the way it would if elevation really is horizon-relative rather than
   airframe-relative? (This is the main-loop's own frame choice, flagged in the roadmap entry as
   "revisit if it reads wrong in flight" — this is that check.)

---

## Pass Criteria

The feature passes if all eight test cases produce the expected result above, and nothing in
`--eyesight-view`'s own existing behaviour changed (it should look exactly as it did before this
branch, whether or not `--pov-view` is also given).
