# Type Checking & Python Conventions

- **`float ** float` returns `Any` under `mypy --strict` — use `math.pow()` instead.** The `**` exponentiation operator's overloads admit a `complex` result in general, so mypy cannot narrow the return type to `float` even when both operands are `float` and the result is mathematically `float`. Solution: `math.pow(0.5, x)` has an unambiguous `float -> float` signature in typeshed and passes strict checking without surprises. Lesson: any future exponentiation in this codebase should use `math.pow()` proactively rather than triggering a `no-any-return` error later (BL-3 implementation note).

- **Platform-guarded Windows imports must use `if sys.platform == "win32": import ...`, not bare `try: import / except ImportError`.** typeshed's `winsound` stub (and similar Windows-only stubs) report all members as "no attribute" outside `sys.platform == "win32"`, so `mypy --strict` fails even on a bare `try` block that would work at runtime. The static platform check is recognized by mypy and skips type-checking the unreachable branch for non-Windows platforms. Pattern: `if sys.platform == "win32": import winsound; ... _player = _WinsoundPlayer() else: ... _player = NonWindowsStandIn()`, where the stand-in raises `RuntimeError` on any call (the code is never executed on Windows, and never expected to succeed on non-Windows). Confirmed via reproduction on this codebase (BL-10 implementation, `aircraft-layer/src/collector/audio_sender.py`, 2026-09-17).

- **mypy's narrowing of a local variable is invalidated by any reassignment of that same variable name anywhere in the function, even inside a branch that always returns and never reaches the narrowed use.** `_decide_without_guidance`'s `GLASSING` branch reassigning `state = replace(state, ...)` made mypy lose the function-top `phase_started_sim is not None` narrowing for an unrelated `SCANNING`-at-home branch further down that never touches that reassignment at all. Fix: bind a branch's new value to a differently-named local (e.g. `glassing_state`) instead of reusing the narrowed name. Mypy's flow analysis is evidently whole-function for a given variable name, not branch-scoped (BL-B110 implementation, `body-layer/src/belief/optic_policy.py`, 2026-11-03).

- **`mypy --strict` cannot see a circular import created only by a value used inside an annotation, when the module is under `from __future__ import annotations`.** A new `belief.expected_area` module needed `belief.optic_policy.LOOK_SWEEP_SIGMA`'s *value* (not just its type) for a bound calculation, but `belief.optic_policy` already imports `belief.enrichment`, which imports `belief.contacts` — so importing from `optic_policy` into `expected_area` (which `contacts` would need to import) would be a real cycle. Because `from __future__ import annotations` makes all annotations lazy strings, mypy type-checks them without ever executing the import, so it reports no error at all — only running the actual test suite surfaced the `ImportError`. Fix applied here (and the precedent for it): declare the constant independently in the new module with a comment stating why, the same way `LOOK_SWEEP_SIGMA` itself already resolves its tension with the sibling constant `GATE_SIGMA_THRESHOLD`, rather than importing it. Lesson: a module-cycle risk introduced only through an annotation's *value* dependency (not its type) is invisible to `mypy --strict` and must be checked by running the suite, not by trusting a clean mypy pass (BL-B111 implementation, `body-layer/src/belief/expected_area.py`, 2026-11-11).
