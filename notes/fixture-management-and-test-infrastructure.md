# Fixture Management & Test Infrastructure

- **A blocked stage that looks like a product fork can actually be a fixture pinning an unreachable state — check whether a real producer can emit the fixture's exact field combination before trusting the "fork."** `group-collapse` Stage 3's first pass hit an existing, unmodified test asserting `classification_raw="BMP-2"` paired with `classification_level=CLASS` (class-level) and read it as a genuine semantic fork between two valid renderings, reverting the stage. Reading the real producers (`naked_eye_source.py`, `hybrid_source.py`) showed no live channel ever emits a type-shaped raw string at class level — `hires` emits a type string only at `TYPE` level (falling back to `op_class` at `CLASS`), `medres` emits `op_class` at `CLASS`, the scope channel hardcodes `TYPE`. The fixture's pairing was simply wrong, not a case the code needed to handle; correcting the fixture (`classification_level=2` → `3`) unblocked the stage with no behaviour change. Lesson: before treating a test-driven blocker as a design question, check reachability against the real producers, not just whether the assertion is internally sensible (`plans/group-collapse/implementation.md`, "Stage 3 — landed (second pass)").

- **Local world-model fixture `.sqlite`s have non-uniform schema/coverage — no single fixture is complete.** Two fixtures are available locally: (1) `latakia-20km.sqlite` (small, feature-rich, per M5) predates M7 Stage 2's `grid.provenance` schema bump and fails on any `describe_position` call with `sqlite3.OperationalError: no such column: provenance` — pre-existing gap, not a feature defect. (2) `syria-full.sqlite` (full theatre, post-M7) has current schema but incomplete feature layers: `airfield`/`named_place`/`navaid`/`road`/`runway` present, but `settlement`/`water`/`ridge`/`valley` missing (ingestion apparently never ran for full theatre). Testing that exercises all feature kinds currently requires fakes or a newly-built schema-current regional fixture. Future fixture work should target a complete build: either rebuild `latakia-20km.sqlite` with current M7+ schema, or run missing ingestion stages against `syria-full.sqlite` (BL-3 implementation note).

- **`caplog.at_level(level, logger=name)` only scopes the *level* of the named logger — it does
  not limit which records land in `caplog.records`.** pytest's `LoggingPlugin` attaches its
  capture handler to the root logger unconditionally for every test's call phase, so any logger
  anywhere in the process that propagates to root (the default, and nothing in this codebase sets
  `propagate = False`) can contribute a record to whichever test happens to be running when it
  fires. body-layer has several `daemon=True` background threads (`BrainLayerClient._poll_loop`)
  that are started by one test against an unreachable URL, retry forever, and are never stopped —
  so a test asserting an exact `caplog.records` list must filter by `record.name` (and, if two
  leaked instances can share a logger name, by `record.thread == <own thread>.ident`) rather than
  trusting the `logger=` argument to `at_level` to have already done that filtering. The pollution
  is wall-clock-coincidental, not seed-deterministic — repeated runs of the identical
  `--randomly-seed` did not reproduce the same failure (`connection-reporter-flaky` debug report,
  2026-10-23).
- **A test that passes when run alone is not proof its assertion is actually discriminating —
  it may be passing because nothing happened to collide with it that run.** The pre-fix
  `test_unreachable_brain_logs_one_line_without_traceback` took `caplog.records[0]` unconditionally
  with no thread filter; it was passing on `main` whenever no other leaked `BrainLayerClient`
  thread happened to log into the same capture window, not because the code distinguished its own
  record from a different leaked instance's. Correctness was accidental, not demonstrated, even on
  runs where the test went green (`connection-reporter-flaky`, DoD pass 2026-10-23).
- **body-layer has no shared fixture module for world-model's `query.describe` info dataclasses** (`SettlementInfo`/`WaterInfo`/`RoadInfo`/...) — each test file that monkeypatches `enrichment.describe_position` declares its own private `_FakeInfo` stand-in. As of `landmark-words-no-names` (F7, 2026-10-20) that shape is independently duplicated across five files (`test_enrichment.py`, `test_speech.py`, `test_console.py`, `test_tools.py`, `test_crew_console.py`). When a plan makes `semantic_facts_for` read an existing field unconditionally instead of only in one branch, every one of those copies needs the new field added or the affected test raises `AttributeError` at fixture-construction time, not a wrong assertion — so a plan's test-impact list naming only one file is not enough; grep the whole `body-layer/tests/` tree for `class _FakeInfo` first.

- **A generated reference's staleness test proves render == input, not input == truth.** `effector-sequences` (BL-B90)'s `test_switch_reference_matches_the_generator` only confirms the committed `switch-reference.md` matches what `render_switch_reference.py` would produce from the current `effectors-raw/mi-24p.toml` right now — it says nothing about whether that TOML's own content (the real DCS dump) is itself correct or current. A real-run dump from an earlier DCS build can pass this test forever while describing a build that no longer exists; the test is a sync check between two files in this repo, not a freshness check against the live install.

- **`git checkout -- <file>` is only a safe mutation-test restore for a file that is already staged or committed.** It restores from the index/HEAD, not "whatever was here a moment ago" — on an uncommitted file it silently discards everything, not just the deliberate mutation. `effector-sequences` Stage 4 hit this live: `body-layer`'s Stage 4 rewrite of `effector_engine.py` was still entirely uncommitted when a mutation-test restore via `git checkout --` wiped the whole rewrite back to its pre-stage shape. For anything dirty-and-unstaged, back up with `cp`/a scratch copy (or `git add` the pre-mutation state first) before mutating it for a counterfactual check (`plans/effector-sequences/implementation.md`, "Stage 4 — readback by need", Notable Discoveries).

- **A shared Lua-function-extraction test helper that only tracks `function`/`if`/`end` tokens silently mis-slices (truncates) any function containing a `for` or `while` loop** — its own `end` decrements the depth counter with no matching `function`/`if` increment. `test_sight_servo_lua.py`'s `_extract_lua_function` was copied into `test_watched_args_lua.py` unchanged and produced a genuine Lua syntax error (not a clean miss) the first time it extracted a function with a `for` loop in it (`parse_arg_list`, Stage 4). Fixed there by widening the token set to also count `do` as an opener, but the fix was not applied retroactively to the other copies (`test_sight_servo_lua.py`, `test_exponent_float_fix.py`) since neither currently extracts a looping function — whoever next copies this helper to extract a function with a loop needs to widen it again (`plans/effector-sequences/implementation.md`, "Stage 4 — readback by need", Notable Discoveries). **It recurred exactly as predicted**: `BL-B67` Stage 4's `test_payload_lua.py` copied the same unfixed `test_sight_servo_lua.py` version to extract `push_payload_state`, which iterates `payload.Stations` with a `for` loop — truncated the same way, fixed in that copy by widening the token set to `function|if|for|while|end`. `test_sight_servo_lua.py`'s own copy is still unfixed as of this note; the next function added there with a loop will hit this again unless someone fixes the helper once, in one place, rather than per-copy.

- **The same `_extract_lua_function` helper has a second, independent latent bug: it matches the bare words `function`/`if`/`end` anywhere in the raw text, including inside `--` line comments**, not just the loop-truncation gap noted above. A comment reading "a mission end/restart..." several hundred lines past `run_sight_servo`'s real closing `end` happened to rebalance `test_sight_servo_lua.py`'s depth counter by coincidence for every extraction so far, so every existing test using it was (and still is, after the fix) passing against a chunk always longer than intended — confirmed by extracting `run_sight_servo` from the pre-change file: 379 lines, not its real ~230. Adding a new function (`sight_servo_tick`, `9k113-hands-off-switch`) shifted that coincidental rebalancing point past the end of the file, which is what actually surfaced the bug (the generated test script failed to compile at all, `'end' expected ... near '<eof>'`) rather than a wrong extraction being silently accepted. Fixed locally in that file's own copy only (skip `--` line comments while counting; block comments `--[[ ]]` still unhandled) — not shared with `test_exponent_float_fix.py`'s copy, which may have the same issue if a future edit there adds or moves a function near a similarly-worded comment. Same lesson as the loop-truncation bug above: a token-matching extractor that doesn't understand the host language's own comment syntax is not safe to trust just because it has worked so far — "has worked so far" can mean "got lucky on rebalancing," not "is correct."
- **A DCS scripting-API call documented/modelled as returning two values (`ok, value`) may in fact return one** — check the real call site, not a `pcall`-wrapping snippet's own variable names. `LoGetNameByType` was modelled in a Lua test mock as returning an `(ok, name)` pair, apparently by analogy with `pcall(LoGetNameByType, ...)`'s own two return values (`okn, nm` — `pcall`'s success flag plus the wrapped call's *single* return). An early draft bound the mock's second value to a boolean and read it back as `"?"` by coincidence (not a string, but printable), silently exercising the wrong branch until an assertion on the resolved name caught it (`BL-B67` Stage 4, `aircraft-layer/research/2026-10-29-bl-b67-loadout-and-atgm-object-recon.md` Probe 2). The tell: a `pcall(...)`'s own two-value return is not evidence about the arity of the function it wraps.

- **A scenario's "masked-window-to-admission" gap is structurally bounded by
  `separation - admission_range + mask_range`, not freely tunable via speed or lateral offset
  alone.** Widening two groups' separation to lengthen the time one stays masked before the other
  is admitted is self-defeating: it also widens the down-range distance any fold needs to span by
  the same amount, so a longer masked window buys nothing. Altitude is the lever that actually
  works, because raising AGL raises the forward-mask threshold (`AGL / tan(mask_angle)`) without
  changing the separation the fold has to cover — but raising it too far instead prevents the near
  unit from ever being admitted at all (`BL-B104`'s own scenario-3 tuning pass found 800 m AGL
  produced zero detections for the whole run, while 600–700 m AGL all reproduced the fold
  reliably). Worth checking this bound analytically before iterating on geometry by trial and
  error for any future scenario needing a similarly long masked window.
- **A module-level function imported with `from x import f` is a separate binding from `x`'s own
  module attribute — patching one for a revert/counterfactual check does not touch the other.**
  If a function is called both from inside its own defining module (resolving the name from that
  module's globals) and by importers that did `from x import f`, a monkeypatch has to replace both
  bindings to actually change behaviour everywhere the function is called. `BL-B104`'s own
  before/after control experiment against `contact_growth_rate_mps` (called internally by
  `association_over_time._contact_covariance` and, via `from ... import`, by `belief.contacts` and
  `belief.attack_run`) first patched only the two importers' bindings and observed **no behaviour
  change at all** — the internal caller never saw the patch. Caught before it reached a committed
  test, but it is exactly the class of "empirical check that doesn't actually exercise the thing it
  claims to" this project has been burned by before (see the `caplog` entries above).

- **Recon samples can mislead when they all share one parameter value.** `generate_effector_registry.py`'s `multiposition_switch` support was first written against `clickabledata.lua` samples that happened to all use `delta_ = 0.1` — the real file's `delta_` values span at least `0.1`/`1/9`/fractional-arithmetic forms, and a generalisation fitted to the first sample set (e.g. assuming a nice round step) would have silently mis-rendered `AC-TEMP-KNOB-PTR`'s own `1/9` step (which deliberately overshoots `1.0`, topping out at `1.111111` — ED's own count/delta mismatch, not a bug). Scan the full set of real occurrences of a pattern before generalising a parser rule from a handful of recon samples.
