### Goal
Fix the M9 OSM `.osm.pbf` ingest path so a theatre-scale merged extract (the `syria-full` build, ~646MB Turkey-dominated, tens of millions of raw elements / millions of kept ways) no longer buffers every kept node and way in Python lists for the entire `apply_file` pass, which is the confirmed root cause of the memory blowup that stalled and had to be killed on the user's Windows box.

**This is a memory/performance fix, not a feature.** Per `CLAUDE.md`'s Agents section this project phase exempts Performance Reviewer/Security by default; that exemption still applies here (it's a phase-wide exemption, not a per-feature judgment call) even though the motivation is explicitly performance. No investigator step is needed — nothing here depends on an unverified DCS-internals claim; it rests entirely on already-established pyosmium behavior (`SimpleHandler.apply_file` calling `node()`/`way()`/`relation()` synchronously per element), which M9 already relies on successfully.

### Root cause (confirmed by reading the code)
`world-model/src/osm/pbf.py`'s `_FeatureCollector` appends every kept tagged `OsmNode` and geometry-resolved `OsmWay` to `self.nodes`/`self.ways` for the whole file, and `load_features` hands back one complete `OsmFeatureSet` only after `apply_file` finishes. At `syria-full` scale (per the stalled run's own progress log: ~77M raw elements / ~8.6M ways kept before it died) this is many millions of live `OsmWay` objects (each a tags dict + a list of `(lat, lon)` tuples) simultaneously resident — plausibly multiple GB of Python object overhead on top of the real coordinate data, consistent with the observed Task Manager "high" memory and the 300s-then-22-minutes-silent stall (very likely GC/swap thrash, not a hang). This was never caught during M9 validation because that milestone only validated against the 82MB single-country Syria extract (`plans/m9-osm-geofabrik/plan.md`), never the full 7-country merged theatre file.

Confirmed **not** a blocker for streaming: `build/ingest_osm.py`'s `_classify_way`/`_ingest_node`/`_ingest_way` are purely per-item (tags-only classification, no cross-way or cross-node state). Relations are never resolved into geometry at all — `relation()` only increments `relations_skipped`, so there is no hidden multi-pass dependency on having seen all ways first. `store/writer.py`'s `insert_features` is a self-contained `INSERT ... ; conn.commit()` call, safe to call once per batch rather than once per stage — each call is its own transaction, with no assumption elsewhere that a stage's features arrive in a single `insert_features` call. The M3 Overpass path (`osm/features.py`) is untouched: Overpass responses are already small/bounded, and nothing here changes its shape or behavior.

### Affected Modules / Files
- `world-model/src/osm/pbf.py` — `_FeatureCollector` gets a bounded-size batch buffer per element type, flushing via caller-supplied callbacks instead of appending forever. New `stream_features(pbf_path, on_nodes, on_ways, batch_size)` entry point does the flushing; `load_features` becomes a thin wrapper around it (unbounded batch, single accumulate-everything callback) so its existing public signature/behavior and all of `tests/test_osm_pbf.py` stay unchanged.
- `world-model/src/build/ingest_osm.py` — split the existing node-loop/way-loop bodies out of `ingest_osm` into two new batch-scoped functions, `ingest_osm_nodes_batch` and `ingest_osm_ways_batch` (each takes a list, mutates a shared `OsmIngestStats`, returns `list[StoredFeature]`). `ingest_osm` itself becomes a two-call wrapper around them — same signature, same behavior, so the Overpass path and `tests/test_ingest_osm.py` are unaffected.
- `world-model/src/build/pipeline.py` — the `osm_pbf_path` branch (`_stage("OSM overlay (.osm.pbf)", 3)`) changes from "parse whole file into one `OsmFeatureSet`, then one `ingest_osm` + one `insert_features` call" to "stream the file, and for every flushed node/way batch: classify+transform it (`ingest_osm_nodes_batch`/`ingest_osm_ways_batch`) and `insert_features` it immediately," accumulating one running `OsmIngestStats` across all batches. The `osm_cache_path` (Overpass) branch is untouched.
- `world-model/tests/test_osm_pbf.py` — add streaming-specific tests (chunking behavior, leftover partial-batch flush, bounded peak buffer size) alongside the existing correctness tests, which stay as-is since `load_features` is unchanged.
- `world-model/tests/test_ingest_osm.py` — add tests for the two new batch functions producing identical output to today's `ingest_osm` on the same input, split across multiple batches.
- `world-model/docs/M9_OSM_RUN_INSTRUCTIONS.md` — add a short note that theatre-scale merged extracts stream through a bounded-memory ingest path (so a future reader hitting a slow-but-not-crashing multi-hour `syria-full` OSM stage doesn't mistake steady-but-slow batched commits for the same failure mode this fix addresses).

### Implementation Plan

1. **`osm/pbf.py`: bounded batching + streaming entry point (minimal working version)**
   - Add a module constant `_INGEST_BATCH_ELEMENTS = 50_000` (kept nodes/ways per flush — deliberately separate from and much smaller than `_PROGRESS_LOG_INTERVAL_ELEMENTS = 500_000`, which counts *raw* elements seen including discarded untagged nodes, not kept objects actually held in memory). At ~8.6M ways total, 50,000 keeps peak buffered way objects to roughly 0.5% of the old unbounded case — tens of MB, not gigabytes — while keeping SQLite commit count reasonable (~170-ish commits for the full ways total, not thousands).
   - `_FeatureCollector.__init__` takes `on_nodes: Callable[[list[OsmNode]], None]`, `on_ways: Callable[[list[OsmWay]], None]`, `batch_size: int`. `node()`/`way()` append to a small buffer list as before, but call the relevant callback and clear the buffer once `len(buffer) >= batch_size`.
   - Progress logging (`_log_progress_if_due`) switches from `len(self.nodes)`/`len(self.ways)` (now meaningless once buffers are periodically cleared) to running totals (`self._nodes_kept_total`, `self._ways_kept_total`) incremented on every keep, independent of buffer flushing. Log line output stays the same shape.
   - Add `collector.flush()` (or equivalent), called once after `apply_file` returns, to flush any leftover partial batch below `batch_size` for both nodes and ways — otherwise the tail of the file silently vanishes.
   - New public function `stream_features(pbf_path, on_nodes, on_ways, batch_size=_INGEST_BATCH_ELEMENTS) -> tuple[int, int]` (returns `(relations_skipped, ways_skipped_unresolved_nodes)`) wraps collector construction, `apply_file`, and the final flush.
   - Rewrite `load_features(pbf_path) -> OsmFeatureSet` in terms of `stream_features`, passing `nodes.extend`/`ways.extend` as callbacks and a large-enough `batch_size` that it never flushes mid-file in practice (or simply pass `batch_size=sys.maxsize`) — this keeps `load_features`'s existing signature, return shape, and all current `test_osm_pbf.py` assertions valid with zero changes to that test file.

2. **`build/ingest_osm.py`: expose batch-scoped ingest functions**
   - Extract the existing `for node in feature_set.nodes: ...` loop body into `ingest_osm_nodes_batch(nodes: list[OsmNode], theatre, centre_x, centre_z, half_extent_x_m, half_extent_z_m, source_id, stats: OsmIngestStats) -> list[StoredFeature]`, and the `for way in feature_set.ways: ...` loop into `ingest_osm_ways_batch` with the analogous signature. Both mutate the passed-in `stats` in place (matching `_ingest_node`/`_ingest_way`'s existing mutate-stats convention) and return the batch's features.
   - `ingest_osm(feature_set, ...)` becomes: build `stats = OsmIngestStats(relations_skipped=feature_set.relations_skipped)`, call both batch functions once each over the full lists, concatenate their results, return `(features, stats)` — identical behavior to today, verified by keeping `tests/test_ingest_osm.py` passing unchanged.
   - **Surfaced while touching this (flagging, not silently fixing without saying so)**: `ways_skipped_unresolved_nodes` exists on `OsmFeatureSet` (M9's own field, for a way whose node locations pyosmium's index never resolved) but `OsmIngestStats` has no matching field today, so it is silently dropped by the existing `ingest_osm` and never reaches `BuildReport` for either OSM path. Since the streaming pipeline change in Step 3 has this count in hand directly from `stream_features`'s return value, this plan adds `ways_skipped_unresolved_nodes: int = 0` to `OsmIngestStats` and threads it through in both `ingest_osm` (from `feature_set.ways_skipped_unresolved_nodes`) and the new streaming path — a one-field, in-scope correctness fix now that the wiring is being touched anyway, not new scope.

3. **`build/pipeline.py`: wire the streaming path into the `osm_pbf_path` branch**
   - Replace `feature_set = load_features_from_pbf(osm_pbf_path)` + one `ingest_osm` call + one `insert_features` call with: construct `stats = OsmIngestStats()` up front; define two closures `_flush_nodes(nodes)`/`_flush_ways(ways)` that call `ingest_osm_nodes_batch`/`ingest_osm_ways_batch` (mutating `stats`), `insert_features(conn, batch_features)`, and update `report.feature_counts` per feature — mirroring exactly what the removed single-shot code did, just per-batch; call `relations_skipped, ways_skipped_unresolved_nodes = stream_features(osm_pbf_path, _flush_nodes, _flush_ways)`, then set `stats.relations_skipped = relations_skipped` and `stats.ways_skipped_unresolved_nodes = ways_skipped_unresolved_nodes` before assigning `report.osm_stats = stats`.
   - Accepted behavior change, noted for the record: the OSM stage's SQLite writes are no longer one atomic transaction per stage — each batch commits independently. Since `open_for_build` always deletes-and-recreates the target file from scratch (never patches in place), a crash mid-stage leaves a partially-written file that the next build overwrites entirely rather than reuses, so this does not create a resumability or "stale partial data mistaken for complete" hazard. Worth a one-line comment in `pipeline.py` at the branch, not a design change.

4. **Tests: chunking correctness (validate correctness)**
   - `test_osm_pbf.py`: a fixture with more tagged nodes/ways than a small `batch_size` (e.g. `batch_size=3` against 10 nodes / 10 ways), asserting `on_nodes`/`on_ways` are each called more than once, no single call's list exceeds `batch_size`, the final partial batch is still flushed (nothing lost), and the concatenation of all flushed batches equals what `load_features` returns for the same file — this is the direct regression test against "streaming produces identical results to the old bulk approach," using a synthetic fixture rather than requiring the real Syria extract for the base assertion.
   - `test_ingest_osm.py`: feed the same node/way list to `ingest_osm` in one call and to `ingest_osm_nodes_batch`/`ingest_osm_ways_batch` split across two batches; assert identical resulting `StoredFeature` lists and identical `OsmIngestStats` (accounting for the new `ways_skipped_unresolved_nodes` field).

5. **Tests: memory-bound validation (validate performance, since this is the actual point of the fix)**
   - A `tracemalloc`-based test in `test_osm_pbf.py`: build a moderately-sized synthetic `.osm.pbf` (large enough to force several flushes at a small `batch_size`, e.g. a few thousand elements), run `stream_features` with a small `batch_size` and assert peak traced memory stays within a small constant bound independent of total element count (e.g. assert peak allocated bytes for nodes+ways buffers stays under a bound sized to `batch_size`, not to the fixture's total element count) — this is the test that would have caught the M9-scale gap, scaled down to something CI can run in milliseconds rather than requiring an actual multi-GB run.
   - A real-data correctness regression test against `data/raw/osm/syria-260911.osm.pbf` (the file M9's own validation used), `pytest.mark.skipif`-gated on that path existing (this is gitignored, machine-local data, consistent with how other real-data-dependent tests in this repo already have to handle `data/raw/`/`data/world-model/` inputs that aren't checked in) — asserts `stream_features`'s batch-accumulated totals (nodes kept, ways kept, relations skipped, ways skipped unresolved) exactly match `load_features`'s single-shot totals on the same file. This is the check that actually proves "identical results at real scale," not just on a synthetic fixture.

6. **Docs**
   - Add a short paragraph to `world-model/docs/M9_OSM_RUN_INSTRUCTIONS.md` noting the theatre-scale OSM stage now streams in bounded batches (cite `_INGEST_BATCH_ELEMENTS`) rather than buffering the whole file, so a future `syria-full`-scale run should show steady periodic commits rather than the unbounded-growth-then-stall pattern this fix addresses — and that if it *does* stall again, that's a new bug, not this one recurring.

### Risks & Unknowns
- **Batch size is a guess, not measured.** 50,000 is sized by rough per-object memory reasoning (tens of MB, not GB), not an actual profiled number against the real Turkey-dominated extract — the user should expect to re-tune `_INGEST_BATCH_ELEMENTS` after watching the next real `syria-full` run's memory behavior, rather than treating this number as final.
- **Per-batch SQLite commit overhead is unverified at real scale.** ~170 commits for ~8.6M ways is a rough estimate; if the real ways-kept count is materially higher (Turkey's extract could push this further) commit count rises proportionally — still almost certainly cheap relative to the 22-minute stall being fixed, but not measured.
- **The real single-country regression test (Step 5b) can't run in CI** — it's gated on gitignored local data, so it only runs on a machine that has `data/raw/osm/syria-260911.osm.pbf` staged (the user's Windows box, per the cross-machine workflow). This is the only test that validates streaming against real theatre-shaped data rather than a synthetic fixture; the user should be told to run it once locally before trusting the fix on the actual `syria-full` rebuild.
- **This fix does not itself re-run or validate the actual `syria-full` build** — per this project's standing rule, real full-theatre builds are never run by the agent; the user runs the actual rebuild once this lands, and that run is the true validation of the fix, not this plan's test suite.

### Second-order effect
None identified beyond this fix's own scope — `ingest_osm`'s public signature and the Overpass (M3) path are both unchanged, so no other milestone's assumptions shift; this only unblocks the user's blocked `syria-full` rebuild and hardens the OSM stage for any future larger theatre.

### Addendum: memory-exhaustion audit of other bulk-ingest stages

Requested separately from the OSM fix above (does not block it — the OSM fix ships regardless of these findings). Scope: does the same pattern that caused the OSM incident — collecting a whole theatre-scale dataset into Python objects before writing to the store — recur elsewhere in `world-model/src/build/` and its source modules. Verdict per candidate, read directly from the current code (not assumed):

**1. `roadnet/ingest_roadnet.py` / `roadnet/routes.py` — fine, already streaming.**
`iter_routes` is documented and implemented as "a streaming generator over an `mmap`" (`roadnet/routes.py` module docstring, confirmed in `iter_routes`'s body — `mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ)` then `yield from _walk(...)`) specifically because `Syria.routes` is 2.25GB and this was already designed around not loading it whole. `ingest_roadnet` does materialize one `StoredFeature` per yielded route into a Python list, but the route *count* is bounded by the `.routes` file's own whole-file total (~11,464 per the file header, `RoadnetIngestStats.routes_found_whole_file`) — three to four orders of magnitude below OSM's tens-of-millions-of-elements scale. This is the same shape of "materialize the derived output, not the raw source" that the OSM fix above is moving *toward*, already done correctly here from the start.

**2. `build/ingest_srtm.py` — fine at current scale, flag if grid spacing is ever tightened.**
`samples: list[list[float | None]]` holds one Python float (or shared `None`) per grid cell, not a compound object — no tags dict, no per-cell geometry list. At `syria-full`'s documented ~2.5 million cells (500m spacing) that's roughly 70-100MB of float objects plus list overhead; at the pipeline's actual `DEFAULT_SRTM_GRID_SPACING_M = 1000.0` default it's ~4x smaller again. This is a real, bounded, single-digit-tens-of-MB cost, nowhere near what stalled the OSM stage. Flag for later, not now: the module's own docstring already calls "row-count sizing" an "undecided-by-this-module concern" left to the caller's chosen spacing — if a future milestone tightens spacing toward SRTM's native ~30-90m resolution across the same bbox, cell count (and this list) grows by roughly two orders of magnitude, at which point this verdict should be revisited.

**3. `build/ingest_terrain.py` (M6 ridge/valley) — fine, same order of magnitude as #2.**
`classify_curvature` and `extract_components` both operate over the same elevation grid `ingest_srtm.py` (or the probe grid) produces — one lightweight classification object per cell, not per-element compound data. Scales with the same grid-cell count as #2, so the same verdict and the same future-tightened-spacing caveat applies; no separate risk.

**4. `roadnet/junctions.py` (M10 junction detection) — likely fine at the measured real scale, but not proven at `syria-full`'s actual numbers; worth confirming once a real run exists.**
`extract_clusters` calls `all_features(conn, ["road"])` (`store/reader.py`, a plain `SELECT ... FROM feature` materialized into one Python list — the same "bulk-load into memory" shape as the OSM bug, just one layer downstream), then builds `Vertex` objects (one small frozen dataclass per endpoint/interior point) for every road in that list. **Important scope interaction**: `syria-full`'s `"road"` `feature_counts` layer is no longer DCS-`.routes`-only once M9's OSM ingest runs against it — `ingest_osm`'s `_classify_way` also emits `kind="road"` for any `highway`-tagged OSM way, so this stage's input is the *combined* DCS-native + OSM road layer, not just `.routes`' ~11,464-route population. The one measured real data point (`latakia-20km`, DCS roads only: 3,266 roads -> 6,496 endpoints + 155,900 interior vertices, clustering completed fine) is the only proof this stage has ever handled at real scale, and it predates OSM roads being folded into the same `"road"` kind. Extrapolating linearly from that ratio to `syria-full`'s reported 14,833 roads gives roughly 700K interior vertices — each a small frozen dataclass, so still probably tens of MB, and the clustering algorithm is already grid-bucketed O(n) rather than O(n²) specifically because `junctions.py`'s own docstring anticipated `syria-full`-scale road counts ("a single `syria-full`-scale region can carry >14,000 `road` features and correspondingly ~30k+ endpoints"). **Verdict: probably fine, but this is extrapolation, not a measurement** — flag as backlog to confirm with real `JunctionIngestStats`/timing output the next time a `syria-full` build (with OSM roads included) actually completes through Stage 5, rather than assuming the linear extrapolation holds. Do not fix pre-emptively; there is nothing concrete to fix yet.

**5. `dcs_data/towns.py` (and beacons.lua) — confirmed fine, not assumed.**
`parse_towns_lua` asserts an exact expected count (`EXPECTED_TOWN_COUNT = 1182`) and raises if it differs — this is a small, DCS-authored, hand-curated gazetteer, not a theatre-scale derived dataset, and its size is enforced by the parser itself rather than merely believed to be small. Same reasoning applies to beacons.lua (a similarly small navaid/airfield list). No risk.

**Backlog note**: only item 4 above has any open action — "confirm `roadnet/junctions.py`'s real memory/timing behavior against a completed `syria-full` build once one exists (post OSM-streaming-fix), rather than relying on the `latakia-20km` extrapolation" — worth a line in `world-model/ROADMAP.md`'s backlog. Items 1, 2, 3, and 5 need no further action at current scale.
