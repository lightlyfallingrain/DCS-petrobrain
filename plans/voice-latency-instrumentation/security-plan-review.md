### Design Findings

- **Correlation id / timing fields are pure instrumentation, not control flow.** `correlation_id`,
  `t_ptt_release_wall`, and the various `*_duration_s` fields never drive a path decision, a file
  path, a SQL/URI string, or a command — they are logged and echoed back across HTTP hops. This
  rules out the two sharpest patterns previously found on this project (`.claude/agent-memory/
  security/project_mission_theatre_field_unsanitized_into_path_and_sqlite_uri.md`'s path/URI
  injection from an untrusted field, and any eval/exec-style use) — neither applies here.
- **Both JSONL sinks this plan writes into (`latency_log.py`, `belief_truth_log.py`'s
  `write_speech`, `speech_log.py`) serialize via `json.dumps`**, confirmed by reading
  `belief_truth_log.py:391/477/633` and `speech_log.py:72` — so an adversarial string in
  `correlation_id` (quotes, newlines, control characters) cannot break JSONL structure or forge a
  sibling log row. No log-injection finding.
- **No new request-body size cap or `Content-Length` handling is introduced**, and none of the
  existing guards are touched — `audio-adapter/src/server.py`'s `_read_body` (validates
  `Content-Length` before `rfile.read`, rejects negative/non-numeric) and `aircraft-layer/src/
  api/server.py`'s equivalent are unchanged. The pre-existing no-body-size-cap gap on `/speak`/
  `/transcribe`/`/audio/play` is recorded as an accepted standing exemption
  (`.claude/agent-memory/security/project_audio_adapter_full_audit_2026_09_26.md`,
  `project_aircraft_layer_full_audit_2026_09_26.md`) and this plan does not expand it — noted, not
  a new finding.
- **Server binds are unchanged.** `audio-adapter`'s `--host` default stays `127.0.0.1`
  (`DEFAULT_HOST` in `server.py`); the live-cockpit flight already runs it with an operator-chosen
  `--host 0.0.0.0` for the cross-machine Mac↔Windows capture path (documented in `audio-adapter/
  CLAUDE.md`), and this plan adds no new bind surface or endpoint beyond new optional fields on
  existing endpoints. No new finding on network exposure.
- **New optional fields follow the codebase's established strict-validation convention by
  precedent, but the plan itself does not spell this out for `correlation_id`.** Every existing
  field on these same handlers (`text`, `urgent`, `wav_b64` in `audio-adapter/src/server.py`;
  `audio_b64`, `urgent` in `aircraft-layer/src/api/server.py`; the eight-field
  `_poll_transcripts` validation in `body-layer/src/logger.py:2460-2524`) is checked field-by-field
  with `isinstance`, rejecting or skipping on type mismatch — confirmed by reading all three. The
  plan's own text ("the same additive way `slots` already is") invokes that precedent for
  `correlation_id`'s thread-through, but never states the validation explicitly for the *new*
  fields (`correlation_id`, `t_ptt_release_wall`) the way it would need to for an implementer who
  skips reading the precedent. This is the same shape as a lesson already in memory
  (`.claude/agent-memory/security/feedback_plan_stage_log_unbounded_response_body.md`:
  "log the body" without stating "bounded" leaves the bound to chance) — applied here to a field's
  *type*, not its size.
- **`correlation_id` is attacker-reachable on the LAN without a stated length bound.** It is
  generated by the capture process (`uuid.uuid4().hex[:12]`, ~12 chars) in the designed flow, but
  nothing in the plan says the server-side handlers (`audio-adapter`'s `/speak`/`/transcribe`,
  `aircraft-layer`'s `/audio/play`) reject an oversized or malformed value before it is threaded
  through to a JSONL sink. Given `json.dumps` escaping (above), the worst case is log-file bloat
  from a misbehaving or malicious LAN peer repeatedly POSTing a very long string, not corruption or
  injection — low impact under this project's stated single-user/LAN-only scope, where any peer on
  the LAN is implicitly trusted. Not blocking.
- **Stage 6's new `_pending_positional_replies` list is bounded by player action rate**, not by
  external input — one entry per `select_target` command, drained every poll, reset on mission
  restart. No unbounded-growth surface.
- **`AudioSink.deliver`'s protocol change ripples through three implementations**
  (`LocalPlaybackSink`, `_WinsoundLocalSink`, `AircraftLayerAudioSink`) plus test doubles — the
  plan already flags this explicitly as a risk to the Implementer (not a security risk, a
  completeness risk); noted here only to confirm it carries no security angle beyond what's
  already covered above (the new parameter is logged/forwarded, never used for control flow in any
  of the three).
- **Read-only DCS access is unaffected.** Nothing in this plan writes into the DCS installation;
  all new file writes are the project's own JSONL logs under operator-controlled paths passed via
  CLI flags (`--latency-log PATH`), the same posture as every existing `--*-log`/`--*-trace` flag.

### Findings carried forward, not filed

- **Bound `correlation_id` (and any other new string field sourced from an HTTP body) to a
  reasonable length, and validate its type explicitly, before it is threaded onto `TranscriptEvent`/
  `write_speech`/the new latency rows.** Per the Risk Communication format:

  **Finding:** new optional `correlation_id`/`t_ptt_release_wall` body fields have no stated
  type/length validation in the plan text (though strong precedent in the surrounding code implies
  one).
  **Location:** `audio-adapter/src/server.py` (`_handle_speak`, `_handle_transcribe`),
  `aircraft-layer/src/api/server.py` (`_handle_audio_play`), `body-layer/src/logger.py`
  (`_poll_transcripts`).
  **Probability:** low — this project's LAN is single-user and every peer is implicitly trusted;
  realizing this requires a misbehaving or malicious process already on that LAN.
  **Impact:** low — `json.dumps` prevents structural log corruption; worst case is disk growth in
  a JSONL sink from an oversized field.
  **Recommended action:** Implementer validates `correlation_id`/`t_ptt_release_wall` with the same
  `isinstance` pattern every sibling field already uses on these handlers, and caps `correlation_id`
  length (the capture side already produces a fixed ~12-char id, so a generous cap like 128 chars
  costs nothing and forecloses the growth case).

  **Not filed as a backlog item, intentionally** — this is guidance for the Implementer to apply
  *within this same feature* (it is about how this plan's own new fields get validated, not a
  separate deferred piece of work), and the Reviewer/Security deep-analysis pass after
  implementation is where it gets checked rather than scheduled. If the Implementer's code departs
  from the established validation precedent, Security's Mode 2 pass will catch it against this
  note.

### Verdict

APPROVED

No new dependency, no known CVE, no path/URI/eval-style injection, no log-structure injection (all
sinks use `json.dumps`), no change to network bind posture or existing size-cap/Content-Length
guards, and no DCS-install write path. The one low-risk design gap (explicit validation/bound on
the new `correlation_id`/`t_ptt_release_wall` fields) is noted above for the Implementer to close
by following the codebase's own established pattern — it does not block proceeding to
implementation.
