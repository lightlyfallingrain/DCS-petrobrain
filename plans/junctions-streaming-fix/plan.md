### Goal
Fix `world-model`'s Stage 5 ("road junctions") so it no longer bulk-loads the entire `road` layer (now DCS `.routes` + M9's OSM `highway` ways combined) into one Python list before clustering, which is the confirmed-by-signature-match cause of the `syria-full` rebuild's silent OOM kill immediately after roadnet ingest completed.

### Root cause (read directly from the code, not assumed)
`build/pipeline.py`'s Stage 5 branch calls `store.reader.all_features(conn, ["road"])` — a plain `SELECT ... FROM feature WHERE kind IN (...)` materialized into one Python list with no bbox/LIMIT pruning — then hands the whole list to `roadnet.junctions.extract_clusters`, which itself builds one `Vertex` frozen-dataclass object per endpoint and per interior point of every one of those roads, all held live simultaneously for the whole grid-bucketed union-find pass. This is exactly the shape flagged as unproven risk in `plans/osm-streaming-ingest/plan.md`'s addendum (item 4): the `"road"` `kind` is no longer DCS-`.routes`-only once OSM ingest runs (`build/ingest_osm.py`'s `_classify_way` emits `kind="road"` for any `highway`-tagged way), so Stage 5's real input population is now the *combined* DCS + OSM road layer, not the ~14,833-route DCS-only population the addendum's linear extrapolation (~700K vertices) was based on. That extrapolation almost certainly badly undercounts a 7-country merged OSM extract's real `highway` contribution, and this build died at exactly this stage, right after Stage 4 confirmed the OSM+DCS road layer was fully written to the store.

### Core design question, resolved
**Does grid-bucketed union-find clustering require the whole vertex population resident at once, or can it run in bounded-memory spatial chunks?** Resolved: chunking is correct here, because the clustering algorithm's only cross-vertex interaction is "are these two vertices within `tolerance_m` (default 0.5 m) of each other" — a strictly local, bounded-radius test. A pair of vertices that unions can only do so if both lie within `tolerance_m` of each other, so a spatial-tile-plus-halo scheme (padding >= tolerance_m on every tile edge) is guaranteed to see every possible union for vertices in a tile's core, exactly as `osmium extract --strategy=smart`'s boundary-way padding is guaranteed to see every way that could cross a boundary. This is **not** the "reduce per-vertex footprint" case (there is no correctness reason vertices must all be resident at once); it genuinely is the "process in bounded spatial tiles" case.

The one caveat, addressed under Risks: union-find is transitive, so in a pathological input a *chain* of coincidences could in principle produce a cluster whose members span much more than one tile width. This is not a concern for genuine junctions (a real cluster's members are all within a few tolerance-widths of each other, per `test_junctions.py`'s and the `latakia-20km` baseline's own measured `max_intra_cluster_distance_m` values, which stay near 0), but it is an assumption, not a proof — see Risks.

**Reused, not reinvented**: `store/chunks.py`'s M8 theatre-anchored chunk lattice (`CHUNK_SIZE_M = 5000.0`, `chunks_covering`, `chunk_bounds`) already exists for exactly this "iterate the theatre in bounded spatial tiles" need (the probe store's `chunk_coverage` keying). This plan reuses it as-is rather than inventing a second tiling scheme — `store/chunks.py` has no I/O dependency and no reason not to be reused here.

### Affected Modules / Files
- `world-model/src/roadnet/junctions.py` — `collect_endpoints`, `collect_interior_vertices`, and `extract_clusters` gain an optional `vertex_bbox: Bbox | None = None` parameter (half-open `[min, max)` on both axes, matching `store/chunks.py`'s convention) that restricts which vertices are collected/clustered to those whose point falls inside it. `None` (the default) preserves exactly today's whole-layer behavior, so every existing test in `test_junctions.py` needs no change. Pure geometry, no store I/O added — the module's existing docstring claim stays true.
- `world-model/src/store/reader.py` — add `count_features(conn, kinds) -> int`, a `SELECT COUNT(*) FROM feature WHERE kind IN (...)`, so Stage 5's `roads_scanned` stat can be computed without materializing any rows.
- `world-model/src/build/ingest_junctions.py` — add `ingest_junctions_streaming(conn, region, source_id, tolerance_m, min_degree, chunk_size_m=CHUNK_SIZE_M) -> Iterator[list[StoredFeature]]`, a generator that walks `chunks_covering(region_bbox, chunk_size_m)`, and per chunk: queries `store.reader.features_in_bbox(conn, ["road"], padded_bbox)` (padded by `max(tolerance_m * 10.0, 10.0)` m on every side), clusters only within that padded bbox via `extract_clusters(roads, tolerance_m, vertex_bbox=padded_bbox)`, keeps only the resulting clusters whose **centroid** falls inside the chunk's own unpadded `chunk_bounds` (ownership-by-centroid, so a cluster near a tile boundary is emitted by exactly one chunk, never zero or two), converts survivors via `to_stored_features`, mutates a shared `JunctionIngestStats` in place, and yields that chunk's `StoredFeature` list. `roads_scanned` is set once up front from `count_features`, not accumulated per chunk (a road can be a bbox-overlap candidate in more than one chunk; summing per-chunk candidate counts would double-count). The existing non-streaming `ingest_junctions()` is left completely unchanged — still used by `test_ingest_junctions.py`'s existing tests and available for any small-store caller that doesn't need chunking, mirroring the OSM fix's "keep the old whole-shot function as a thin/independent path" precedent.
- `world-model/src/build/pipeline.py` — Stage 5's body changes from one `all_features` + one `ingest_junctions` + one `insert_features` call to: construct `stats = JunctionIngestStats(...)` up front, iterate `ingest_junctions_streaming(...)`, and for each yielded chunk's features call `insert_features(conn, chunk_features)` and update `report.feature_counts` immediately — mirroring exactly the per-batch insert pattern `plans/osm-streaming-ingest/plan.md` already established for Stage 3, so a reader who knows that fix recognizes this one immediately. `report.junction_stats = stats` after the loop.
- `world-model/tests/test_junctions.py` — add: (a) `vertex_bbox` filtering unit tests (a vertex outside the box is dropped even though it would otherwise cluster; half-open boundary behavior at the box edge); (b) a "chunked matches monolithic" regression test — a synthetic multi-chunk fixture (roads placed in at least 3 distinct `CHUNK_SIZE_M`-scale tiles, including one junction deliberately placed within padding distance of a tile boundary) asserting that summing `extract_clusters` calls per padded tile + centroid-ownership filtering produces the exact same cluster set as one unchunked `extract_clusters` call over all roads at once; (c) extend the existing `test_latakia_20km_regression_baseline` (skipped without that local store) with a chunked-vs-bulk comparison against the real store, asserting identical `_LATAKIA_CLUSTER_COUNT`/`_LATAKIA_JUNCTION_COUNT` — the only test in this plan that validates the chunking scheme against real (if modest-scale) road geometry, not just a synthetic fixture.
- `world-model/tests/test_ingest_junctions.py` — add tests for `ingest_junctions_streaming`: stats identical to the existing bulk `ingest_junctions` on the same small fixture split across chunks, no double-counted `roads_scanned`/`clusters_found` when a road's bbox is a candidate in more than one chunk, and a `tracemalloc`-based bounded-peak-memory test mirroring `plans/osm-streaming-ingest/plan.md` Step 5's pattern — a synthetic fixture with roads spread across many chunks, asserting peak traced memory during the streaming pass stays bounded to roughly one chunk's working set, not the whole fixture's total road count.
- `world-model/ROADMAP.md` — resolve the addendum's open backlog line ("confirm `roadnet/junctions.py`'s real memory/timing behavior... rather than relying on the `latakia-20km` extrapolation") once this fix lands and the user's next `syria-full` run gets past Stage 5, per that backlog note's own stated closing condition.

### Implementation Plan
1. **`roadnet/junctions.py`: `vertex_bbox` filtering (minimal working version)**
   - Add `Bbox = tuple[float, float, float, float]` (min_x, max_x, min_z, max_z) locally or import from `store.chunks` (prefer importing — one definition, not two copies of the same tuple shape).
   - `collect_endpoints(roads, vertex_bbox=None)` / `collect_interior_vertices(roads, vertex_bbox=None)`: when `vertex_bbox` is given, only append a `Vertex` whose `point` satisfies `min_x <= x <= max_x and min_z <= z <= max_z` (closed/inclusive — over-inclusion at a padded boundary is safe, the ownership filter downstream is what must be exact, not this one).
   - `extract_clusters(roads, tolerance_m=..., vertex_bbox=None)` threads `vertex_bbox` through to both collectors. No change to `_cluster_vertices`, `_arm_count`, or `to_stored_features` — the bucketed union-find algorithm itself is untouched, it just now runs over a spatially pre-filtered vertex list.
2. **`store/reader.py`: `count_features`**
   - `def count_features(conn, kinds=None) -> int`: `SELECT COUNT(*) FROM feature` (+ `WHERE kind IN (...)` if `kinds` given), `fetchone()[0]`. No row materialization.
3. **`build/ingest_junctions.py`: streaming orchestration**
   - `ingest_junctions_streaming(conn, region, source_id, tolerance_m=DEFAULT_JUNCTION_TOLERANCE_M, min_degree=DEFAULT_JUNCTION_MIN_DEGREE, chunk_size_m=CHUNK_SIZE_M) -> Iterator[list[StoredFeature]]`:
     - `stats = JunctionIngestStats(roads_scanned=count_features(conn, ["road"]), clusters_found=0, junctions_kept=0, degree_histogram={})` — but `stats` needs to be visible to the caller after the generator is exhausted; return it via a small wrapper (e.g. the generator closes over a `stats` object the caller passes in, matching `ingest_osm_nodes_batch`'s "mutate a caller-supplied stats object" convention exactly) rather than inventing a new return shape. Signature becomes `ingest_junctions_streaming(conn, region, source_id, stats: JunctionIngestStats, tolerance_m=..., min_degree=..., chunk_size_m=CHUNK_SIZE_M) -> Iterator[list[StoredFeature]]`, caller constructs `stats = JunctionIngestStats(roads_scanned=0, clusters_found=0, junctions_kept=0, degree_histogram={})` first; the function fills in `roads_scanned` itself on entry, then mutates the rest per chunk.
     - `region_bbox = (region.centre_x - region.half_extent_x_m, region.centre_x + region.half_extent_x_m, region.centre_z - region.half_extent_z_m, region.centre_z + region.half_extent_z_m)`.
     - `padding_m = max(tolerance_m * 10.0, 10.0)` — generously above `tolerance_m` (the actual correctness requirement is padding >= tolerance_m; 10x plus a 10 m floor costs nothing at `CHUNK_SIZE_M = 5000` scale and leaves headroom).
     - For each `(ix, iz)` in `chunks_covering(region_bbox, chunk_size_m)`: `core = chunk_bounds(ix, iz, chunk_size_m)`; `padded = (core[0]-padding_m, core[1]+padding_m, core[2]-padding_m, core[3]+padding_m)`; `roads = features_in_bbox(conn, ["road"], padded)`; `clusters = extract_clusters(roads, tolerance_m, vertex_bbox=padded)`; keep only clusters whose centroid satisfies `core[0] <= cx < core[1] and core[2] <= cz < core[3]` (half-open, so a boundary point belongs to exactly one chunk — matches `chunk_bounds`' own documented convention); `features = to_stored_features(owned_clusters, source_id, min_degree=min_degree)`; update `stats.clusters_found += len(owned_clusters)`, `stats.junctions_kept += len(features)`, merge `degree_histogram` counts from `owned_clusters`; `yield features`.
   - Leave `ingest_junctions()` byte-for-byte as-is.
4. **`build/pipeline.py`: wire the streaming path into Stage 5**
   - Replace the current three-line body with: `stats = JunctionIngestStats(roads_scanned=0, clusters_found=0, junctions_kept=0, degree_histogram={})`; loop `for chunk_features in ingest_junctions_streaming(conn, region, roadnet_source_id, stats, tolerance_m=junction_tolerance_m, min_degree=junction_min_degree): insert_features(conn, chunk_features); for f in chunk_features: report.feature_counts[f.kind] += 1`; then `report.junction_stats = stats`.
   - One-line comment at the branch noting (mirroring the OSM fix's own precedent comment) that Stage 5's SQLite writes are now one commit per chunk rather than one atomic stage transaction — safe for the same reason: `open_for_build` always deletes-and-recreates the target file, so a mid-stage crash just means the next build starts over, never a stale-partial-data hazard.
5. **Tests: chunking correctness (validate correctness)** — per the "Affected Modules" list above: `vertex_bbox` unit tests, the synthetic chunked-vs-monolithic regression test (with a junction deliberately placed near a tile boundary to actually exercise the padding/ownership logic, not just interior-of-tile cases), and the extended real-store `latakia-20km` chunked-vs-bulk comparison.
6. **Tests: memory-bound validation (validate performance, since this is the actual point of the fix)** — the `tracemalloc` test in `test_ingest_junctions.py` described above, sized so peak memory during streaming stays roughly constant as the fixture's total chunk count grows (only per-chunk content should show up in the bound), the same shape of proof the OSM fix used to validate its own batching.
7. **Docs / backlog** — close out the `plans/osm-streaming-ingest/plan.md` addendum's item 4 backlog line in `world-model/ROADMAP.md` once the user's next `syria-full` run actually completes Stage 5, per that note's own stated closing condition; until then leave it open.

### Risks & Unknowns
- **Chunking assumes clusters are spatially local; this is not mathematically guaranteed.** Union-find is transitive: a pathological chain of many roads whose endpoints each sit within `tolerance_m` of the next, but strung out over a long physical path, could in principle produce a cluster whose centroid-vs-member spread exceeds the padding margin, causing it to be split across two chunks (each chunk would then independently find a *partial* cluster, and — worse — the centroid-ownership filter could drop it from both, or double-count it from both, depending on exactly where each partial centroid lands). This has never been observed in this project's real data (`latakia-20km`'s measured clusters are all near-zero-radius; the one documented false-positive population — 16 coincident roads at one point — is also a single-point cluster, not a spread-out chain) and is not expected in real road geometry, but it is an assumption carried forward from convenience, not proven from the `.routes`/OSM data's actual structure. The synthetic + real-store regression tests in this plan validate the common case, not this pathological one.
- **Padding/chunk-size constants are reasoned, not measured**, exactly like the OSM fix's own `_INGEST_BATCH_ELEMENTS`: `padding_m = max(tolerance_m * 10.0, 10.0)` and reusing `CHUNK_SIZE_M = 5000` are sized by the same kind of back-of-envelope reasoning the OSM fix used for its batch size, not a profiled number against the real Turkey-dominated `syria-full` road population. If a real run still shows high per-chunk memory (e.g. a handful of extremely road-dense chunks in a city center), `chunk_size_m` may need to shrink for a future run — this plan does not pre-tune for that, matching the OSM fix's own "expect to re-tune after watching a real run" stance.
- **Redundant road re-fetching across chunks is a deliberate, unmeasured I/O trade-off.** A road whose bounding box spans many chunks (a long highway) gets re-fetched from SQLite (full geometry) once per chunk whose padded bbox its bbox overlaps, even though most of its points get filtered out by `vertex_bbox` immediately after. This trades some extra total I/O/CPU for bounded peak memory — the right trade-off for fixing an OOM kill, but total wall-clock time for Stage 5 could increase relative to the old single bulk pass; not measured, and the user should expect Stage 5 to possibly take noticeably longer (not just "not crash") on the next `syria-full` attempt.
- **This fix only addresses Stage 5.** It does not re-run or validate the actual `syria-full` build — per this project's standing rule, the agent never runs real full-theatre builds; the user runs the next attempt, and that run is the true validation, not this plan's test suite. If Stage 5 now completes but a later stage (6/7/8) OOMs next, that is a new, separate finding — the `osm-streaming-ingest` addendum already audited stages 6-8 (SRTM grid, probe grid, terrain semantics) as fine at current scale (bounded by elevation-grid cell count, not road count), so this is not expected, but it hasn't been re-checked against the *combined* road-inflated feature set specifically (those stages don't read the `road` layer at all, so they shouldn't be affected either way).

### Second-order effect
None beyond closing the specific Stage 5 gap the OSM-streaming-fix's own addendum flagged as unmeasured: `roadnet/junctions.py`'s pure-geometry API gains an additive, opt-in `vertex_bbox` parameter (no existing caller's behavior changes), `ingest_junctions()` is untouched, and the stored `junction` feature schema/semantics are unchanged — nothing downstream (query API, mission interpreter) sees a different `junction` feature shape, only a build pipeline that survives to completion at real theatre scale.

### Decisions Requiring User Input
None — the tiling design reuses an existing, already-reviewed primitive (`store/chunks.py`'s M8 chunk lattice) rather than introducing a new mechanism, and the remaining choices (padding margin, chunk size, redundant-fetch trade-off) are local, reversible, and match this project's established "reason now, re-tune after a real run" pattern from the OSM streaming fix — not architectural forks requiring a stop.
