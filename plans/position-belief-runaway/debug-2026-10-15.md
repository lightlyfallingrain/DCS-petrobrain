### Debug Report

### Observed Issue

Live sortie on `main` (`45a1a87`, no tuning file in play — `X-T26`/`feature/9k113-sight`
ruled out). The belief-truth tripwire (`body-layer/src/belief_truth_log.py`) fired repeatedly:

```
BELIEF-TRUTH TRIPWIRE t_sim=140.1 contact=CONTACT_53 object_id=16781824
  believed_range_m=532616 (cap=10000) position_error_m=533198 (uncertainty=588)
```

— four contacts, same `t_sim`, believed ranges clustered within ~700 m of each other
(531.9–532.6 km), and the eyesight view independently showed ~75 believed markers collapsed
onto one bearing/range (−070°, ~530 km) while the matching truths spanned +050°..+102°,
6.8–18.7 km.

### Hypothesis

**Confirmed root cause: `ConsolePerceptionRunner`'s belief state is never cleared across a
DCS mission restart, and nothing in body-layer detects that a restart happened.**

The sortie's log files contain **more than one flight concatenated**, because the collector
process kept running across a mission reload: `t_sim` resets from 1,635.4 back to 0.0
partway through the belief-truth log, and the detection-trace log shows the same pattern
twice (at line 515,721 and 1,215,937 — three flights total in that file). Splitting the
belief-truth log at the reset:

| segment | t_sim range | rows | distinct contacts | tripwire contacts |
|---|---|---|---|---|
| 0 (previous flight) | 0.4 … 1635.4 | 3,088 | 67 (ids 1–68) | **0** |
| 1 (reported flight) | 0.0 … 140.1 | 871 | 22 (ids 5–72) | 12 at t=140.1, 18 total |

Contact ids continue across the reset (5…72, never restarting at 1) — the live `ContactStore`
built during flight 0 simply kept existing into flight 1. **Every one of segment 1's
tripwire contacts already existed in segment 0** (`[5, 7, 11, 17, 18, 31, 38, 40, 41, 42, 43,
44, 45, 48, 51, 53, 56, 57]` — this set is exactly the full tripwire-contact set, confirmed
by intersecting both segments' own contact-id lists). Segment 1 introduces **zero** new
tripwire contacts of its own.

The new flight's own ground truth is a different, real group (~532 km from the new flight's
ownship — confirmed by the user as real mission geography, not a coordinate defect). Those
far-group percepts are correctly rejected by the player-bubble filter before they ever reach
belief: the detection trace shows `outcome: "player_bubble"`, `observation_id: null` for that
group throughout — **perception is filtering correctly.** The contacts that fire the tripwire
are *stale leftovers from flight 0*, still holding flight-0's believed positions, now ~532 km
from flight 1's ownship. The tripwire pairs one of these stale contacts against a flight-1
ground-truth object sharing its join key and reports the distance between them as a
"belief-truth error" — a real distance, correctly computed, but the actual defect is "this
contact should not exist any more," not "this contact's position fused wrong."

**The tripwire behaved correctly and is not at fault.** It is the instrument that caught a
real defect; nothing about it needs to change.

### Two wrong turns, recorded because both were plausible and would otherwise be re-derived

1. **Coordinate-frame / projection-origin hypothesis.** The symmetric clustering (all believed
   ranges within 700 m of each other, `position_error_m ≈ believed_range_m` in every tripwire
   row) initially looked like a shared wrong origin or observer used to derive believed
   positions. **Killed by the user directly**: the two spatial clusters the data showed (one
   near the SE edge of the Syria theatre, one near the sea, ~532 km apart) are real mission
   geography, not a projection artifact — confirmed, not inferred.
2. **`object_id`-collision hypothesis** (mine). Streaming the 428 MB detection-trace file
   showed one numeric `object_id` (16781824) attributed to a building, a BMP-2, and a T62M.
   That looked like DCS reusing an id across unrelated, simultaneously-existing objects within
   one mission — which would have been a real defect in `belief/contacts.py`'s
   `_resolve_continuity` (its object-permanence shortcut, lines 1257-1280, skips the spatial/
   class gate entirely and has no distance check of its own; see "related, not fixed here"
   below). **Killed by the `t_sim` reset discovery**: the log spans three different flights
   with the collector never restarted, so the same numeric id meaning different real objects
   is normal, *expected* DCS behaviour across missions, not an in-mission collision. The three
   object types sharing that id never actually coexisted at the same time within one mission.

### Related, found but not fixed here (no confirmed live trigger)

`belief/contacts.py`'s `_resolve_continuity` (lines 1257-1280) skips the spatial/class gate
whenever a percept's `continues_observation_id` resolves to an existing contact and
`object_id_continuity_valid` + `class_compatibility != "incompatible"` hold. The latter check
passes on an "unknown" compatibility (e.g. two unclassified `PRESENCE`-level percepts), so two
real objects that both read as "something, unclassified" could in principle be folded together
with no distance check at all, *if* DCS ever reused an `object_id` within one continuous
mission — exactly the residual risk `contacts.py`'s own docstring already names ("DCS reusing
an `object_id` across a real kill/respawn boundary"). This session confirmed the mechanism
precisely but found no evidence it fired in this sortie — the `object_id` reuse actually
observed was across missions, which is expected and harmless. Worth a follow-up ticket on its
own merits, not folded into this report.

### Fix Applied

**None — deferred by user direction.** Mission start/end lifecycle handling (detecting a

### What else survives a mission transition today (plain enumeration, for the backlog item)

Everything in `ConsolePerceptionRunner` (`body-layer/src/logger.py:323-463`) is a plain
dataclass field with no lifecycle hook that clears it mid-process, so all of the following
carry stale state from one mission into the next exactly the same way `store` does:

- **`store: ContactStore`** — the confirmed defect. Nests `GroupStore` internally
  (`belief/contacts.py:768`), so group membership/identity is stale too, not just individual
  contacts.
- **`tasks: TaskStore`** — any pending `scan_area`/`watch_contact`/`attack_target` intent from
  the old mission survives, including one that references a contact id that no longer makes
  sense in the new mission.
- **`enrichment: EnrichmentContext | None`** — the `WorldEnrichmentCache` persists across polls
  by design (its own docstring); it would also persist across a mission boundary it was never
  meant to span.
- **`mission_phase_tracker: MissionPhaseTracker | None`** — BL-7's phase state carries over,
  reporting a phase computed against the previous mission's own structure.
- **`scan_plan: ScanPlan`** — whatever gaze/scan pattern was active (including anything set by
  an F10/voice `Scan` command) continues into the new mission rather than resetting to
  `FREE_SCAN_PLAN`.
- **`optic_state: OpticState`** — the binocular cycle's own state (`plans/binocular-optic/
  plan.md` Stage 2), including any in-progress glass phase and, per BL-14's attack-run work,
  its aim fields — carries straight through.
- **`attack_run_state: AttackRunState | None`** — if an attack run was engaged against a
  contact in the old mission, that state (including the target contact id) survives into the
  new one, where the referenced contact is itself stale per the `store` finding above. This is
  the most likely candidate for a second, harder-to-notice bug layered on top of the first if
  the reset is ever implemented by clearing `store` alone.
- **`attitude_history: deque[...]`** — the steadiness-gate's rolling pitch/bank/heading window
  carries stale samples from the end of the old mission into the start of the new one.
- **`optic: Optic`** / **`_last_look_direction: tuple[int, int] | None`** — the last-resolved
  optic and the last look-direction actually pushed to the Hook script.
- **Both perception sources' own per-channel dedup/continuity state** —
  `NakedEyePerceptionSource`/`HybridPerceptionSource`'s `_object_id_to_last_observation_id`,
  `_last_emitted_texts`, `_observation_count`, `_dropped_count` (`perception/
  naked_eye_source.py`, `perception/hybrid_source.py`). These are exactly the maps that feed
  `continues_observation_id`/the object-permanence shortcut above — carrying them across a
  mission boundary is also what would let an `object_id` genuinely reused *between* missions
  (confirmed to happen, see above) collide with the "related, not fixed here" gap if that gap
  is ever triggered by an in-mission reuse instead.
- **`CrewConsole`'s own state** (not on `ConsolePerceptionRunner` itself, but constructed once
  per process and shared the same way) — not audited in this session; flagging by name rather
  than by content, since it is exactly the kind of thing easy to miss when this is picked up:
  speech/escalation queues, any outstanding confirm-band intent, and callout/debounce occupancy
  state all plausibly live there and would need the same treatment.

### Separate question: live LOS coverage

`live LOS coverage: 420/5106 gate-4 evaluations had no live verdict this sortie` (≈8.2%),
as printed by the live session. **I could not cleanly reproduce this exact figure from the
raw JSONL, and my own reconstruction gives a much higher rate, which is worth flagging rather
than smoothing over.**

- `_entry_to_dict`'s absent-key-means-`None` convention (`detection_trace_writer.py`'s own
  docstring) means a `None` live verdict does not appear in the JSONL as `"live_los_clear":
  null` — the key is **omitted entirely**. A naive text search for the key therefore only
  finds rows with an *available* verdict (`true`/`false`), which is the opposite of what "no
  live verdict" means.
- Correcting for that: rows whose `outcome` is `"gaze"` (gate 4's own rejection outcome, which
  `perception/visibility.py`'s docstring says is also what a `None` verdict produces, same as
  `False`) but which carry **no** `"live_los_clear"` key at all are the "no live verdict"
  population. Counted that way **over the whole three-flight file**: 131,401 rows reached
  gate 4 and were rejected there, of which 80,587 (61%) carried no live verdict — far above
  8%. This count is almost certainly not the same population the live counter's 5106 refers
  to (my proxy only counts *rejected* gate-4 attempts; the live counter's own docstring says it
  counts *every* candidate that reached the gate, including ones that got a `true` verdict and
  continued past it, which I have not added back in), so **I do not trust my 61% figure as a
  comparison point for the quoted 8.2%** — it is evidence the field semantics are easy to get
  wrong after the fact, not a contradiction of the live number.
- Qualitatively, some non-zero miss rate is structurally expected regardless: the LOS Hook
  script polls at 1 Hz and restricts its own enumeration to "10 km bubble → commanded
  look-direction wedge → not ownship" (`aircraft-layer/CLAUDE.md`), so a naked-eye candidate
  that clears gates 1-3 but sits outside Petrovich's *currently commanded* look direction will
  legitimately get no live verdict that poll, independent of feed health. 8% over a 140 s
  actively-scanning sortie is not obviously anomalous on that basis alone.
- **I cannot say with confidence that 8.2% is "normal" rather than "a degraded feed worth
  filing"** without the exact definition the live counter uses, and settling it needs either
  reading `logger.py`'s own `LiveLosCoverage` accounting directly (not attempted this session —
  time was spent on the mission-restart question per the user's priority) or correlating
  misses against `runner.scan_plan`/gaze transitions in a live session, which the module's own
  docstring says is exactly why the counter exists ("so a dead live-LOS feed is observable in
  the logs rather than indistinguishable from an empty sky"). Flagging as unresolved rather
  than guessing further.
