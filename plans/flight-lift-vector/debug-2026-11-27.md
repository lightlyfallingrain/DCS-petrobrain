### Debug Report

### Observed Issue

BL-16 LV-1 sixth re-fly (`docs/acceptance/2026-11-27-sortie-feedback.md`, branch
`feature/bl16-lift-vector-law` @ 8dadf03d, logs `docs/acceptance/logs-2026-11-27/refly6_flight_trace.log`
/ `refly6_debug.log`). User, verbatim: *"deceleration leads to descent as well. Should maintain
altitude."* Speed-change rate itself is accepted ("decent rate, good") — only the altitude-hold
through a decel is the defect.

Trace: a commanded decel at t≈291 (≈273 → ≈108 km/h) showed `a_f_d` −2.4…−3.7 (deceleration demand)
with `u_c` pinned at −1.00 for t≈300–309 while `a_u_d` (the vertical loop's own desired acceleration)
was +2.7…+5 — asking to **climb** — and `v_u` −4…−7 m/s; ≈100 m lost (≈384 → ≈282 m). A second decel
at t≈339 (108 → ≈74 km/h) lost ≈45 m the same way. Accelerations lost only ≈15–25 m, so the fault is
specific to deceleration.

### Hypothesis

`flight_control.lua`'s "Slowing down is always pitch back and also less collective" rule
(section G/E, sortie 2026-11-20) biased `c_dot_nominal` — a collective **rate** — by
`-profile.k_collective_speed_give * |a_f_d|` whenever `a_f_d < 0`. `c_dot_nominal` is multiplied by
`dt` and added into the integrator state `u_c_i` every frame
(`u_c_candidate = u_c_ff + state.u_c_i + c_dot_nominal * dt`). Because a commanded deceleration keeps
`a_f_d < 0` for as long as the speed shaper is still chasing the new target — several seconds, same
order as the speed-change duration the user accepted — this term **integrates for the whole
deceleration**, not just for one frame, and nothing in its own formula bounds that integral. The
vertical loop's own counter-term, `profile.k_collective * e_u`, only grows once a real altitude/VS
error has built up (`e_u = a_u_d - a_u`, and `a_u_d` itself is a *shaped* reference that takes time
to demand climb assertively) — so the unbounded speed-give bias wins the race for several seconds,
drives `u_c` to its −1.00 floor, and the aircraft sinks before the vertical loop can catch up.

### Evidence

- Read `flight_control.lua` lines 1029–1052 (pre-fix): `c_dot_nominal` carried both the vertical
  error term and the speed-give bias, and only the *combined* value was fed through `* dt` into the
  integrator-backing state — there is no separate bound, decay, or time limit on the speed-give
  piece; it is exactly as persistent as the vertical term it is meant to merely "sit on top of"
  (the profile comment's own words, "on top of, never instead of").
- `flight_profile.lua`'s own comment on `k_collective_speed_give` (pre-fix) confirmed the intent was
  a feed, but the implementation was a rate: "the collective feed-forward/integrator **step** is
  biased down by this gain times the deceleration demand" — "step" here meant the per-frame rate
  increment, not a one-shot value.
- Reproduced the mechanism with a toy-plant harness that closes the vertical loop for real
  (`TestDecelerationHoldsAltitude`, `aircraft-layer/tests/test_flight_control_law.py`): take at
  273 km/h / 300 m, command 108 km/h with no altitude command (so `alt_goal_m` holds the take
  altitude, per `law_stopping_height` at `w_mps = 0`), vertical speed/altitude integrated from `u_c`
  via a first-order plant, `a_u` fed back to the law from that same plant (not left at its
  `measured.a_u or 0.0` fallback). **Before the fix** (old `flight_control.lua`, same scenario, same
  toy plant): altitude deviation reached **−42.2 m** over 20 s. Confirms the mechanism independent
  of the real flight's own numbers (which lost ~100 m over a longer, harder decel at a different
  speed/gain point) — same direction, same cause.
- `theta_i`/`e_u`/`a_u_d` sign conventions checked against the plan's own section C/E formulas
  (`plans/flight-lift-vector/plan.md`): `a_u,d` rises (asks to climb) as altitude falls below
  `h_ref`, which matches the trace's own `a_u_d` +2.7…+5 while `v_u` was negative — the vertical
  loop was behaving correctly; the speed-give bias was simply larger and never released.
- No existing test exercised this path: grepped `k_collective_speed_give`/`speed_give`/
  `c_dot_nominal` across `aircraft-layer/tests/*.py` — only the shared `_PROFILE` fixture constant,
  never a scenario driving `a_f_d < 0` against a real (non-zero) vertical plant.

### Fix Applied

**`flight_control.lua`, section E** (the "Slowing down is always pitch back and also less
collective" term): converted from an integrated rate bias into a **bounded, value-level feed-forward
nudge**, computed fresh every frame from the *current* `a_f_d` (never carried forward), added
alongside `u_c_ff` the same way `u_c_ff` already is — not folded into `c_dot_nominal`:

```lua
local u_c_speed_give_ff = 0.0
if a_f_d < 0.0 then
    local capped_decel = math.min(math.abs(a_f_d), profile.collective_speed_give_max_a_f_d_mps2)
    u_c_speed_give_ff = -profile.k_collective_speed_give * capped_decel
end
local u_c_ff_total = u_c_ff + u_c_speed_give_ff
```

`u_c_candidate` now reads `u_c_ff_total` where it read `u_c_ff`; `next_state.u_c_i` is backed out
against `u_c_ff_total` (not `u_c_ff` alone), so the nudge is never double-counted into the carried
integrator state — exactly the same bookkeeping `u_c_ff` itself already had.

**Why this is "bounded... the vertical loop can override", not merely a smaller version of the same
bug:** because the nudge is a *value* recomputed from the present `a_f_d` and never accumulated, its
total magnitude per frame is capped at
`k_collective_speed_give * collective_speed_give_max_a_f_d_mps2` (0.1 × 3.0 = 0.30 of collective
travel) regardless of how many frames the deceleration lasts. The vertical loop's own `e_u`
integrator (`state.u_c_i`, driven by `profile.k_collective * e_u`) is completely unaffected by this
change — it still integrates for as long as altitude is actually off its reference, and since it
adds on top of `u_c_ff_total` exactly as it already added on top of `u_c_ff`, it can fully offset
the capped nudge the same way it already offsets the lift-length feed-forward during a turn. The
user's intent ("less collective when slowing") is kept: the negative control
(`test_speed_give_nudge_still_reduces_collective_below_the_vertical_term_alone`) confirms collective
is still measurably lower with the nudge active than with `k_collective_speed_give = 0` in the same
scenario.

New profile constant: `flight_profile.lua`, `collective_speed_give_max_a_f_d_mps2 = 3.0` — caps the
`|a_f_d|` the nudge reads, so a transient feedback spike (the trace's own −3.7 against the formal
1.9 `speed_accel_cap_mps2`, from `k_speed_error`'s own push) cannot drive the nudge past its own
bound. A Lua-authored profile literal, not a value crossing a wire/external boundary, so no
`math.isfinite`-style guard is added — same trust level every other loop constant in
`flight_profile.lua` already has (its own header: "the same trust level every loop constant in this
codebase has had until now").

**Out of scope, not touched:** the 60 km/h left-yaw runaway the user routed to the slow-speed stage
— recorded as a plan line under LV-3 (`plans/flight-lift-vector/plan.md`), with the user's own
verbatim words carried over from the feedback file.
