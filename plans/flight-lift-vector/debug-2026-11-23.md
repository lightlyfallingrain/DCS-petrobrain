## Problem 1 — Never write axes after "you have controls"

### Observed Issue
Player: "I have controls" → moved to the pilot seat before the readback → Petrovich: "you have
controls" → Petrovich still held the controls.

### Hypothesis / root cause found
`config/rules/flight.lua`'s `i_have_controls` handler spoke "You have controls." the instant
`flight.release_controls()` returned `acted=True` — which is true the moment the release request is
*queued* (`CrewConsole.release_controls` sets `flight_control_transition = "release"`), not once
`Export.lua` has actually processed it. The release request is only sent on the *next* poll
(`body._apply_flight_requests`, ~1 Hz), and Lua only stops writing axes once that UDP datagram
arrives and `request_release` runs. So the spoken confirmation could land up to a poll interval plus
one round trip *before* Lua had actually released — during that window Lua keeps writing axes every
frame. This is exactly `take_controls`'s own already-fixed pattern from the opposite direction:
`take_controls` defers "I have controls." behind `PendingTake`/`fd_acks`; `release_controls` never
got the same treatment when BL-16 Stage 3 moved the take side onto the numbered channel.

Lua itself (`flight_control.lua`'s `request_release`) is correct — it sets `fc_mode = "off"` and
clears `fc_law` synchronously on receipt, and `run_flight_control` never calls `run_active_frame`
(the only place that writes axes) while `fc_mode ~= "active"/"taking"`. There is no self-arm path
that can re-engage immediately after an explicit release while the player is in the pilot seat
(the "off → armed" self-arm clause requires a genuine `is_parked` rising edge, which a seat change
alone does not produce — checked against `ai_pilot_wheel.lua`'s `player_seat`/`is_parked` getters,
which are camera-seat and stick-park state respectively, not coupled). The defect is entirely on the
body-layer side: speaking before confirmation, not Lua writing after release.

### Evidence
`body-layer/src/belief/crew_console.py::take_controls` defers its `says` via `pending_take_says` →
`PendingTake` → `resolve_pending_take` (ack-gated). `release_controls` (before this fix) set
`flight_control_transition = "release"` and returned `{"acted": True}` with no deferred text;
`config/rules/flight.lua`'s `i_have_controls` rule then called `say("You have controls.")`
unconditionally on `r.acted`. `flight_control.lua::request_release`/`run_flight_control` confirm Lua
side is correct once the request actually lands.

### Fix Applied
Made `release_controls` symmetric with `take_controls`:
- `CrewConsole.release_controls()` now sets `self.pending_release_says = "You have controls."`
  instead of returning text for the rule to speak.
- `config/rules/flight.lua`'s `i_have_controls` rule no longer calls `say(...)` — the line is the
  caller's own ack-gated speech now.
- `body.py::_apply_flight_requests`, mirroring the `take` branch, queues a new
  `CrewConsole.flight_pending_release: PendingTake | None` (reusing the `PendingTake` shape) when it
  sends the `release` request.
- `CrewConsole.drain_flight_control` resolves `flight_pending_release` against `fd_acks` every poll
  (reusing `resolve_pending_take`), independently of the take/readback-FIFO logic (a release never has
  anything staged behind it the way a take can), and speaks "You have controls." — or "Unable, not
  ready." on a refusal/timeout — only once Lua's own ack lands.

Files: `body-layer/src/belief/crew_console.py`, `body-layer/src/body.py`,
`body-layer/config/rules/flight.lua`.

## Problem 2 — Estimator spikes (LV-0 shadow)

### Observed Issue
(a) Every mission start: `a_f` 350–700 m/s² for ~0.35 s. (b) Mid-flight (last segment,
t=373.63/377.58/383.10/389.46): position-derived `v` reads exactly `0.000` on all three axes for one
sample while `vec_*` (raw `LoGetVectorVelocity`) stays smooth, producing 300–550 m/s² spikes that
decay over ~0.3 s.

### Hypothesis → confirmed from the trace, three distinct mechanisms
1. **(b) Degenerate ring window, not a real reset.** `est_ring_slope`'s own `denom == 0.0` guard
   (fewer than two samples, or two samples sharing one timestamp) returns `0.0` and `est_sample`
   accepted that `0.0` as `v`. At t=373.63 the acceleration rings (`acc1_*`/`acc2_*`) were *not*
   reset (confirmed: the surrounding `phidot`/`thetadot`/`psidot`/`vec_*`/`ball` trace fields are
   perfectly continuous across that row — no real `dt`-gap reset fired, which would have zeroed `a`
   too, not spiked it to -311). A single fabricated `v=0` sample landed in an otherwise-live ring
   with ~15 m/s of real history, reading as a 300+ m/s² deceleration. Root external trigger (why the
   ring briefly degenerated — a duplicate/near-duplicate model-time tick, plausibly at a pause
   boundary per the user's own suspicion) is not confirmed from this trace alone; `aircraft_layer_
   debug.log` was never supplied and would not show it anyway (see "not fixed" note on problem 4 for
   why Lua's own debug log says nothing about this path).
2. **(a) Genuine warm-up, not a degeneracy.** The very first sample primes the ring at `v=0` (no
   information exists yet); the *second* sample's real slope is a legitimate two-point least-squares
   fit, but it is a one-step jump from that artificial `0`, read by the acceleration ring as a huge
   transient. This is an inherent cost of deriving velocity from position with no prior history, not
   a coding defect by itself.
3. **Found during the retest, more severe, same family.** The retest's `retest_flight_trace.log`
   shows the aircraft departing controlled flight and being destroyed at t≈115.1s (see problem 3);
   `LoGetVectorVelocity` starts returning `nil` at t=115.165, and a few frames later `LoGetSelfData`
   itself fails too. `read_estimator_raw` defaulted `pos_n/u/e` to `0.0` on that failure — fed into a
   ring holding ~115 s of real position history, that read as `a_f` = **-13,169,930 m/s²**.

### Evidence
`lv0_flight_trace.log` lines 30122–30132 (the t=373.63 spike, `vec_*`/`phidot` continuous
throughout); `retest_flight_trace.log` lines ~45440–45488 (`phidot` 8.9 → -6.9 → -41.6 → -90.8 →
-126.8 → 143.2 → 536.3 deg/s over 6 samples, then `v_n` to 4,981,192, then `vec_*` → `nil`, then
`a_f` to -13,169,930 once `pos` itself degraded too).

### Fix Applied
`aircraft-layer/dcs-export/Petrobrain/flight_control.lua`:
- New `est_ring_primed(ring)`: `false` for `count < 2` or a `denom == 0.0` window. Deliberately
  **not** a full-window-span check — that was tried first and made (a) worse (a single bigger step
  once the span threshold crossed, confirmed by a failing test), so only the genuinely degenerate
  case is withheld.
- Position-source velocity: push into the ring unconditionally (so it keeps priming), but only
  accept the slope when `est_ring_primed`; otherwise fall back, in order: (i) `raw.vec_n` when
  available (bridges the mission-start warm-up whenever the trace flag or `velocity_source ==
  "vector"` is already reading it — true for every LV-0 card flight) — fixes (a) when `vec_*` is
  available; (ii) hold `est.v` at its last value — fixes (b), and (a) partially when `vec_*` is not
  available (documented residual, pinned by its own test rather than silently left).
- Acceleration ring: same `est_ring_primed` gate, one stage further down.
- **New**: `read_estimator_raw` now reports `raw.pos_valid` (true only when `LoGetSelfData().
  Position` is a clean `{x,y,z}` numeric table); `est_sample` holds `est.v` instead of pushing the
  `0.0` fallback into a live ring when `pos_valid == false` — the mechanism that produced the
  retest's -13,000,000 m/s² reading.

### Verification
`aircraft-layer/tests/test_flight_control_estimator.py`, `TestResetAndPriming`: new
`test_duplicate_timestamp_sample_does_not_spike_acceleration` (mirrors the t=373.63 pattern exactly),
`test_mission_start_bridges_from_vector_velocity_while_priming` (mirrors t=0.038 with `vec_*`
present), `test_mission_start_without_vector_velocity_still_bounded` (documented residual, pinned so
a regression is caught), `test_invalid_self_data_holds_velocity_instead_of_snapping_to_origin`
(mirrors the retest's crash-triggered reading). All 21 tests in the file pass; full existing suite
(`test_a_model_time_gap_past_dt_cap_re_primes_with_no_spike` etc.) unchanged and still passes —
confirms the fix does not touch the already-tested genuine-reset behaviour.

### Not fixed — residual, named rather than hidden
Problem 2a's warm-up transient is **not eliminated** when `velocity_source == "position"` and the
trace flag is off (no `vec_*` reading available at all) — there is no way to know velocity before
the position ring has two real samples. `test_mission_start_without_vector_velocity_still_bounded`
pins the current (unchanged, pre-existing) bound rather than silently accepting a regression. A real
fix needs either seeding `v` from a getter that returns it directly on every reset (not only when the
trace flag happens to be on) or accepting the ~0.2–0.35 s warm-up as documented behaviour, per the
plan's own "Total lag about 0.15–0.2s" note — a decision for the architect/LV-1, not this pass.

## Problem 3 — Erratic take (off→m1 and m2→m1)

### Observed Issue
"Very erratic takeover. Bank goes to 60+ degrees, moves back towards neutral, but spirals out of
control again." Both off→Mode 1 and Mode 2→Mode 1.

### Hypothesis
Not provable to a specific sign/gain bug from the trace alone (the plan's own law is pre-LV-1, no
`fd_mode`/take-origin field in the trace to pin which transition this was), but the retest trace
gives direct, strong evidence of a **genuine control-loop divergence ending in a crash** — not a
measurement/estimator artifact. `phidot` (roll rate, from the real `LoGetAngularVelocity`/attitude
transform, independent of the estimator's own rings) sits in a bounded oscillation (~19–26°/s) for
over a second, then over six consecutive ~38 ms samples runs away: `8.96 → -6.91 → -41.6 → -90.8 →
-126.8 → +143.2 → +536.3` deg/s, after which `LoGetVectorVelocity`/`LoGetSelfData` start failing
(aircraft destroyed). This shape — a sign flip followed by exponential-looking growth in both
directions within ~200 ms — is the signature of an under-damped/unguarded integrator (the plan's own
flagged risk, "Decision 30's unguarded `phi_i` windup risk", explicitly **not yet closed** in the
current pre-LV-1 law; LV-1's own section H, "Anti-windup", is written to close exactly this) rather
than a one-off sign error, which would show a steady bias, not a divergence. The plan's own "What
reading the code turned up" section already names the two latent errors most likely to feed this
(`q` read as a body rate in `law_outputs`'s `u_pitch` damping, and `r = -ang.y` reading low in a
bank for `phi_i`'s own integration) as the leading suspects for *why* the loop has no stable margin
in a bank.

### Evidence
`retest_flight_trace.log`, t=112.4–115.17 (`phidot` series above); the subsequent catastrophic
`v`/`a` readings (problem 2, mechanism 3) are the crash's downstream data corruption, not a separate
event.

### Fix Applied
None — out of scope per the task's own instruction ("Do not redesign the law; LV-1 replaces it").
The estimator fix (problem 2) removes a confound that would otherwise have made this divergence look
worse/different in the trace than the real attitude loop produced, which matters for whoever next
investigates this with a clean LV-0 trace.

### What would confirm this
A trace carrying `fd_mode`/take-origin and the inner loop's own `phi_i`/`T_p` integrator state
(neither is in the current flag-gated trace) across a reproduced erratic take — not available this
pass. Recommend: add those two fields to the flight trace (testing aid, not built here) before the
next attempt to reproduce problem 3 specifically; LV-1's anti-windup (section H) is the architectural
fix already planned.

## Problem 4 — Lost ack → false "Unable, not ready"

### Observed Issue (first pass)
"turn heading 000" → "unable, not ready", then the turn happened 2 s later.

### Observed Issue (retest, second instance)
After the epoch fix (982b1a80) and a collector restart, the off→m1 voice take was *again* refused/
timed out ("unable, not ready"), with the user noting "so no data" for that attempt.

### Hypothesis
**First pass**: `resolve_pending_flight_readbacks`'s own documented strict-FIFO-by-`seq` rule (only
the *front* of `pending_flight_readbacks` is ever checked against `fd_acks`, even when a later
entry's ack already arrived) means one lost/late-acked earlier request blocks every later one's
speech until it times out (`HANDOVER_ACK_TIMEOUT_S` = 3.0 s) — by design, per the module's own
docstring ("the only way to guarantee seq order against a ring that can resolve out of order"). The
turn's own `set` was very likely accepted by Lua near-instantly; the spoken "unable, not ready."
belonged to an earlier, blocked entry timing out, and the turn's own readback (and the real aircraft
response) landed right after, once the front cleared — matching "unable" then "did turn 2s later"
almost exactly (3.0 s timeout vs. the user's "2 s" is consistent with an inexact live estimate).
**Not fixed**: this is the documented, deliberate trade-off (seq-order correctness over best-effort
early speech) and changing it is a design decision, not a bug fix — flagging for the architect rather
than changing it here.

**Retest (second instance)**: Cannot be distinguished between "the take's own UDP datagram never
reached `Export.lua`" and "it was refused by Lua for some reason body-layer never saw" (`epoch`/
`bounds`/`stale`/`not_flying`), because **`Export.lua`'s `flight`/`flight_desired`/`flight_control`
modules call `debug_log` on exactly two paths — a malformed command (missing field) and an unknown
`kind` — never on an ordinary accept or on any of `push_ack`'s refusal reasons** (`epoch`, `bounds`,
`stale`, `not_flying`, `wrong_mode`, `precondition`, or the handover's own refusal causes). Confirmed
by grep: `retest_aircraft_layer_debug.log` (5931 lines) has zero lines matching `flight|take|
release|ack|epoch` apart from the unrelated per-frame cap message below — every line is either
`core.lua`'s connection/throttle/PTT noise or an unrelated world-objects dump. The take/ack/refusal
path is genuinely invisible in this log, exactly as the coordinator suspected.

**One concrete correlated lead, worth checking**: at 21:27:54 the log shows a burst of 34
consecutive `"dropping read_args command: per-frame cap reached"` lines. `commands.lua`'s
`poll_command_socket` drains the *entire* backlog of the one shared `command_socket` every frame in
one `while true` loop, regardless of op — the `read_args` cap (`MAX_READS_PER_FRAME = 4`,
`effectors.lua`) only skips calling the handler for `read_args` entries past the cap; it does not
stop or delay the loop, so a `flight` datagram queued behind a read_args burst would still be
processed the same frame. The cap mechanism itself is therefore **not** the direct cause — but a
burst of 34 datagrams arriving in one receive window is a plausible *symptom* of the same underlying
pressure (an effector sequence, e.g. the SAU-handover sequence merged into this branch, firing many
one-shot reads at once) that could, at the OS/socket-buffer layer (outside Lua's own visibility),
drop a UDP datagram sent by body-layer around the same wall-clock moment — which would explain a
take request that silently never reached `Export.lua` at all (no ack ever pushed, pure timeout, no
log line possible either way). Not provable from this log; the socket layer's own drop counters
(not currently read or logged anywhere) would confirm or rule this out.

### Fix Applied
None — the FIFO behaviour is a deliberate design choice (escalate, don't silently change); the
retest instance cannot be fixed without first being observable. **Testing aid to add (named per the
task's own instruction, not built in this debugging pass — root `CLAUDE.md`'s "Workflow" light
path):**
- `flight_desired.lua::handle_flight_command` — one `debug_log` call per `push_ack(seq, status,
  detail)` site (there are 9: `epoch`, `bounds`, `stale`, `not_flying` for `set`; the `take`
  accept/pending/refused triple; the `release` accept/refused pair), logging `seq`, `kind`, and the
  ack status/detail. This alone would have told us, from `aircraft_layer_debug.log` directly,
  whether the retest's take was ever received by Lua and why it was refused if so.
- `commands.lua::poll_command_socket` — one `debug_log` on *every* op actually handled (not only the
  two "ignoring ..." failure paths), at minimum the op name and whatever identifies it (`seq` where
  present), so a missing log line for an expected `seq` is itself evidence of a dropped/never-sent
  datagram rather than an unlogged acceptance.
- A one-line counter/log on `command_socket:receivefrom()` returning an error (not just `nil`) would
  separate "nothing arrived" from "a read genuinely failed," which today both look identical from
  outside.

### Verification
N/A — no code fix, documented hypotheses only (this pass's effort went into the provable problem 1/2
fixes instead, per the coordinator's "finish with hypotheses where needed").

### Fix B -- epoch re-sync after an Export.lua reload

**Confirmed from code before fixing, as instructed:**

- `_resolve_command_reset` (`body-layer/src/body.py`) returned immediately once `runner.command_
  reset_confirmed` was `True` -- a one-shot latch, never re-checked for the rest of the process.
- `flight_control.lua`, `ai_pilot_wheel.lua` and `flight_desired.lua` each hold their own echoed
  epoch as a **module-level local** (`local fc_reset_epoch = nil` / `local ai_pilot_reset_epoch =
  nil` / `local fd_epoch = nil`), re-initialised to `nil` whenever `Export.lua`'s module chunks
  re-run their top-level code -- which a DCS mission (re)start does (the sortie's debug log shows
  `core.lua`'s own "connected to collector"/"command listener bound" lines, logged only at first
  module load, again mid-sortie at 21:28:44).
- `commands.lua`'s `handle_reset_command` already dispatches `reset(epoch)` to all three modules
  (`flight_control`, `ai_pilot_wheel`, **and** `flight_desired` -- confirmed it is not missing from
  that list), so a resent reset does reach `flight_desired.lua`'s own `fd_epoch` too; the gap was
  purely that body-layer's own handshake never noticed the echo had gone stale and so never
  resent.
- `_apply_flight_requests`/`_apply_ai_pilot_wheel_goal` are both gated on `runner.command_reset_
  confirmed` and, while the latch stayed stuck `True`, kept sending with `runner.command_reset_
  epoch` -- which no longer matched Lua's now-`nil` `fd_epoch` -- so `flight_desired.lua`'s
  `handle_flight_command` refused every one of them `r:epoch`. This reproduces the retest's second
  instance exactly ("off -> m1 voice take was again refused ... 'so no data'" -- refused via the
  ack path, not a bare timeout, which is consistent with a send that *did* go out, just against the
  wrong epoch).

**Fix**: `_resolve_command_reset` now checks the echo on every call, confirmed or not. A mismatch
on an already-`command_reset_confirmed` process flips it back to `False` and restarts both the
resend clock and the slow-confirm-warning clock (`command_reset_unconfirmed_since_wall`/`command_
reset_warned` reset to their fresh-process values) from *this* mismatch, rather than reusing
whatever cursor the original startup handshake left behind -- so an ordinary mission restart
reconfirms within a resend or two, exactly like a fresh process start, and the slow-confirm warning
does not fire just because the first handshake happened long ago.

**The gap before it reconfirms**: `_apply_flight_requests`/`_apply_ai_pilot_wheel_goal` stay gated
off while unconfirmed (unchanged) -- so once this fix flips `command_reset_confirmed` back to
`False` on a reload, nothing is sent carrying the stale epoch at all. A handover/goal dispatched in
that window has its one-shot transition field held, staged, until the next poll reconfirms and
sends it with the *right* epoch -- it is acted on or truthfully refused/timed out once Lua actually
answers, never silently dropped, and no readback is ever spoken for a request that was not applied.
**One residual, named rather than fixed**: an *unrelated* command dispatched in that same narrow
gap still clears the pending transition at the top of `handle_command` (the same "reset-at-top"
convention every one-shot field already has) -- a pre-existing window, not widened by this fix (it
already existed around the very first startup handshake), and not closed here. The player hears
nothing during the gap either way; `[[BL-B134]]`'s "stand by" readback (out of scope for this task,
per the coordinator's instruction) is what would give that feedback.

**Tests added** (`body-layer/tests/test_body_command_reset.py`, `TestCommandResetResync`):
confirmed -> one echo reverts to `None` -> resent and unconfirmed; confirmed -> echo changes to a
*different* non-null epoch -> same; the un-confirming edge resets the slow-confirm clock rather
than firing the warning off a stale cursor; and confirmed -> stale -> re-echoed (same, unchanged
`command_reset_epoch`) -> confirmed again. **One pre-existing test rewritten, not just extended**
(`test_already_confirmed_is_a_true_no_op` -> `test_already_confirmed_with_both_echoes_still_
matching_is_a_true_no_op`): the old test asserted the one-shot latch behaviour directly (confirmed
+ an echo that had never actually matched -> still a no-op), which is exactly the behaviour this
fix removes; rewritten to assert the correct invariant instead (confirmed + an echo that *still*
matches sends nothing), per this task's own explicit instruction to change the latch.

**Note for the coordinator's mid-task clarification** (AI-overlay handover after "you have
controls" is still a mode-2 handover, mode 2 never writes raw axes, only a fresh take returns mode
1): neither fix above touches `controls_to_player_edge`, `ai_pilot_wheel.lua`'s park/unpark
handling, or any mode-1/mode-2 transition logic -- the release-ack test only exercises `drain_
