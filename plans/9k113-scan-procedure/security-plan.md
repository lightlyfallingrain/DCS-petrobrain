## Security Plan Review: 9k113-scan-procedure (BL-B89 Stage 1)

### Dependencies Checked

No new dependency. `/extract-plan-deps plans/9k113-scan-procedure/plan.md` found no dependency
language in the plan at all (only an unrelated "do not reinvent the wheel" hit), and the plan's
own Affected Modules section lists only edits to existing `body-layer` modules
(`belief/optic_policy.py`, `perception/gaze.py`, `body.py`, their tests, `config/defaults.toml`).
No package import, no network client, no new file format.

### Design Findings

This stage is entirely internal to `body-layer`'s idle-search state machine: it renames/reduces an
enum (`SightSearchLeg`), adds one pure selection function (`choose_sighting_look`) that reorders
already-admitted `LookTarget`s, adds two sector-wedge tables consumed only by in-process geometry
functions, and adds/renames a handful of tunable range constants read from
`config/defaults.toml`/`config/tuning.toml`. Walking this against the in-scope categories:

- **Code execution / deserialization** — none. No `eval`/`exec`, no new parser, no new
  deserialization path. All inputs are already-believed simulation state (ranges, bearings,
  contact levels) computed upstream by code already reviewed.
- **Access to the computer / file paths** — none. No new file I/O; `config/defaults.toml` is
  regenerated by the existing `tools/generate_defaults.py --write` mechanism, unchanged in kind.
- **Network / LAN-port-scanner surface** — none. This stage adds no listener, no HTTP endpoint, no
  socket. It does not touch `aircraft-layer`'s Hook bridge or any transport.
- **LLM prompt injection** — none. Nothing here is text an LLM reads; `choose_sighting_look` and
  the sector tables operate on structured numeric/enum state, not free text, and Stage 2 (voice
  command parsing, not built this round) is explicitly deferred.
- **Dependency/framework CVEs** — n/a, no new dependency (above).
- **Secrets/credentials** — none introduced or referenced.

**Tunable bounds (the one category worth a security-shaped look here, since a pathological bound
could make a poll-loop-adjacent cycle misbehave):** the plan's new/changed tunables
(`SIGHT_SEARCH_NEAR_M`, `SIGHT_SEARCH_WIDE_MID_M`, `SIGHT_SEARCH_WIDE_FAR_M`) each carry `lo`/`hi`
bounds per the `X-T26` convention, and the plan explicitly flags the one known gap: no per-key
bound stops `NEAR_M` being tuned above `WIDE_MID_M` (etc.), producing an empty/inverted band. This
is the same documented residual-coupling shape already accepted for `belief.decay`, it requires a
local user edit to `config/tuning.toml` to trigger (not externally reachable — single-user,
LAN-only, no untrusted input feeds these values), and its worst effect is an empty search leg, not
a crash or a stuck loop (the lap-completion/`SIGHT_MAX_DWELL_S` glance-away still fires
regardless). Not a security blocker; it is a correctness/tuning concern, which the plan itself
already schedules as a "Decision Requiring User Input" (confirm the band placeholders) rather than
leaving silent.

### Passed to Reviewer

The following are player-experience/correctness matters for the Reviewer, not security findings,
and carry no verdict here: whether `choose_sighting_look`'s priority-bucket ordering matches the
user's stated intent; whether the sector-wedge tables (`SIGHT_SECTOR_WEDGE_DEG`, `SIGHT_AHEAD_LEGS`)
correctly reproduce the explore-notes' angular spans; the nose-up boresight-relative test coverage
at 50–800 m AGL; and the cross-key tuning coupling noted above as a possible source of an empty
search band in flight.

### Verdict

APPROVED
