# world-model/CLAUDE.md

Subproject instructions for the DCS World Model Builder. Augments the root `CLAUDE.md` — read that first for overall Petrobrain architecture; this file adds stack/testing/structure specifics that apply only within `world-model/`.

See `README.md`, `ROADMAP.md`, `WORKFLOW.md` in this directory for project design, milestone status, and the Mac/Windows cross-machine workflow. See `docs/CONVENTIONS.md` for the non-negotiable working rules (DCS reconnaissance, provenance/confidence, read-only DCS access).

## Tech stack

- Python 3.11+, fully type-hinted, `mypy --strict` (`pyproject.toml`).
- Formatter/linter: `ruff format` / `ruff check`.
- Test runner: `pytest`.
- **Coordinate transforms: `pyproj`** (M1 decision). Used for DCS x/z <-> WGS84 lat/lon via `+proj=tmerc +axis=neu`, in `src/coordinates/`. This decision is scoped to coordinate transforms only — the separate spatial-storage question (GeoPackage/SpatiaLite/FlatGeobuf/GeoPandas etc.) is **deferred to M5**: M3 confirmed no DB is needed yet (its only persisted artifact is a raw Overpass JSON cache; parsed features live as in-memory dataclasses for one tool invocation — no point-in-polygon/nearest-neighbor/multi-feature-type join workload exists before M5's `describe_position(...)`). See `research/2026-09-03-m3-osm-overlay.md`.
- **Raster tile decoding: `pillow`** (M2 decision). RasterCharts tiles are standard DXT5/BC3 DDS images (NVTT-built, no ED-proprietary encoding) — Pillow's built-in DDS plugin (9.1+) decodes them with no extra native deps, in `src/raster/`. See `world-model/research/2026-09-03-m2-rastercharts-recon.md` for the format recon behind this choice.
- **Elevation / DEM: SRTM (M4 decision)**. DCS-side elevation comes from `land.getHeight`, Mission Scripting-only (same environment as `coord.LOtoLL`) — no offline heightmap exists, so extraction is always a live-mission probe (`tools/dcs-mission-probe/elevation_probe.lua`), parsed by `src/elevation/dcs_grid.py`. External comparison DEM is SRTM's flat `.hgt` format (either SRTM1 or SRTM3 — `src/elevation/dem.py`'s `SrtmTile` derives grid resolution from file size rather than assuming one), parsed with stdlib `array` only, no GDAL/rasterio dependency. See `world-model/research/2026-09-03-m4-elevation-recon.md` (recon) and `.../2026-09-03-m4-dcs-elevation.md` (results) for the findings behind this choice.
- **Persistent spatial storage: stdlib `sqlite3` + R\*Tree (M5 decision)**. One SQLite file per region (`data/world-model/<theatre>.sqlite`), geometry stored as JSON `[[x,z],...]` in DCS x/z metres rather than WKB or GeoPackage — no GDAL/GeoPandas dependency; QGIS access goes through a `tools/export_geojson.py` export instead of a native GeoPackage writer. Implemented in `src/store/`. This decision closes the spatial-storage question left open since M3. See `world-model/research/2026-09-03-m3-osm-overlay.md` (deferral) and `.../2026-09-04-m5-first-persistent-model.md` (decision + milestone results).
- **Roads: DCS-native `.routes`/`.rn4` binary parsing, not live-probe (M5 decision)**. `land.getClosestPointOnRoads`/`findPathOnRoads` are dropped entirely in favor of directly parsing `Mods/terrains/Syria/roads/Syria.routes`'s float64-triple polylines (scan-forward resync over a `landscape4::`-prefixed binary container), in `src/roadnet/`. Road type/subtype from `.rn4` is left `null` in M5 (row→geometry join unconfirmed). See `world-model/research/2026-09-04-m5-roadnet-byte-decode.md` for the byte-exact format decode behind this choice.
- **Towns/beacons: regex Lua parsers (M5 decision)**. `towns.lua` (a list, not a dict) and `beacons.lua` (`{x, y, z}` with the middle value as elevation) are parsed directly from DCS's own terrain Lua source with targeted regexes, in `src/dcs_data/`, rather than a live Mission Scripting probe. See `world-model/research/2026-09-03-m5-nodes-lua-probe.txt` for the source recon behind this choice.
- **World-model seam: HTTP, not in-process (MI-2 decision)**. `src/api/server.py`'s
  `WorldModelAPIServer` is world-model's first HTTP seam -- a read-only wrapper around
  `describe_position`/`find_place_by_name`/`line_of_sight_clear` for mission-interpreter's
  `world_enrich/world_model_client.py` to call over the network, mirroring `aircraft-layer` <->
  `body-layer`'s existing HTTP seam (`body-layer` <-> `world-model`'s in-process import remains the
  sole deliberate exception, per root `CLAUDE.md`'s "Module independence" note). Single-threaded
  `HTTPServer` (not `ThreadingHTTPServer`) since one server instance shares a single, not
  thread-safe-by-default, `sqlite3.Connection`.
- **Probe-tier data: a second, persistent SQLite store per region, not a column on the base store (M8 decision)**. `data/world-model/<region>-probe.sqlite`, alongside the unchanged base `<region>.sqlite`, holds chunk-by-chunk accumulated probe data (fine elevation, `surface_type`, ridge/valley) plus a tri-state coverage record keyed `(kind, chunk_ix, chunk_iz)`. The base store's contract is "always rebuilt from `data/raw/`"; probe data is not rebuildable from anything on disk (its source is a live DCS mission), so the two must never share a file whose lifecycle is delete-and-recreate. Implemented in `src/probe_store/` (schema/writer/reader/paths) and `src/store/chunks.py` (the theatre-anchored chunk lattice, anchored at the DCS x/z origin rather than any one region's corner). Read integration is `ATTACH`-based (`query.describe.describe_position`'s optional `probe_db_path`), so `store/reader.py` needed no change. See `plans/m8-incremental-store/plan.md` and `world-model/docs/M8_PROBE_STORE.md`.
- **OSM classified-feature cache: a third persistent SQLite store per region (osm-classified-cache decision)**. `data/world-model/<region>-osm-cache.sqlite`, sibling to `<region>.sqlite` and `<region>-probe.sqlite`, caches already-classified `store.models.StoredFeature` rows from `build.ingest_osm`/`osm.pbf`'s streaming parse -- extending M8's two-store pattern to a third instance ("expensive-to-recompute derived data that must survive a delete-and-recreate rebuild"), here because the ~25-30+ minute pyosmium-parse-plus-classify pass, unlike probe data, *is* rebuildable from `data/raw/`, just at a cost that hurts a DCS-driven rebuild loop. Population piggybacks on the same `stream_features`/`_flush_nodes`/`_flush_ways` pass `build.pipeline`'s `osm_pbf_path` branch already runs -- no second read of the `.osm.pbf`. Populated at a `.tmp` path and `os.replace`'d to its canonical path only after the full pass succeeds (`osm_cache.writer.finalize_cache`) -- existence at the canonical path is the only validity signal, no flag column. Invalidated (full rebuild, never a partial reuse) on any mismatch across `pbf_sha256` (streamed via `hashlib`, never loading the whole file), `pbf_size_bytes`, `build.ingest_osm.CLASSIFIER_VERSION`, `osm_cache.schema.OSM_CACHE_SCHEMA_VERSION`, and the region's bbox. Implemented in `src/osm_cache/` (schema/models/writer/reader/paths/hashing), mirroring `probe_store/`'s file layout. Cache-hit reads reuse the existing `store.writer.insert_features` per batch rather than a hand-rolled `ATTACH`+bulk-SQL copy (documented fallback if this proves too slow at real scale, not built). See `plans/osm-classified-cache/plan.md`.
- **OSM ingest: pre-filter to a landcover/settlement/water/coastline vocabulary, roads dropped entirely (osm-landcover-optimization decision)**. Job (a) gained a second step (RUN.md §2.4): `osmium tags-filter` against the committed `tools/osm_tags_filter.txt` expression file, run once after the country-clip merge, before job (b) ever reads the file -- cuts a country-scale merged extract's node count by roughly 85-87% before pyosmium even opens it. `osm.pbf`'s `stream_features` layers a second, in-process `osmium.filter.KeyFilter` on top (same key vocabulary) and now defines an `area()` callback, which makes `apply_file` run libosmium's two-pass multipolygon manager automatically -- multipolygon relations (Lake Assad, city/town/village place areas, forest relations with holes) assemble into real ring/hole geometry instead of the M9-era silent skip. `build.ingest_osm`'s classifier is three pure functions over tag dicts (`_classify_node`/`_classify_line`/`_classify_area`) producing five kinds: `named_place` (place/peak/dam points), `water` (river lines; lake/reservoir/river_area polygons), `coastline` (its own kind, not `water`, so `nearest_water` isn't swallowed by the coast), `settlement` (built-up/place polygons only -- no more landuse-grab-bag), `landcover` (forest/orchard/fields/scrub/barren polygons). **`road` is no longer an OSM-classified kind at all** -- DCS's own `.routes` layer is the sole road source now; `nearest_road_osm` is removed from `query.describe.PositionDescription` accordingly (it had zero consumers). A ring's holes are stored as a derived `tags["inner_rings"]` entry (`store/models.py`'s reserved-tag convention), not a new geometry column, so `store.schema.SCHEMA_VERSION` and the M8 probe-store pairing are unaffected. `MIN_AREA_M2` (5 ha) and `SIMPLIFY_TOLERANCE_M` (30 m, iterative Douglas-Peucker) keep polygon/hole/vertex counts bounded. **The tiling gate was assessed against the wrong polygon and has now been re-measured at theatre scale** (2026-09-16): Stage 6's small-extract validation named Lake Assad at 3,359 outer vertices "well short of the threshold", but Lake Assad is only the largest polygon *in the Latakia extract*. A full `syria-full` store holds a considerably larger one -- Atatürk Baraj Gölü at **13,097 outer + 127 hole = 13,224 vertices**, 3.9x Lake Assad -- with Karakaya Baraj Gölü (3,651) next and Lake Assad itself third (3,602 incl. holes). Theatre-wide totals cross-check exactly against the build's own `vertices_after_simplify` (2,010,767 = 1,921,115 outer + 89,652 hole across 77,381 area features). 13k still sits under the plan's "tens of thousands" tiling threshold, so the no-tiling decision stands -- but the margin is ~1.5x, not the ~6x the small-extract figure implied, and the next terrain module (or a tolerance change) could cross it. Re-measure at theatre scale, never on an extract, before treating that gate as settled again. `query.describe.describe_position` gained `nearest_coastline` (side `"sea"`/`"land"` via `geometry.signed_side_of_polyline`'s angle-weighted-pseudo-normal sign, unreliable within `position_uncertainty_m` of the line) and `inside_landcover` (smallest-area precedence, holes honoured; `None` means "no mapped landcover," never "confirmed open ground"). See `plans/osm-landcover-optimization/plan.md` and `research/2026-09-13-osm-landcover-optimization-validation.md`.

## Commands

```sh
ruff format world-model/src world-model/tests   # format
ruff check world-model/src world-model/tests    # lint
mypy world-model/src                             # type check (strict)
pytest world-model/tests -q                      # test
```

Run a single test: `pytest world-model/tests/path/to/test_file.py::test_name -q`.

## Testing

Every coordinate transform or spatial-query function must have at least one test against a known geographic control point (see `../docs/concept/WORLD_MODEL_BUILDER.md` "Validation"). A transform that "looks about right" without a control-point test is not done.

## Structure

- `src/` — pipeline code: DCS extraction, coordinate subsystem, OSM/DEM reconciliation, spatial DB, query API.
- `tools/` — one-off inspection/probe scripts (raster inspector, coordinate probes). Not part of the pipeline; exploratory.
- `research/` — dated findings from DCS/forum/community investigation. Required before encoding any claim about DCS internals into pipeline code.
- `tests/` — automated tests, including known geographic control points.
- `data/` — gitignored. `raw/` (untouched extracted/downloaded input), `processed/` (intermediate), `world-model/` (final per-theatre spatial DB).
