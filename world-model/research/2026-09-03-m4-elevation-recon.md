# M4 — DCS elevation extraction & external DEM recon

**Date:** 2026-09-03
**DCS version:** 2.9.29.27278 (per M0), findings below not yet reproduced against a live probe on this exact copy — see Unresolved
**Theatre:** Syria

### Question

Three open questions blocking M4 planning:
1. Is `land.getHeight` confined to the Mission Scripting environment (same constraint as `coord.LOtoLL`, M1), or is there an offline-extractable DCS terrain heightmap file?
2. Are `io`/`lfs` actually stripped from Mission Scripting by default in the installed DCS version — resolve directly, don't re-flag as unverified.
3. What external DEM source (SRTM vs Copernicus GLO-30) fits the Syria/Turkey theatre region and the existing dependency stack?

### Findings

**Q1 — `land.getHeight` environment and offline heightmap search**

1. **`land.getHeight(vec2)` is documented Mission Scripting-only, same as `coord.LOtoLL`** — **evidence:** documented — **source:** [Hoggit wiki, DCS func getHeight](https://wiki.hoggitworld.com/view/DCS_func_getHeight): `number land.getHeight(table vec2)`, Environment: Mission Scripting, added 1.2.0, takes `{x=, y=}` where `y` holds the z-coordinate (i.e. call as `land.getHeight({x=point.x, y=point.z})`). No Export-environment or GUI-environment variant is documented anywhere on Hoggit for `land.*` — the entire `land` singleton (`getHeight`, `getSurfaceHeightWithSeabed`, `getSurfaceType`, `isVisible`, `getIP`, `profile`, `getClosestPointOnRoads`, `findPathOnRoads`) is presented as one table with no per-function environment override, and Mission Scripting is the only environment stated. **Not yet reproduced-locally** — M1 confirmed `coord.LOtoLL` empirically against the live install; `land.getHeight` itself has not been called live in any prior session. Given both functions live in the same documented environment and `coord.LOtoLL` was confirmed to behave exactly as documented, this is reasonably high-confidence by analogy, but is still an inference, not a direct reproduction, for `land.getHeight` specifically.
2. **`Export.lua` (the separate, always-io/lfs-open environment) does not appear to expose `land.getHeight` or any terrain-geometry query** — **evidence:** forum-claim-unverified — **source:** WebSearch of Hoggit's `DCS_Export_Script`/`DCS_export` pages and community Export.lua examples (DCS-BIOS, DCS-ExportScripts). Export's documented API surface is the `LoGetXxx`/`LoSetCommand`-style aircraft/sensor telemetry functions, not `land`/`coord`/`world`. No evidence found of any community tool bridging `land.getHeight` into Export — if this bridge existed, some moving-map/EFB-style project would very likely already use it, and none surfaced in search. Treat "Export can query terrain height" as ruled out pending direct counter-evidence.
3. **No offline-extractable open heightmap/DEM asset found in the installed Syria terrain folder** — **evidence:** reproduced-locally (grep of a real file listing) — **source:** `world-model/data/raw/dcs/2026-09-02/DCS-files.txt`, full listing of `Mods/terrains/Syria/` (23 top-level entries). The only plausibly-relevant assets are under `surface/` (`Syria.ng5`, `Syria.onlay.sup4`, `Syria.surface5`, `Syria.tile`) and `surfaceDetails/` (`Syria.sd5`, vegetation `.ref`/`.sht` files) — proprietary Eagle Dynamics binary formats with no public specification found (not on Hoggit, not in any community reverse-engineering project turned up by search, unlike the RasterCharts/`clipmap` formats M2 already decoded). `terrain.cfg.lua.pak.crypt` at the terrain root is literally packed *and* encrypted (`.crypt` extension) — consistent with M1's Finding 5 that Syria's terrain config carries no readable projection/parameter text; ED appears to deliberately obscure this whole config layer, not just projection data specifically. No `.hgt`, `.dem`, `.raw`, `.asc`, or similarly-named flat heightmap file exists anywhere in the Syria terrain tree, nor is there a generic "heightmap" asset — the only filename matches for "height" across the entire install are a shader (`Bazar/shaders/heightmapFrameBufferCleaner.fx`) and an unrelated `Scripts/targetview/heightmap.conf` (a targeting-pod display feature config, not terrain data).
4. **Conclusion for Q1: no viable offline path exists; `land.getHeight` via a live-mission trigger script is the only currently-known extraction route**, exactly matching M1's `coord.LOtoLL` precedent. This was already the working assumption baked into `docs/concept/WORLD_MODEL_BUILDER.md`'s Milestone 4 wording ("extraction/probing mechanism," implying live probing) and M2's research note (Finding block on "Dense elevation sampling"), and this session's targeted file-listing search now directly supports it rather than leaving it merely assumed.

**Q2 — io/lfs sandbox status**

5. **`os`, `io`, and `lfs` are stripped from the Mission Scripting environment by default, in every DCS version checked by convergent community sources — evidence: forum-claim-unverified but strongly convergent across 3+ independent sources, not yet confirmed by reading this installation's actual `Scripts/MissionScripting.lua` content.** Sources agree on the exact mechanism: a `local function sanitizeModule(name) _G[name] = nil; package.loaded[name] = nil end` followed by `sanitizeModule('os')`, `sanitizeModule('io')`, `sanitizeModule('lfs')`, plus `_G['require']`/`_G['loadlib']`/`_G['package']` set to `nil`. Independent sources: [MOOSE official docs, "De-Sanitize DCS"](https://flightcontrol-master.github.io/MOOSE/advanced/desanitize-dcs.html) (a widely-used, actively maintained scripting framework whose users routinely hit this exact wall); a second, unrelated community repo (`jboecker/dcs-mission-planner`, `scripts/save-mission-state/MissionScripting.lua`) describing the same three `sanitizeModule` calls and the same workaround pattern; WebSearch results independently corroborating the same function name/behavior from ED forum thread titles ("Making lfs and io available in ME Script Environment"). This is convergent, technically specific evidence (exact function/variable names agree across unrelated sources over multiple years of DCS versions), which is much stronger than a single unverified forum claim — but it is still community-observed behavior of *a* shipped `MissionScripting.lua`, not a direct read of *this* install's copy, so it is labeled forum-claim-unverified rather than documented/reproduced-locally.
6. **This sandboxing is DCS's deliberate, standing security default (not a one-off bug or version-specific quirk)** — **evidence:** forum-claim-unverified, same sources as Finding 5 — the stated rationale (missions downloaded from an untrusted server could otherwise read/write the client's filesystem) is a permanent design constraint of Mission Scripting, not something expected to change across patches. The standard community "fix" is editing `MissionScripting.lua` to comment out the three `sanitizeModule` calls — **this is a DCS installation modification and is out of scope per this project's read-only invariant; do not do this.**
7. **A read-only-compliant path around the io/lfs restriction exists and does not require editing any DCS file: `net.log(string)`** — **evidence:** documented (Hoggit, thin) + forum-claim-unverified (behavior details) — **source:** [Hoggit wiki, DCS func log](https://wiki.hoggitworld.com/view/DCS_func_log): `net.log("string")` writes an INFO-level entry (`"LuaNET (Main): <string>"`) to the DCS log file. Hoggit's page is explicit that the *full* argument set is undocumented, but the basic single-string form is documented and stable. `net` is a separate module from `os`/`io`/`lfs` and is not touched by `sanitizeModule` in any source describing the sandbox (Finding 5) — it is the mechanism several community tools rely on specifically *because* it survives the default sandbox. The DCS log file (`Saved Games/DCS/Logs/dcs.log` per prior WORKFLOW.md path conventions) is written continuously during a running session regardless of mission-script sandboxing, and reading it afterward from outside DCS is a pure read of an existing DCS-managed log — not an installation modification. **This resolves the scaling problem the architect flagged**: instead of `trigger.action.outText` (on-screen, manual transcription, does not scale to a grid of dozens/hundreds of points) or `io.open` (likely blocked per Finding 5), a probe script can serialize each grid point's `(x, z, height)` as one `net.log(...)` call (or one call per row of JSON), and a separate read-only step parses `dcs.log` afterward for lines matching the probe's log prefix.
8. **Net conclusion for Q2: not fully resolved by documentation/forum evidence alone, but resolved enough to plan around.** The weight of convergent evidence says io/lfs are stripped by default; the practical implication for M4 is the same either way, because `net.log` avoids the question entirely (works whether or not io/lfs are open) and is preferable regardless for install-cleanliness reasons (it needs zero `MissionScripting.lua` edits even if io/lfs happen to be open on this install). A live probe would still directly settle it, but is no longer *load-bearing* for choosing M4's extraction mechanism — see Possible Approaches.

**Q3 — External DEM source**

9. **SRTM (30 m / SRTM1) — format is exactly as assumed: flat binary, stdlib-parseable, no new dependency** — **evidence:** documented — **source:** convergent WebSearch results (OpenTopoData SRTM dataset docs, Digital Earth Africa SRTM spec, Carleton Library DEM-formats guide) plus well-established public knowledge of the format: one `.hgt` file per 1°×1° tile (e.g. `N36E036.hgt`), big-endian signed 16-bit samples, 3601×3601 grid for SRTM1 (1 arc-second, ~30 m), row-major from the NW corner, void value `-32768`. This is directly parseable with Python's stdlib `struct` (or `array('h')` with a byte-swap for endianness) — **no GDAL/rasterio required**, confirming the architect's assumption. The Syria/Turkey study region (36–40°N, 36–38°E) needs on the order of 15 one-degree tiles.
10. **SRTM access has gotten harder since 2021 — NASA's official channel now requires an Earthdata login** — **evidence:** forum-claim-unverified (WebSearch synthesis, not independently confirmed by attempting a download this session) — **source:** WebSearch results citing NASA Earthdata's 2021 authentication requirement for direct HTTPS/S3 downloads (`LPCLOUD`/`SRTMGL1` collections), and USGS EarthExplorer similarly requiring a free account. This is registration friction, not a licensing restriction — SRTM itself remains a US-government public-domain product. A no-login mirror exists: **viewfinderpanoramas.org** (`viewfinderpanoramas.org/dem3.html`), which redistributes `.hgt`-format tiles (SRTM-derived, with voids filled from other sources) via plain HTTPS with no account — practical fallback if NASA/USGS registration is undesirable, at the cost of the tiles being a third-party-processed derivative rather than the raw NASA product.
11. **Copernicus DEM GLO-30 — no-login public access, but a different file format with a real dependency cost** — **evidence:** documented — **source:** [AWS Registry of Open Data, Copernicus DEM](https://registry.opendata.aws/copernicus-dem/) and its bucket [readme](https://copernicus-dem-30m.s3.amazonaws.com/readme.html): public S3 buckets `s3://copernicus-dem-30m/` (GLO-30, ~30 m) and `s3://copernicus-dem-90m/`, plain HTTPS/S3 GET, **no account or API key required** (AWS Open Data Sponsorship Program). Format is **Cloud-Optimized GeoTIFF (COG)** — internally tiled/compressed GeoTIFF. Unlike `.hgt`, this is not realistically stdlib-parseable: COG's internal tiling and DEFLATE/LZW compression means a correct reader needs either `rasterio`/GDAL (heavy new dependency, matches the architect's concern) or, at minimum, a TIFF-aware library (e.g. `tifffile`, still a new dependency not currently in the stack per M1–M3's `pyproj`/stdlib/`Pillow` toolset — and `Pillow`'s TIFF support does not reliably handle GDAL-style COG tiling/compression variants). Licensing: free for public use, but requires attribution — the bucket's own readme specifies exact required credit text (a named-source, non-share-alike attribution clause), a lighter-weight but analogous obligation to OSM's ODbL requirement M3 already handles.
12. **Recommendation: SRTM for M4** — flat `.hgt` format needs zero new dependencies (fits the existing `pyproj`/stdlib/`Pillow` stack exactly as M1–M3 established), public-domain-grade licensing, and the region's tile count (~15) is small enough that the registration friction (NASA Earthdata account, or the no-login viewfinderpanoramas mirror) is a one-time setup cost, not an ongoing pipeline dependency. Copernicus GLO-30 is higher-provenance and easier to fetch programmatically (no login at all), but its COG format would force adopting GDAL/rasterio (or at least a TIFF-tiling-aware library) purely to read elevation grids — a disproportionate dependency cost for M4's stated goal ("sample DCS elevation over a small region, generate a grid, compare with an external DEM"). If a future milestone needs Copernicus-grade absolute vertical accuracy or broader/easier scripted global coverage, revisit then; M4 does not need it.

### Possible Approaches

- **M4 Stage 1 extraction mechanism**: a live-mission trigger script (same pattern as `coord_probe.lua`), calling `land.getHeight({x=.., y=..})` over a regular grid of DCS-native `(x, z)` points covering the target small region, serializing `(x, z, height)` via **`net.log(...)`** (Finding 7) rather than `io.open` or `trigger.action.outText`. This sidesteps the io/lfs question (Finding 8) entirely and scales to however many grid points are needed in one mission run — Stage 1 should size the grid to whatever `net.log` throughput/log-size proves comfortable (untested this session; worth a small-N smoke test before committing to a large grid).
- **Read-side of the same probe**: a small read-only WSL/Windows-side step that greps `Saved Games/DCS/Logs/dcs.log` for the probe's log-line prefix and reconstructs the grid — purely reading an existing DCS-managed log file, no installation change.
- **If `net.log` proves awkward at scale** (e.g. line-length limits, log rotation mid-run, or the "undocumented full argument set" caveat from Hoggit causing unexpected behavior), fall back to the original `coord_probe.lua`-style `io.open` write — but first add a trivial, fully read-only WSL probe that just `cat`s the installed `Scripts/MissionScripting.lua` (no mission needed, no DCS launch needed) to directly settle Finding 5 rather than relying on community convergence. This is cheap and should probably be run regardless, since it's nearly free and would upgrade Finding 5 from forum-claim-unverified to reproduced-locally.
- **DEM ingestion**: SRTM `.hgt` per Finding 12; if NASA Earthdata registration is unwanted, use the viewfinderpanoramas.org no-login mirror (Finding 10) as the fetch source, same parser either way (both are `.hgt`-format).
- **If Copernicus-grade accuracy is later desired**: revisit with GDAL/rasterio explicitly scoped as a new dependency decision for Architect, not folded silently into M4.
- **User has indicated willingness to manually edit `MissionScripting.lua` to open io/lfs, if that turns out to be needed.** This is a real option and removes Finding 5's constraint entirely if exercised — but it directly conflicts with `world-model/CLAUDE.md`'s stated non-negotiable invariant, "Never modify the DCS installation." I have not treated this as license to plan around an edited install, and have not asked the user to make the edit. This is an Architect/user decision to make explicitly (and, if made, to record as a deliberate, scoped exception to the invariant — e.g. "io/lfs de-sanitized by user choice for M4 probing," not a silent bypass) — not something Investigator should assume or recommend. **My recommendation stands regardless: prefer `net.log` (Finding 7) even if io/lfs access is granted**, since it needs no install edit at all, works identically either way, and keeps the read-only invariant intact without sacrificing capability.

### Unresolved

- `land.getHeight` has not itself been called against the live install (only `coord.LOtoLL`, in the same documented environment, has been). Resolves with: the M4 Stage 1 probe script itself — first real-world confirmation will come from actually running it.
- Whether `os`/`io`/`lfs` are stripped in *this specific* installed `MissionScripting.lua` (2.9.29.27278) is not directly confirmed, only inferred from strongly convergent multi-year community evidence. Resolves with: a trivial read-only `cat Scripts/MissionScripting.lua` via WSL (no mission launch required) — cheap enough that it's worth doing even though `net.log` makes it non-blocking for M4.
- `net.log`'s practical throughput/line-length/rotation behavior under a large grid (dozens-hundreds of points) is untested — Hoggit itself flags the full argument set as undocumented. Resolves with: a small-N smoke test (e.g. 10 points) before committing to a full-region grid size.
- The proprietary `.surface5`/`.tile`/`.ng5`/`.sup4` terrain-mesh formats under `Mods/terrains/Syria/surface/` were not reverse-engineered this session (out of scope — `land.getHeight` already provides equivalent data through a documented API, so there's no pipeline need to crack this format, unlike RasterCharts in M2 which had no API equivalent).
- Whether Copernicus GLO-30 tiles could be read via a lighter-weight approach than full GDAL/rasterio (e.g. a minimal COG-subset reader) was not investigated in depth — moot given the SRTM recommendation (Finding 12), but would matter if a future milestone revisits Copernicus.
