# M5 recon — DCS-authoritative roads, water, surface, and named places

**Date:** 2026-09-03
**DCS version:** 2.9.29.27278 (per M0)
**Theatre:** Syria

### Question

M5 needs elevation (settled, M4), roads, settlements, water, and named places for a ~20x20 km region, plus `describe_position(theatre, x, z)`. The project invariant is "DCS is authoritative about the simulated world; external GIS augments, never overrides." Before finalizing the M5 plan: can DCS itself supply road/water/surface/named-place data, or is M5 necessarily OSM-derived (external, ~5 km displaced per M3) for everything except elevation?

### Findings

**Q1 — `land.getSurfaceType`**

1. **`land.getSurfaceType(vec2)` is documented Mission Scripting-only, same environment as `land.getHeight`** — **evidence:** documented — **source:** [Hoggit wiki, DCS func getSurfaceType](https://wiki.hoggitworld.com/view/DCS_func_getSurfaceType). Signature: `enum land.getSurfaceType(table vec2)`, added 1.2.4. Argument shape matches `getHeight`: `{x=.., y=..}` where `y` holds the DCS z-coordinate (confirmed by the Hoggit usage note: "convert trigger-zone vec3 by setting the y-component to the z-value").
2. **SurfaceType enum is documented with 5 values distinguishing ROAD and WATER separately** — **evidence:** documented — **source:** same Hoggit page. `LAND=1, SHALLOW_WATER=2, WATER=3, ROAD=4, RUNWAY=5`. This directly answers the key sub-question: yes, a sampled grid of `getSurfaceType` calls can in principle produce both a DCS-authoritative water mask (`WATER`/`SHALLOW_WATER`) and a DCS-authoritative road mask (`ROAD`) for the same region in the same pass, at whatever grid resolution is sampled — no separate call needed to distinguish them.
3. **Not yet reproduced locally.** Like `land.getHeight` before M4's Stage 1/2 probes, `getSurfaceType` has not itself been called against the live install this session — only documented via Hoggit, by analogy to `getHeight`'s already-confirmed behavior (M4).
4. **Important limitation for a "road mask": `getSurfaceType` returning `ROAD` at a sampled point only tells you that exact point is road surface — it gives no width, centerline, or connectivity.** A grid coarser than actual road width (which can be a few meters) will alias: sparse grids will miss most roads entirely, catching only where a grid point happens to land on pavement. This makes `getSurfaceType` alone a poor tool for road *geometry* — see Q2 for the geometry-capable functions.
5. **One live ED forum wishlist thread exists titled "land.getSurfaceType small enhancement"** — **evidence:** forum-claim-unverified (unread) — **source:** `forum.dcs.world/topic/369869-landgetsurfacetype-small-enhancement/`. This 403'd on automated fetch (WebFetch), consistent with prior sessions' experience that forum.dcs.world blocks automated fetch (see agent memory `forum-dcs-world-fetch.md`). Not read this session. If the enhancement request reveals a known limitation of the current function, it's not captured here — **ask the user to open this URL manually and paste the content back if it matters for M5 planning.**

**Q2 — `land.getClosestPointOnRoads` and `land.findPathOnRoads`**

6. **Both documented Mission Scripting-only, added patch 2.5** — **evidence:** documented — **source:** [Hoggit wiki, getClosestPointOnRoads](https://wiki.hoggitworld.com/view/DCS_func_getClosestPointOnRoads), [Hoggit wiki, findPathOnRoads](https://wiki.hoggitworld.com/view/DCS_func_findPathOnRoads).
7. **`getClosestPointOnRoads` signature: `number, number land.getClosestPointOnRoads(string roadType, number xCoord, number yCoord)`** — takes **plain numeric x/y args, not a vec2 table** (unlike `getHeight`/`getSurfaceType`) — returns two numbers (x, y of nearest road point). `roadType` accepts `'roads'` or `'railroads'`.
8. **`findPathOnRoads` signature: `table land.findPathOnRoads(string roadType, number xCoord, number yCoord, number destX, number destY)`** — returns a numerically-indexed table of vec2 waypoints along the route. **Documented bug: the railroad-type string for this function is actually `'rails'`, not `'railroads'`** — inconsistent with its sister function `getClosestPointOnRoads`, which does use `'railroads'`. This is a real, documented-on-Hoggit landmine worth encoding directly in any pipeline code that calls both functions.
9. **Documented performance note: `findPathOnRoads` "can return a high number of points over a relatively short route"** — **evidence:** documented (Hoggit usage note) — **source:** same page. No numeric bound given.
10. **No community reports found of `nil`/garbage results far from roads for either function** — **evidence:** unresolved (absence of evidence, not evidence of absence). Targeted searches (web search, MOOSE Core.Point wrapper docs) turned up no bug reports, no caveats in the MOOSE wrapper (`GetClosestPointToRoad`, `GetPathOnRoad`) beyond one-line descriptions, and no forum threads surfaced. This does not confirm the functions are well-behaved arbitrarily far from any road (e.g. deep desert, mid-Mediterranean) — it only means no evidence of misbehavior was found. **A live probe testing both functions from a point known to be far from any road (e.g. open desert east of Palmyra) would resolve this directly and cheaply** — worth including as a smoke-test point in the M5 Stage 1 probe regardless of what else is sampled.
11. **Feasibility assessment for deriving DCS-authoritative road *geometry* over 20x20 km**: two candidate mechanisms, different cost/quality tradeoffs.
    - **Grid-snap via `getClosestPointOnRoads`**: sample a regular grid (e.g. 200-500 m spacing → 1,600-10,000 points for 20x20 km), call `getClosestPointOnRoads('roads', x, z)` at each, keep points whose returned nearest-road-point is within some small threshold of the query point (i.e. actually near/on a road) or record every (query, snapped) pair and post-process for line reconstruction. This is a single-call-per-point operation, same cost class as `getHeight`, and produces snapped points near roads but **not necessarily connected polylines** — reconstructing centerlines/topology from scattered snapped points is a real, non-trivial post-processing problem in `src/`, not something the probe itself solves.
    - **`findPathOnRoads` between point pairs**: gives an actual connected polyline for a specific route, richer than grid-snap, but only for roads reachable between the two query points, is more expensive per call (unknown, likely non-trivial given "high number of points" warning), and needs some strategy for choosing which point-pairs to query to cover a whole 20x20 km road network (e.g. corridor sampling along a coarse grid-snap result) rather than random pairs.
    - **Recommendation**: grid-snap first, as a research-only capability at this stage — it's the cheaper, more uniform mechanism and is realistic to run in one mission session at 250-500 m spacing (a few thousand calls, same order of magnitude as M4's already-tested 100-point grid, just scaled up — see Q3). `findPathOnRoads` should be treated as a follow-up refinement (e.g. snap-then-path between adjacent grid cells that show a road, to recover connectivity) rather than the primary extraction mechanism for M5, and its cost/behavior needs its own small smoke test before being relied on at scale. **Neither mechanism is validated locally yet — this is a plan for Architect/Implementer to schedule as a probe, not evidence "it works."**

**Q3 — Probe scale limits**

12. **M4 precedent**: a single mission-scripting `DO SCRIPT FILE` trigger already ran 100 `land.getHeight` calls plus `io.write` with no observed problem (`research/2026-09-03-m4-dcs-elevation.md`). That's the only locally-reproduced data point on cost so far.
13. **No documented hard watchdog/timeout limit for Mission Scripting trigger execution was found** — **evidence:** forum-claim-unverified / inferred — **source:** web search of Hoggit's Mission Scripting Tools Documentation and forum threads turned up only the general, oft-repeated community claim that "a hung script can hang the entire server and a slow script can slow the entire server" (no ED-official numeric watchdog threshold found), plus confirmation that a **busy-wait loop** (`while timer.getTime()~=time+10 do end`) is known to crash/hang DCS. This is a different failure mode than "many quick sequential calls" (M5's use case) — a tight busy-wait blocks the sim clock itself, whereas thousands of quick `land.*` calls executing once and returning is closer to what M4 already validated at n=100, just larger n. No numeric ceiling (in call-count or wall-clock terms) was found for the latter case.
14. **`timer.scheduleFunction` chunking across scheduled ticks is the standard, documented community pattern for spreading large loops across multiple frames to avoid a single-frame stall** — **evidence:** documented — **source:** [Hoggit wiki, DCS func scheduleFunction](https://wiki.hoggitworld.com/view/DCS_func_scheduleFunction) plus convergent community threads (ED forums `timer.scheduleFunction()` topic, "A note on DCS Scripting scheduleFunction"). Mechanism: the scheduled function processes one chunk (e.g. N grid points) per call, then returns `model_time + delay` to reschedule itself for the next chunk, until all chunks are done. This is a general DCS scripting idiom, not specific to terrain sampling — no DCS-terrain-specific bulk-sampling community project was found by search (searches for DCS-gRPC, Olympus, LotATC, and generic "terrain export mod" turned up no hits actually doing bulk `land.*` grid sampling; those projects instead do live per-unit telemetry, not offline terrain-grid dumps).
15. **`net.log` throughput/line-limit behavior remains untested at the scale M5 would need** (already flagged unresolved in M4's recon note, carried forward here) — the M4 mechanism used `io.write` to a `.jsonl` file (100 lines, no issue), not `net.log`; M5's 1,600-10,000+ point grid, especially with 2-3 calls per point, has not been tested with either mechanism at that scale.
16. **Recommended concrete pattern for M5's probe** (synthesizing 12-15, not yet run): chunk the grid into batches of a few hundred points (matching M4's already-proven n=100 order of magnitude, scaled conservatively) driven by `timer.scheduleFunction`, with each batch calling `getHeight`/`getSurfaceType`/`getClosestPointOnRoads` per point and appending to the same `io.open(...,"a")` output file (append mode, not truncate) rather than building one giant in-Lua table and writing once at the end — this avoids both a single large-loop stall and keeping the whole result set in memory. Do a smoke test at n=100-200 (same order as M4 Stage 1) with all three calls before committing to a full 1,600-10,000-point run, and add a smoke-test point Q2's Finding 10 needs (a point deliberately far from any road) into that same batch.

**Q4 — Settlements / named places from DCS**

17. **`Mods/terrains/Syria/map/towns.lua` is a real, DCS-shipped, plain (unencrypted, uncompressed) Lua data file, distinct from the towns.lua guess in M1's earlier recon (M1 only noted the filename existed, did not read contents) — evidence: reproduced-locally — source:** `world-model/data/raw/dcs/2026-09-03/syria_terrain_lua_probe_20260903T075625Z.txt` (full-text WSL `cat`, read-only, no install modification), 1187 lines / **1186 named entries**. Format per entry:
   ```lua
   ["Aleppo"] = { latitude = 36.219471, longitude = 37.142091, display_name = _("Aleppo")},
   ```
18. **This is a DCS-authoritative name+position gazetteer, but it is point-only (no polygon/extent, no settlement-size/category field) and it mixes settlement names with a broad range of other named points** — **evidence:** reproduced-locally, same source. Confirmed content spans: major cities (Aleppo, Damascus, Homs, Beirut, Amman, Jerusalem, Tel Aviv), small villages by the hundreds (mostly Turkish/Syrian/Lebanese/Cypriot toponyms), named military installations (e.g. "SAA 4th Armoured Division", "SyADF 159th Regiment", "Army Vehicle Training Ground"), landmarks (e.g. "Dome of the Rock", "Church of the Holy Sepulchre", "Ataturk Dam"), and commercial POIs (e.g. "Adana Hilton", "Kings Avenue Mall", "Sourasky Medical Center"). There is no `category`/`type` key distinguishing these classes in the dumped file — every entry has exactly `latitude`, `longitude`, `display_name`. Coordinates are in real-world lat/lon (matching known real-world locations, e.g. Damascus at 33.518073/36.296386 is correct within normal precision), i.e. this is the same lat/lon frame as the beacon `positionGeo` fields already cross-validated in M1/M4.
19. **Practical consequence for M5**: this file is a legitimate DCS-authoritative *name* source that should not be ignored — it directly contradicts a blanket "names come from OSM" stance for at least the subset of named places DCS itself chose to label (this is very likely the data source backing F10 map labels at zoomed-out view, though that specific F10 rendering link is inferred, not directly observed this session). However, because entries have no extent/polygon and no settlement-vs-POI distinction, `towns.lua` alone cannot supply settlement *boundaries* the way OSM's building/landuse polygons could — it supplies a name-at-a-point, comparable in kind to OSM's `place=*` node (not `landuse=residential` polygon) data. **Revised stance for Architect: names AND position (for the point/label itself) can be DCS-authoritative via `towns.lua` for any place DCS chose to name; OSM remains necessary only for settlement *extent/footprint* and for names DCS didn't bother to label (small villages very likely under-covered relative to OSM's finer-grained coverage — not verified by direct count comparison this session).** This changes the M4-recon-era assumption; Architect should decide whether M5 prefers `towns.lua` as primary name source (DCS-authoritative, no displacement, matches invariant) with OSM as a supplement for finer settlement coverage/extent, or some other split.
20. **`towns.lua` requires no live mission / no Mission Scripting environment to read — it is a plain data file, readable exactly like `beacons.lua`/`entry.lua` via a read-only WSL `cat`/grep, already proven this session and in M1.** This is strictly easier and more reliable than the Q1-Q3 mechanisms — no probe-scale risk, no io/lfs sandbox dependency, fully offline-extractable once synced from the Windows machine. It should be pulled into `world-model/data/raw/dcs/` as a first-class dependency for M5, and a small parser belongs in `src/`, not `tools/` (per `world-model/CLAUDE.md`'s src/tools split) once Architect scopes it.
21. **`MissionGenerator/nodes.lua` (93 lines) and `MissionGenerator/nodesMap.lua` (1 line) exist in the same terrain tree and were not read this session (only grepped for projection keywords, which found no matches — expected, since these are unlikely to use `latitude`/`longitude` keys)** — **evidence:** inferred / unresolved. Given the "MissionGenerator" naming and their presence alongside `towns.lua`/`beacons.lua`, these are plausibly an AI-mission-generation road/waypoint node graph — which, if so, could be a second DCS-authoritative source for road *topology* independent of the Q2 live-mission functions, and would need no live mission to read (same read-only `cat` mechanism as `towns.lua`). **This is a promising, unresolved lead**: a follow-up read-only WSL probe (`cat Mods/terrains/Syria/MissionGenerator/nodes.lua Mods/terrains/Syria/MissionGenerator/nodesMap.lua`) is cheap (two small files) and should be run before committing to the Q2 live-mission road-extraction mechanism as the only option — if `nodes.lua` turns out to encode a road graph, it could replace or supplement Q2's approach entirely, at far lower probe-scale risk.

### Possible Approaches

- **Road/water/surface (Q1/Q2)**: primary mechanism is a live-mission Mission Scripting probe combining `getHeight` + `getSurfaceType` (+ `getClosestPointOnRoads` for road geometry) per grid point, chunked via `timer.scheduleFunction` per Finding 16, output via incremental-append `io.write` (following M4's proven `io`/`lfs` sandbox-edit precedent, user-authorized). This can produce a DCS-authoritative surface/water/road-proximity raster over the 20x20 km region in one mission run at 250-500 m spacing, entirely analogous to and buildable on top of M4's `elevation_probe.lua` pattern (same points, same trigger, extra fields per line).
- **Road *topology* (Q2)**: treat grid-snap (`getClosestPointOnRoads`) as the first cut; treat `findPathOnRoads`-based connectivity recovery as a stretch goal, not required for M5's initial pass — OSM road geometry (already available per M3, ~5 km displaced but internally consistent) remains a viable fallback/cross-check for connectivity even if DCS-native topology reconstruction proves too costly, consistent with "DCS authoritative, OSM augments" (DCS supplies confirmed road *presence* at sampled points; OSM's road graph, once corrected for the known M3 displacement, can supply connectivity as an augmentation rather than an override).
- **Named places (Q4)**: adopt `towns.lua` as the primary DCS-authoritative name+point source for M5's "named places" layer; use OSM only to fill gaps `towns.lua` doesn't cover (small settlements without a labeled entry) and for settlement *extent* polygons, which `towns.lua` cannot provide. This directly satisfies "DCS is authoritative, external augments" for names in a way the M4-era working assumption ("names come from OSM") did not anticipate — Architect should treat this as a plan-changing finding, not a minor addendum.
- **Cheap follow-up before committing M5's road-extraction design**: read `MissionGenerator/nodes.lua`/`nodesMap.lua` in full (Finding 21-22) — if they encode a road/waypoint graph, this could substantially de-risk or replace the Q2 live-mission mechanism. **The probe script to do this is now written and staged (Finding 22) — it just needs to be run on the Windows machine.**
- **Test-region choice (Finding 26)**: if Architect wants M5's small-region demo to showcase a DCS-authoritative named-place layer, the Gemerek envelope is the wrong region for that — `towns.lua` has zero coverage there. Either pick/add a second small test region within `towns.lua`'s actual coverage (e.g. somewhere in the Aleppo/Homs/southern-Turkey band) for the named-places layer specifically, or knowingly scope Gemerek's named-places layer as "OSM-only, by observed necessity, not by unexamined default" — a materially different framing than the original M4-era "names come from OSM" assumption this session was meant to correct.
