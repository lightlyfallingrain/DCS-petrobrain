# M5 Stage 5 — light perf measurements

**Date:** 2026-09-04
**DCS version:** 2.9.29.27278 (per M0) — no live DCS access this session, all
measurements against already-staged local files and the already-built store.
**Theatre:** Syria, region `latakia-20km`.

### Question

Per `plans/m5-first-persistent-model/checklist.md` Stage 5 ("light perf"): measure
rebuild wall time, `.sqlite` size, `describe_position` latency over ~100 points, and
— the one check that actually matters this stage — the full `Syria.routes` walk's
wall time and peak memory, to confirm or refute Stage 2's claim that
`roadnet.routes.iter_routes` streams rather than loading the 2.25 GB file into
memory. This is a measurement stage, not an optimization stage: no new production
code was expected or written, only a throwaway measurement script
(`tools/measure_m5_stage5_perf.py`, four independent subcommands: `latency`,
`routes-walk`, `rebuild`, `sqlite-size`).

### A regression this session caught and fixed

The first `rebuild` run used `build_world_model.py`'s bare CLI (no `--probe-output`
flag) because that flag has no registered default for `latakia-20km` in
`_DEFAULT_RAW_PATHS` (unlike `--towns`/`--beacons`/`--osm-cache`/`--routes`, which
do). That silently produced a "probe: skipped" build and **overwrote the real
Stage 3/4 store, dropping its 1,681-point elevation/surface_type grid** (`grid`
rows: 0, `grid_sample` rows: 0, down from 2/3,362). Caught by inspecting the
rebuilt store directly rather than trusting the CLI's summary output alone.
Fixed by passing `--probe-output` explicitly at
`data/raw/dcs/2026-09-04/terrain_probe_output_full.jsonl` (the Stage 3 full-rung
probe output already staged locally) in `measure_m5_stage5_perf.py`'s `rebuild`
subcommand, and re-running. All numbers below are from the **corrected**,
probe-inclusive rebuild. `--srtm-tile` was left unset — no local SRTM tile
for Latakia is staged (`data/raw/dem/` only has Gemerek's M4 `N39E036.hgt`) —
per `build.pipeline.build_region`'s contract this is a safe no-op (the SRTM
delta stays absent from grid stats, not an error), an already-accepted M5
deferral, not a Stage 5 gap.

Post-fix verification:
- `grid` rows: 2 (elevation + surface_type); `grid_sample` rows: 3,362 (1,681 × 2)
  — matches Stage 3/4's expected counts exactly.
- `describe_position` at the region centre (44934.892, 5685.076) returns
  `elevation.dcs_m=37.1263` and `surface_type.value="LAND"` (both correctly
  non-null) — confirms the fix at the query layer, not just a row count.

`tools/build_world_model.py latakia-20km --probe-output
data/raw/dcs/2026-09-04/terrain_probe_output_full.jsonl` (region + towns + beacons
+ OSM + roadnet + full 1,681-point probe grid, timed end to end as a subprocess via
`time.perf_counter`):

**430.9 s (~7.2 min)**

Build summary (feature counts, unchanged from Stage 4's real-store numbers):
`airfield=1, named_place=108, navaid=8, road=3266 (3136 OSM + 130 DCS), runway=2,
settlement=338, water=117`; roadnet stats `routes_found_whole_file=14833,
routes_in_region=130, resync_events=14833, sync_loss_events=220,
bytes_covered=2249111022`; probe stats `points_expected=1681,
points_received=1681, surface_type_counts={WATER: 412, LAND: 1236, ROAD: 29,
RUNWAY: 4}`.

As Stage 2 already found, the `.routes` walk dominates total build time by roughly
two orders of magnitude over every other ingest stage combined (towns/beacons/OSM
ingest is sub-second; the probe-grid ingest of 1,681 already-collected points is
also sub-second — only the live DCS probe collection, not measured here, is slow
for that stage).

### Measurement 2 — `.sqlite` file size

`data/world-model/latakia-20km.sqlite`, corrected (grid-restored) build:

**8,982,528 bytes = 8.57 MB (8.57 MiB)**

Unchanged from the pre-Stage-5 store's size to the byte — SQLite reused freed
page space from the dropped-then-restored grid rows rather than growing the file,
which is expected `VACUUM`-free SQLite behaviour, not evidence the grid data is
missing (row counts were independently verified above).

### Measurement 3 — `describe_position` latency, 100 points

100 points sampled across the Latakia region (80 uniform within the region's own
20×20 km bbox, 20 extended out to 1.5× the half-extent to include near-boundary
and outside-coverage points, fixed seed for reproducibility — see
`_sample_points` in the measurement script), each timed individually with
`time.perf_counter` around a single `describe_position` call (not batch wall-clock
divided by count):

| stat | value |
|---|---|
| mean | 89.0 ms |
| median | 71.3 ms |
| p95 | 223.7 ms |
| p99 | 275.0 ms |
| min | 31.6 ms |
| max | 304.0 ms |

(A near-identical run against the probe-skipped store, before the regression fix,
gave mean 89.7 ms / median 71.9 ms / p95 223.3 ms / p99 270.9 ms — consistent to
within noise, confirming the grid fix didn't materially change query latency, as
expected since `describe_position`'s grid lookups are cheap in-memory dict/array
reads once the small `grid_sample` table is loaded.)

No index or query-shape work is indicated by these numbers — sub-300ms p99 for an
offline single-user local pipeline with no hot path is well within what this
phase needs. The mean/p95 gap (89 ms vs 224 ms) is consistent with SQLite R*Tree
range-query variance depending on how many candidate features a given point's
bbox search touches (e.g. a point near many OSM road/building-adjacent features
vs. open water), not measured further this session since nothing here indicates
a problem.

### Measurement 4 — full `.routes` walk: wall time + peak memory (the key check)

Run **standalone**, isolated from the full build pipeline, via
`tools/measure_m5_stage5_perf.py routes-walk` (just `roadnet.routes.iter_routes`
walking the full local `Syria.routes`, no store/ingest code involved), wrapped in
`/usr/bin/time -l` for an external cross-check of the script's own
`resource.getrusage` self-report:

```
wall_time_s: 446.26
routes_found: 14833
bytes_covered: 2249111022 (of 2,251,462,776 total -- 99.90%)
resync_events: 14833
sync_loss_events: 220
```

(`routes_found`/`bytes_covered`/`resync_events` agree exactly with the full
rebuild's in-pipeline walk above and with Stage 4's resync-fix numbers, a useful
determinism check on the parser independent of this stage's actual perf ask.
`sync_loss_events=220` matches Stage 4's post-resync-fix figure, not re-litigated
here — see `plans/m5-first-persistent-model/implementation.md` Stage 4.)

**Peak memory — two numbers, and the distinction between them matters:**

```
2280800256   maximum resident set size   (~2.18 GB)
  22497056   peak memory footprint       (~22.5 MB)
```

Both are from the same `/usr/bin/time -l` invocation of the same process. On
macOS, **"maximum resident set size" is not the number to read as "how much
memory did this program's own working set use."** It counts every page of the
`mmap`-ed `Syria.routes` file that the OS ever mapped into the process's resident
set as the walk touched sequential regions of the file — those pages are
clean, file-backed, and trivially reclaimable by the OS under memory pressure
(this is exactly what `mmap` is for), not heap allocated by
`roadnet.routes.iter_routes`. Because the walk eventually touches nearly the
whole 2.25 GB file, RSS accumulates to nearly the file's own size — that is a
property of `mmap`+sequential-scan, not evidence the streaming claim is false.

**"Peak memory footprint"** is macOS's own actual-heap/dirty-memory metric —
the number that answers "how much did this process actually allocate," excluding
reclaimable clean file-backed pages. At **~22.5 MB** for a walk over a 2.25 GB
file, this is the number that confirms Stage 2's claim
(`roadnet/routes.py`'s own docstring: "never loads `.routes` into memory"):
**peak footprint stays flat and low regardless of file size — it does not scale
with the 2.25 GB input.** No accidental full-buffer materialization was found in
`iter_routes`, and none was expected given this result.

**Conclusion: the streaming claim holds.** Reporting only "maximum resident set
size" without this distinction would have looked like a ~2.18 GB memory blowup
and been a false alarm; reporting only "peak memory footprint" without explaining
why the other number is so much larger would have looked like cherry-picking the
flattering metric. Both are reported here with the mechanism explained, per this
stage's instruction not to gloss over a memory-scaling finding either way.
