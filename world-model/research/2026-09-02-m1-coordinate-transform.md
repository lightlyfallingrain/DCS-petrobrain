# M1 — DCS local x/z ↔ WGS84 coordinate transform (Syria)

**Date:** 2026-09-02
**DCS version:** 2.9.29.27278 (per M0 probe, `2026-09-02-m0-dcs-install.md`) — projection findings below are NOT yet re-verified against this specific installed copy; see Unresolved.
**Theatre:** Syria

### Question

What map projection does DCS actually use for a theatre's local x/z grid, how is the origin defined, is `coord.LOtoLL`/`coord.LLtoLO` usable as ground truth, and can we find at least one control point with both a DCS-native coordinate and an independently-sourced real-world lat/lon, for Syria specifically?

### Findings

1. **Projection type — Transverse Mercator, not Lambert Conformal Conic** — **evidence:** forum-claim/community-tool-derived, but internally consistent and independently plausibility-checked (see Reproducible Test) — **source:** [pydcs](https://github.com/pydcs/dcs) `dcs/terrain/projections/transversemercator.py` (`TransverseMercator` dataclass: `central_meridian`, `false_easting`, `false_northing`, `scale_factor`, hardcoded `lat_0=0`; builds a `+proj=tmerc` PROJ4 string with `+ellps=WGS84 +axis=neu`) and `dcs/terrain/syria/projection.py` (Syria's fitted parameters, see below). This directly contradicts the "Lambert Conformal Conic per theatre" folklore claim — no ED source, forum thread, or code found says Lambert. The Lambert claim's likely origin (inferred, not confirmed): real-world VFR/IFR aeronautical charts (which DCS terrain art is built from) conventionally use Lambert Conformal Conic — plausible conflation of the source cartography's projection with DCS's internal engine coordinate system, but this is speculation, not a traced source.
2. **Syria's specific fitted parameters (pydcs)** — **evidence:** forum-claim/community-tool-derived — **source:** `dcs/terrain/syria/projection.py`, file header states "generated by tools/export_map_projection.py" (i.e. not hand-entered, but fitted from live-game data — see finding 5): `central_meridian=39`, `false_easting=282801.00000003993`, `false_northing=-3879865.9999999935`, `scale_factor=0.9996`.
3. **Axis convention x=north, z=east, y=up** — **evidence:** documented — **source:** official ED FAQ, [digitalcombatsimulator.com/en/support/faq/1256](https://www.digitalcombatsimulator.com/en/support/faq/1256/) ("Basic terms and types"): "x is directed to the north", "z is directed to the east", "y is directed up", units in meters, "DCS ground is an infinite plain." This is the one part of the projection question that is ED-documented, not folklore — but ED does not state which projection produces this plane from geodetic coordinates.
4. **Origin/reference point** — **evidence:** inferred from pydcs's derivation method, not independently confirmed against the installed Syria terrain — **source:** pydcs `tools/coord_export.lua`. There is no Lua table in the terrain files (per grep of `DCS-files.txt` filenames — see Findings 8) with an obviously-named "origin"/"central meridian" field; pydcs instead *empirically derives* the origin/parameters by calling `coord.LOtoLL` on the theatre's `(0,0,0)` point and on every airbase from a live running mission, then curve-fits a `tmerc` projection to that sample set (`compute_tmerc_parameters()` in `tools/export_map_projection.py`, tries UTM-style 6° central meridians and picks the best fit). So: **empirical derivation, not a directly-readable config value**, at least via this method. Whether Syria's own terrain Lua (e.g. `entry.lua`) states projection parameters directly is still open — DCS-files.txt is filename-only and doesn't contain file contents (see Findings 8/Unresolved).
5. **coord.LOtoLL / coord.LLtoLO availability** — **evidence:** documented (Hoggit) — **source:** [Hoggit wiki, DCS func LLtoLO](https://wiki.hoggitworld.com/view/DCS_func_LLtoLO): `vec3 coord.LLtoLO(lat, lon, alt)`, environment = "Mission Scripting", added Game Patch 1.2.0; `coord.LOtoLL` is the documented inverse. Both are Mission Scripting environment functions — **they require a running mission**, not callable from an external/offline process, confirming the workflow implication in the question. This matches pydcs's own approach: `tools/coord_export.lua` is a Lua script loaded via a mission trigger (`DO SCRIPT FILE`) while DCS is running, iterating `world.getAirbases()` and calling `Airbase.getPoint()` + `coord.LOtoLL()`, plus a `(0,0,0)` origin call — i.e. the best available community precedent for this exact task uses live in-game execution, not static file parsing.
6. **Circularity risk — confirmed, must be flagged explicitly** — **evidence:** reproduced-locally (traced pydcs source) — **source:** `tools/coord_export.lua`. pydcs's "known" airbase lat/lon values, which its projection fit is checked against, come from `coord.LOtoLL` itself (applied to each airbase's native DCS point) — not from an independent real-world airbase database. So pydcs's own internal self-consistency check (its parameters reproduce `coord.LOtoLL`'s output) does **not** constitute independent validation. Any control-point test we build must use a real-world-sourced lat/lon (e.g. published ARP) that was never derived from DCS, exactly as the architect's question anticipated.
7. **Independent control point — Damascus International Airport (OSDI)** — **evidence:** reproduced-locally (see Reproducible Test) — **source:** pydcs `dcs/terrain/syria/airports.py`, class `Damascus`, DCS-native position `Point(x=-178652.320313, y=52081.296875)` (pydcs `Point` uses `x`=northing, `y`=easting per the `+axis=neu` transformer wiring in `dcs/mapping.py`, i.e. this maps directly onto DCS-native `(x, z)`). Cross-checked against Wikipedia's published Damascus Intl (OSDI) ARP, 33.41139°N, 36.51556°E (cross-referenced by SkyVector/PlaneMapper-class sources, itself not derived from DCS). Running the Syria `tmerc` parameters from Finding 2 through a standard PROJ4 transform on the pydcs Damascus point gives **33.42551°N, 36.51851°E — 1594 m from the published ARP**. This is a genuine independent real-world cross-check (unlike Finding 6): it confirms the projection *type and rough parameters* are plausible (Transverse Mercator centered near 39°E fits the region; a wildly wrong projection would produce errors of tens to hundreds of km, as seen in a deliberately-wrong axis-order variant tested — 327 km error), but the ~1.6 km residual means these exact parameters/point should not be trusted as sub-km-accurate without independent confirmation against the live DCS install. Plausible explanations for the residual (inferred, unconfirmed): (a) DCS's in-game "Damascus" airbase reference point (e.g. a specific taxiway/tower position placed by terrain artists) is not the same physical point as the officially published ARP; (b) pydcs's fitted parameters carry some residual fitting error from `compute_tmerc_parameters()`'s search; (c) satellite-imagery-based terrain placement in DCS is not surveyed to ARP precision.
8. **No obviously-named projection table found in Syria terrain filenames** — **evidence:** inferred (filename listing only, not file contents) — **source:** `world-model/data/raw/dcs/2026-09-02/DCS-files.txt`, grep of `Mods/terrains/Syria/`. Lua files present directly under the terrain root: `beacons.lua`, `entry.lua`, `notInstances.lua`, `radio.lua`, `shadingOptions.lua`; elsewhere: `map/towns.lua`, `MissionGenerator/nodes.lua`, `MissionGenerator/nodesMap.lua`, `misc/metacache/base.lua`, `extra/lightmap/lightmap.lua`. None of these filenames suggest an obvious "projection.lua" or "coordinates.lua". `entry.lua` is the standard DCS terrain entry-point config and the most likely place ED would declare projection/origin parameters directly, if they do so in Lua at all — **this has not been checked, because DCS-files.txt has no file contents.**
9. **Prior-art license note** — **evidence:** documented — **source:** pydcs GitHub repo license badge — LGPL-3.0. Reusing pydcs's per-theatre projection parameter tables (not necessarily its code) as a documented starting point is very likely fine; reusing/linking its code directly carries LGPL-3.0 copyleft obligations. Flag for Architect to decide reuse-vs-reimplement.
10. **Other prior art checked, not independently reverse-engineering projection** — **evidence:** forum-claim-unverified (surface-level search only, not code-read) — **source:** WebSearch results for DCS-gRPC, DCS Olympus. No evidence found that these reimplement per-theatre projection math; the typical pattern in the wider community (inferred from search snippets, not confirmed by reading source) is to call `coord.LOtoLL`/`LLtoLO` live in-game via an export/gRPC bridge rather than reimplementing the projection offline — consistent with Finding 5's environment constraint. Not read in detail; treat as a lead, not a finding.

### Reproducible Test

Local Python probe (not requiring DCS or the live install), run in a venv with `pyproj` installed:

```python
from pyproj import CRS, Transformer

central_meridian = 39
false_easting = 282801.00000003993
false_northing = -3879865.9999999935
scale_factor = 0.9996

proj4 = (
    f"+proj=tmerc +lat_0=0 +lon_0={central_meridian} +k_0={scale_factor} "
    f"+x_0={false_easting} +y_0={false_northing} +units=m +ellps=WGS84 "
    f"+axis=neu +no_defs"
)
crs_local = CRS.from_proj4(proj4)
to_ll = Transformer.from_crs(crs_local, CRS.from_epsg(4326))

px, py = -178652.320313, 52081.296875  # pydcs "Damascus" airbase point
lat, lon = to_ll.transform(px, py)
# -> 33.42551, 36.51851
# published OSDI ARP: 33.41139, 36.51556 -> ~1594 m error
```

Confirmed the axis convention (`+axis=neu`, i.e. input `(x, y)` = (northing, easting) = DCS-native `(x, z)`) by testing swapped/unswapped variants: the correct convention above gives 1.6 km error; a naive `(easting, northing)` PROJ default order gives 327 km error, ruling out that alternative decisively.

This test used only publicly available parameter/point values (pydcs source) and a public real-world ARP value — **it did not touch the live DCS installation**, so it cannot yet confirm these parameters are correct for the actual installed Syria terrain, only that they are internally plausible and roughly consistent with reality.

### Possible Approaches

- **Preferred for M1**: treat pydcs's Syria `tmerc` parameters as a strong starting hypothesis (Findings 1–2), then confirm/refine against the live install using the prepared `coord_probe.lua` mission probe (Findings 5–6) — this closes the "not yet verified against the installed copy" gap and gives us DCS-native ground truth for the origin and every Syria airbase in one run, at zero incremental parameter-fitting cost since pydcs's method is directly reusable in concept (not necessarily in code, for license reasons).
- **Validation control points**: use `coord_probe.lua` output for Damascus (and 2–3 other well-documented Syria-area airports — Beirut-Rafic Hariri, Latakia Bassel Al-Assad, Incirlik — all have precisely published ARPs) as DCS-native x/z, cross-checked against independently-published real-world lat/lon (aviation ARP data, not Wikipedia-only — cross-reference against an AIP/SkyVector-class source per point) exactly as `docs/concept/WORLD_MODEL_BUILDER.md`'s Validation section describes.
- **If `entry.lua` does state projection parameters directly** (per the `probe_syria_terrain_lua.sh` script below), prefer that as the primary source over pydcs's empirically-fitted values — it would be closer to "documented" than "forum-claim/community-tool-derived."
- **Fallback if `coord.LOtoLL` cannot be exercised** (e.g. `io`/`lfs` sandboxed out per the caveat in `coord_probe.lua`, and the user doesn't want to touch `MissionScripting.lua`): fall back entirely to pydcs's already-fitted parameters plus the Damascus-only cross-check already done here, explicitly documented as "not independently confirmed against the live install, ~1.6 km known residual on one point" — sufficient for early pipeline development, insufficient for a final accuracy claim.
- **Do not** use `coord.LOtoLL` output as your only "ground truth" airbase lat/lon set for validation (Finding 6) — always pair at least one point with an externally-sourced real-world value.
