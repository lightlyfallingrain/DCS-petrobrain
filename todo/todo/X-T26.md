# X-T26 — Make behaviour-affecting constants configurable

- [ ] **X-T26 — Gather the constants that affect *behaviour* into declared constants where they are
  still literals, then expose them through per-subproject configuration files with short
  descriptions, so the pilot can fiddle with parameters without editing code.** #status/open User
  priority task, 2026-10-14. Sequenced **after** the `BL-14` merge, and before the `BL-B64` 9K113
  Architect pass.

  ## The ask, and the scope decision attached to it

  His request was *"go through the code files and find all magic constants. Make them into declared
  constants … then gather the declared constants and make them configurable via configuration files
  … Add proper but short description of what each constant does in the default configuration
  files."*

  Offered a narrowing — that what he actually wants is the **behaviour-affecting** ones rather than
  every literal in the tree — his answer was **yes**. So:

  **In scope**: constants whose value changes what Petrovich *does* or *says*. Detection and
  recognition tiers, cohesion bounds, decay half-lives, speech rate and the inter-utterance gap, the
  attack-run gates and cadence threshold, the scan loop's dwell and plan, the association gate's
  terms, the plausible-speed table, the bias fraction.

  **Out of scope**: arithmetic literals that are part of a mechanism rather than a tuning choice — a
  `2` in a halving, a `0.5` in a midpoint, buffer sizes, array indices. Exposing those adds ways to
  break the code and no way to improve behaviour.

  ## Why the narrowing matters rather than being tidiness

  This repo already keeps behaviour constants in named places **with their provenance attached** —
  `SYSTEMATIC_BIAS_FRACTION`'s "keeps a heavily-observed contact converging on a wrong,
  confidently-held position", `SPEECH_RATE_WPS`'s *"Uncalibrated — needs a live sortie"*,
  `BEARING_SIGMA_DEG`'s "models the crewman's own pointing precision, not anything DCS reports", the
  three attack-run gates as declared agreed guesses. A mechanical sweep would flatten that reasoning
  into a config key and lose the part that tells the next reader whether a number is a measurement
  or a guess.

  A config layer is also the natural home for this project's own **"mechanism and calibration never
  share a commit"** rule (`perception/optics.py`'s provenance comments say so explicitly) — which is
  an argument *for* doing this, not against it.

  ## What the Architect pass has to settle before anything is implemented

  1. **The inclusion test.** What makes a constant tunable, stated so two people would classify the
     same constant the same way. "Affects behaviour" is not yet that test.
  2. **Where the files live and how they compose.** One per subproject, or one shared? Defaults in
     the file or in code with the file as an override? What happens when a key is **absent**, and
     what happens when it is **nonsense** — fail closed, fall back with a warning, or refuse to
     start. The last is a real decision: a silently-ignored bad value would be worse than the status
     quo, because the pilot would be tuning something that is not being read.
  3. **Where the provenance goes.** The comments quoted above are load-bearing. They cannot simply
     move into a one-line config description, and duplicating them in both places guarantees drift.
  4. **Load timing.** Mid-sortie reload or startup only. Startup is almost certainly right, but it
     should be a decision rather than an accident.
  5. **Which subprojects.** body-layer has the bulk; audio-adapter, aircraft-layer and world-model
     each have some. Whether this lands subproject-by-subproject or all at once decides how reviewable
     it is.

  ## Flow

  Architect → Implementer (likely staged per subproject) → Reviewer → Performance + Security once →
  DoD → merge, per his own *"review, DoD and then merge"*.

  Related: the three deliberately-unset `BL-14` constants are the clearest instance of why he wants
  this — `plans/attack-run/plan.md`'s lined-up band, elevation gate and change threshold are all
  values a sortie is supposed to set, and today setting one means editing `attack_run.py`.
  `[[AA-B5]]` would move the inter-utterance gap into the audio path, which overlaps this item's
  surface — check which lands first.
