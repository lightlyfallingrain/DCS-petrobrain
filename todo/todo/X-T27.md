  ## The judgement call on reported bugs — a refinement of the 2026-10-05 rule, not a reversal

  His first priority carries its own qualifier: *"some warrant explore, some immediate action, some
  later action. Needs judment calls."*

  This **modifies** the standing capture-then-explore direction
  (`docs/acceptance/2026-10-05-sortie-feedback.md`, enforced by three hooks and quoted in root
  `CLAUDE.md`): *"write down the provided feedback so that it is not lost. Then use the explore
  skill to investigate with user what the behaviour should be."*

  What stands and what changes:

  - **Capture still happens every time.** The 2026-10-05 reasoning was that the loss is silent and
    the words are the specification; nothing in this direction touches that, and the hooks stay.
  - **Explore is now explicitly conditional.** It was already written as *"not a mandatory
    ceremony"* for unambiguous small items, but the default read was explore-unless-trivial. The
    user is asking for a real triage: some bugs are acted on immediately, some wait, some need the
    conversation.
  - **The judgement is the orchestrator's to make and to state.** A bug whose *behaviour* is
    obvious (a crash, a wrong word, a repeated line) is immediate action. A bug whose **correct
    behaviour is the open question** — what should he say, when should he go quiet, which instrument
    should he use — is exactly the class where this project's history says the first reading is
    wrong (the Bekaa reversal, the water-flow analogue, *"still one clock hour at a time"*, the
    per-kind direction word). Those still get explored. Say which call was made and why, in one
    line, rather than silently choosing.
