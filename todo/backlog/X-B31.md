# X-B31 — Build the occluder layer: buildings from DCS, trees from OSM

- [ ] **X-B31 — Build the occluder layer: buildings from DCS, trees from OSM.** #status/open Falls out of [[X-B4]],
  2026-09-29, and is build work with the research already done rather than a question.

  Today `query/line_of_sight.py` samples bare terrain and nothing else, so Petrovich sees through
  towns and forests. Three sources are now in hand and each has a measured cost:

  | occluder | source | cost |
  |---|---|---|
  | terrain | today's elevation grid, or `land.profile` (one call vs 20+ `getHeight`) | 0.9 us/point |
  | buildings | `world.searchObjects` + `VolumeType.SEGMENT`, true 3D, no size table | 8.7 us/sightline |
  | trees | OSM `landcover` polygons — world-model already holds 44,811 | already local |

  **The architectural question this raises, and it is not small:** buildings are only reachable
  from the *Windows* box through the mission-scripting bridge, while `line_of_sight_clear` runs
  in-process on the Mac inside body-layer's 5 Hz perception loop. A per-candidate LOS check would
  have to cross the LAN. That collides with [[X-B27]]'s topology decision and with
  `plans/pb1-perception-logger/plan.md` decision 3 ("same box always"). **Resolve the topology
  before designing the call**, not after — the measured 8.7 us is a loopback figure and says
  nothing about a LAN round trip per candidate per poll.

  Cheapest first slice, if one is wanted before the topology moves: **trees only**, entirely
  Mac-side, since the OSM polygons are already in the store and need no bridge at all. That would
  close the forest half of the missed-AAA class of defect without touching the seam.

  **Do not start before [[X-B26]]'s SRTM-resolution question is settled** — both change
  `line_of_sight_clear`, and doing them in either order separately means touching it twice.

  **The "trees from OSM" row is settled rather than assumed, as of 2026-10-01** (merge `306ae05`).
  It was the fallback pending an answer; it is now the measured answer. **No DCS call gives
  tree-aware line of sight** — `isVisible`, `getIP`, `searchObjects` at any volume and
  `getSurfaceType` are all terrain/scenery only, tested against vehicles the pilot placed inside
  canopy. The engine has the capability but it is compiled and Petrovich's own verdict is an audio
  file. DCS's per-tree placement does exist on disk, and is deferred behind the `.surface5`
  payload-addressing wall ([[X-B32]]). Full reasoning:
  `aircraft-layer/research/2026-09-29-tree-los-probe-results.md`.

  **The trees-only slice is being taken, 2026-10-13 — and this item's framing for it is
  superseded. See `plans/forest-occlusion/plan.md`.** User direction
  (`docs/acceptance/2026-10-13-tree-cover-direction.md`): *"anything in forest is not seen"*, flat
  and binary, treeline deferred to a later `/explore`.

  **Why the framing changed.** This item puts forest polygons in `query/line_of_sight.py`, as
  occluders along the sightline. `BL-11` Stage 4 (`plans/bl11-stage4-fail-closed/plan.md`) has
  since removed that primitive from the live path — *"any future work on that primitive … is now
  purely an offline/fixture-correctness concern with no runtime consequence"* — so an occluder
  added there would change the offline oracle and `WM-B7` and **nothing Petrovich does in the
  air**. Trees are built instead as a separate Mac-side gate on the *target's own position*
  (gate 5 in `perception.check_visibility`), which needs no world-model change at all.

  **This item's sightline-occluder shape is not wrong** — it stays the right shape for the offline
  oracle, and for the chord-length treeline model the capture names as most promising. It is just
  not the live path any more.

  **So what remains of X-B31 is the buildings half**, which is also where its real architectural
  question lives (the LAN bridge, [[X-B27]]'s topology). Separating them means the topology decision
  no longer gates trees at all.

  **Measured while planning the slice** (real `syria-full` store, read-only): 9,710 of the 44,811
  landcover polygons are `forest`; `containing_polygons(conn, ["landcover"], x, z)` costs **0.075 ms
  median / 0.271 ms p95** per point (vs `describe_position`'s 84.6 ms); **1–3% of ground positions
  sit inside forest** (2.8% Latakia, 0.0% Palmyra), and **42–96% of positions have no mapped
  landcover at all** — which is why `None` must be read as *not forest*.

  **The trees-only slice is DoD-PASSED 2026-10-13 on `feature/forest-occlusion` (tip
  `ba6bd394`), merge pending user approval, `#needs-flight`.** Stages 1–2 only (mechanism + wiring,
  flag off by default); Stage 3 (flip the live default on) and Stage 4 (in-loop cost measurement)
  are deliberately not built — the user decides Stage 3 after flying the A/B. Reviewer (APPROVED,
  full read, both the Stages 1-2 pass and the security-fix round), Performance (APPROVED —
  MONITOR) and Security (one required fix — non-finite `x`/`z` reaching `math.floor` unguarded —
  closed and re-reviewed clean) all signed off. Full report: `plans/forest-occlusion/dod-check.md`.
  Acceptance card (branch, setup, the A/B, what to watch for, honest limits):
  https://claude.ai/artifact/T7dPmNq3h91hXNeZRvCRyS.

  **Fixture-only — no sortie has exercised this path.** Measured blast radius is small by
  construction (1–3% of ground positions theatre-wide, 0% of 300 points right at Latakia itself;
  the coastal belt north-east of Latakia is the theatre's densest at 3.2% areal), so an ordinary
  sortie elsewhere will rarely or never fire the gate — units have to be deliberately parked in
  and at the edge of that belt to generate any evidence at all, including for the treeline
  `/explore` this slice is meant to unblock. This leaves **only the buildings half of X-B31 still
  open**, which is where the item's real architectural question lives (the LAN bridge, [[X-B27]]'s
  topology).
