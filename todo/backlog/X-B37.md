# X-B37 — The tuning TOML generator renders only a first sentence, and renders markdown into it

- [ ] **`generate_defaults.py` extracts a *first sentence* from markdown-flavoured `#:` prose, which
  both truncates what the pilot sees and leaks unbalanced markup into the file he reads.**
  #status/open Filed 2026-10-15 from the `X-T26` review and fix passes
  (`plans/configurable-constants/review.md`).

  Two defects with one cause — the generator treats prose written for a code reader as if it were
  written for a config file.

  **1. Markup artifacts.** Three attack-run gate descriptions carry a stray backtick and one decay
  description a stray leading `*`, because a first sentence cut out of markdown prose can open a span
  it never closes. Cosmetic, but `config/defaults.toml` is the pilot-facing file, so it is the one
  place the project's generated text is read by someone who did not write it. The fix is to strip or
  balance inline markup during extraction — deliberately **not** to edit the authoritative `#:`
  provenance comments, which are correct as code comments and must stay that way.

  **2. First-sentence-only truncation is a real information loss, not a style choice.** It was a
  documented Stage 1 design decision (`plans/configurable-constants/plan.md`), and it bit
  immediately: the `X-T26` security pass asked for the inverse threshold/range relationship to be
  spelled out for the three visibility tier radii — a smaller threshold means a *longer* detection
  range, which is easy to get backwards and is how a config file could silently rebuild the
  hawk-eyed Petrovich this project exists to replace. The implementer added exactly that sentence,
  and **none of it rendered**, because it was the second sentence of each block. The merge worked
  around it by folding the information into the first sentence of those three keys, which is fine for
  three keys and does not scale to Stage 3's ~80.

  **So the question this item has to settle is a rendering contract**, not a bug fix: how much of a
  `#:` block reaches the TOML. Candidates — the whole block; the first *paragraph*; an explicit
  `#:` marker separating "pilot-facing" from "provenance"; or a short `description =` kwarg on
  `tuning.real(...)` beside `lo`/`hi`, keeping pilot text and code provenance deliberately separate.
  The last is the most honest about the two audiences but costs a signature change on every key.

  **Worth doing before Stage 3**, not after: Stage 3 exposes ~80 more keys, and whatever contract is
  chosen has to be applied to all of them at once. Doing it afterwards means rewriting 95 blocks
  instead of 15.

  **3. A third defect, in a different function, added 2026-10-15 after this item was filed.**
  `_join_comment_lines()`'s backtick-parity join silently **eats the space** when a `#:` line is
  wrapped inside a backtick-quoted span: `` `range = size_m / threshold` `` broken across two
  physical lines rendered as `size_m /threshold`. The join is correct for the case it was written
  for — a dotted name wrapped mid-identifier, where no space belongs — and wrong for any other
  wrapped span.

  **It is a distinct mechanism from 1 and 2, and worth keeping distinct**: those are about
  `_first_sentence()` deciding *how much* of a block is rendered, this is about
  `_join_comment_lines()` corrupting *what* is rendered, and it can hit any wrapped backtick span
  whether truncated or not. Found during `X-T26` fix pass 3 and worked around by keeping each
  formula on one physical line — a workaround in three comment blocks, not a fix, and nothing stops
  the next author wrapping in the wrong place.

  **How it was found is the part worth keeping**: by regenerating `defaults.toml` and reading the
  rendered output, not by reading the source diff. Two reviews had read the source and missed it.
