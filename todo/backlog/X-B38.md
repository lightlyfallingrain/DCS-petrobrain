# X-B38 — Two accepted-but-untested edge cases in `tuning.py`

- [ ] **`body-layer/src/tuning.py` carries two edge cases that were examined, judged safe, and
  deliberately left untested. Both were disclosed candidly rather than discovered later — this item
  exists so they do not become the next silent regression.** #status/open Filed 2026-10-15 from
  `X-T26`'s review passes (`plans/configurable-constants/review.md`).

  An untested-but-accepted edge case is this project's own recurring regression shape, which is the
  only reason these are filed at all rather than left as comments.

  **1. A duplicated bound literal with nothing asserting it stays in sync.**
  `LOWRES_ANGULAR_RADIUS_RAD` and `MEDRES_ANGULAR_RADIUS_RAD`'s `lo` bounds are written as the
  literal `0.00128` — the value of `RESOLUTION_ANGULAR_RADIUS_RAD`, the optical-resolution floor that
  `perception/clustering.py`'s docstring states and relies on as part of a correctness proof.

  **The literal is not laziness and the two reasons were both verified.** A name reference raises
  `NameError`, because the two bounds bind at `visibility.py:312`/`327` and
  `RESOLUTION_ANGULAR_RADIUS_RAD` is assigned at line 405; and independently
  `generate_defaults.py`'s AST reader has no `ast.Name` branch, so it would raise
  `ValueError: unsupported literal node`. A module reorder fixes only the first half. Both failure
  modes are loud, which is why this merged.

  **The residual risk is the quiet one:** change `RESOLUTION_ANGULAR_RADIUS_RAD` and the two copies
  silently stop matching the floor they exist to enforce, with nothing failing. The reviewer's
  suggested guard is a test using `generate_defaults.collect_declarations()` to assert
  `lo == RESOLUTION_ANGULAR_RADIUS_RAD` dynamically — cheap, and it closes exactly what the literal
  opened.

  **2. Double-fault misclassification in the cross-key coupling check.**
  `_check_scan_decay_coupling` reads each coupled key's raw override **without re-validating that
  key's own bounds first**. So when one key is independently out of range *and* large enough to make
  the pre-check flag a second, genuinely in-bounds key, that second key is reported as
  `"invariant violation"` rather than left applied.

  Safe either way — it falls back to its own code default — but **the reason text is the only place
  the distinction exists**, so being wrong there misdirects the pilot about which of his edits caused
  the rejection. The reviewer judged it mergeable because both rejection lines appear together in the
  startup block and the detail text names the exact value used, so it is self-diagnosable. A test
  pinning the precedence would make it stay that way.

  Both are small. Neither is urgent. Together they are one short pass over `tests/test_tuning.py`.
