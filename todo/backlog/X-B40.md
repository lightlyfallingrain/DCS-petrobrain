# X-B40 — Petrobrain launcher: a text UI for starting, stopping and watching the services

- [~] **X-B40 — A cross-platform (Windows and Mac) text-based launcher that starts and stops the
  Petrobrain services, toggles their command-line options, shows their recent log lines, and reads
  its per-machine setup from `petrobrain.env`.** #status/in-progress Filed 2026-11-17 at user
  direction. In progress on `feature/launcher` (worktree `../DCS-petrobrain-launcher`).
  Cross-cutting: it launches services from several subprojects, so it belongs to no single roadmap.

  ## The user's spec, verbatim

  > *"Let's have a (text based) GUI for launcing the different services."*

  ```
  ==================================================
              Petrobrain v0.x.x
  ==================================================

   * settings
     | - <here list of settings from petrobrain.env>

   1 - aircraft layer             ON/OFF
       |-> options
       |-> log

   2 - audio capture              ON/OFF
       |-> options
         | [x] '--argument1'    - short description
         | [ ] '--argument2'    - short description
       |-> log
         | <here show 10 last lines of service log>

   3 - chart viewer ON/OFF
       |-> options
       |-> log
  ```

  > *"key arrow up/down moves in the launcher.*
  > *Space toggles arguments on/off.*
  > *Space or enter expand/collapse options, logs, settings.*
  > *By default, all expandables are collapsed.*
  > *Key press of number key, toggles corresponding service on/off. Enter on service line toggles
  > service on/off.*
  > *When service on, show green "ON". When off, show red "OFF".*
  > *petrobrain.env will have (optional) line DEFAULT_SERVICE=service1_name,service2_name,... those
  > will be started automatically when launcher starts.*
  > *Ctrl-C stops all services and exits launcer.*
  >
  > *Launcher will run on both windows and mac. petrobrain.env will then give the necessary settings
  > for each setup."*

  ## What already exists (checked 2026-11-17)

  - `run-scripts/` holds today's launch path: one `run-<service>.sh` per service, plus
    `start-mac`/`start-win` and `stop-mac`/`stop-win`, which track processes with pidfiles under
    `/tmp/petrobrain-<service>.pid`. **The individual `run-*.sh` scripts are what the user actually
    uses; the start/stop scripts do not work as intended** — user, 2026-11-17: *"The idea is there,
    implementation not so much. The individual run-* scripts are what I currently use."* So the
    `run-*.sh` command lines are the working reference for how each service is started; the
    start/stop scripts are the idea this item replaces, not code to build on.
  - `run-scripts/petrobrain.env` is per-machine and gitignored, written as shell `export KEY=value`
    lines (paths, the LAN IPs of the Mac and the Windows box, piper/sox locations). Every
    `run-*.sh` sources it. `DEFAULT_SERVICE=` would be a new key; a launcher on Windows has to read
    the same `export` form, or the format changes for both.
  - The machine split is in memory `project_compute_topology`: the Mac runs Ollama/brain, Windows
    runs DCS/aircraft-layer. So each machine's `DEFAULT_SERVICE` lists a different subset.

  ## Settled, user 2026-11-17

  - **Piper is one of the services.** *"note: piper is also a service we need to run"*
    (`run-scripts/run-piper-mac.sh`, `run-piper-windows.sh`).

  - **Options come from each service's own `--help`**, flags and one-line descriptions both, so the
    list cannot go stale. *"options list from --help"*
  - **The log view is the service's stdout/stderr**, captured by the launcher. *"log from services
    std out/err. User can go and look at log files if necessary."* The services' own log files are
    not read by the launcher.
  - **Shells: WSL bash on Windows, Terminal (zsh or bash) on the Mac.** *"Assume environment is WSL
    bash and mac terminal (zsh or bash)."* Both are POSIX terminals, so Python's stdlib `curses` is
    available on both and a text-UI dependency may not be needed at all. That is a candidate, not a
    finding.

  ## Settled, user 2026-11-19

  > *"This does not need to be fancy or very robust at this stage. I just want an easy way to start
  > and stop everything and see if there's a problem somewhere."*

  - **Value flags take their value from `petrobrain.env`; the launcher only toggles them on/off.**
    *"for values, read them from .env file. The launcher then just toggles argument on/off."*
  - **Options toggle only while the service is OFF**, so a change takes effect at the next start.
    *"option toggling only when service off, so they effect on start."*
  - **No terminal-drawing options.** *"terminal draw debug option not available in launcher. I'll
    start manually if I need them."* `--eyesight-view`, `--pov-view` and their radius are hidden;
    `run-body-layer-debug-view.sh` stays a manual script.
  - **No stdin.** body-layer's typed-command REPL is not used: *"If I need it, I'll start body layer
    manually."* Services get stdin closed.
  - **List every service available on this machine; autostart only those in `DEFAULT_SERVICES`.**
    *"List all services available. Start only those listed in DEFAULT_SERVICES."* (The 2026-11-17
    spec said `DEFAULT_SERVICE`; the launcher reads `DEFAULT_SERVICES` and accepts the singular
    too.)
  - **Stays filed here**, not under its own roadmap. Code in its own `launcher/` directory.
  - **Deferred:** *"ON/OFF could show "connected" when connection to that service is established
    (on another computer). Defer, not needed initially."* — a service running on the other machine
    shown as reachable. Not in this plan.

  ## Plan (light path — a helper tool, no change to what Petrovich does)

  **Shape: the launcher is a process manager over the existing `run-*.sh` scripts**, not a second
  copy of their command lines. They are what works today (2026-11-17 note above); the launcher adds
  process control, the option list and the log pane.

  ```
  launcher ──spawn (own process group, cwd run-scripts/, stdin closed)──▶ run-<svc>.sh <toggled flags>
      ▲                                                                       │
      └──────────────── stdout+stderr pipe, last N lines kept ◀───────────────┘
  Ctrl-C / stop: SIGINT to the group → 5 s → SIGTERM → 2 s → SIGKILL
  ```

  **Service table** (in code; platform = Darwin vs WSL via `/proc/version`):

  | service | Mac | WSL |
  |---|---|---|
  | `aircraft-layer` | — | `run-aircraft-layer.sh` |
  | `audio-capture` | — | `run-audio-capture.sh` |
  | `audio-adapter` | `run-audio-adapter.sh` | `run-audio-adapter-windows.sh` |
  | `piper` | `run-piper-mac.sh` | `run-piper-windows.sh` |
  | `brain` | `run-brain.sh` | `run-brain.sh` |
  | `body-layer` | `run-body-layer.sh` | `run-body-layer.sh` |
  | `chart-viewer` | — | `run-chart-viewer.sh` (new) |

  The names are what `DEFAULT_SERVICES` lists. Each row also carries a small hide-set
  (`--help`, the terminal-drawing flags, one-shot flags such as `--print-tuning`/`--print-rules`).

  **Options.** Read lazily on first expand from `run-<svc>.sh --help` (argparse exits after
  printing, whatever else is on the line), cached for the session, 20 s timeout. Each `--flag`
  line becomes one option with the first line of its help text:
  - **on/off flag** → toggleable.
  - **value flag** → toggleable only if `petrobrain.env` has `OPT_<SERVICE>_<FLAG>=value`
    (upper-cased, `-` → `_`; e.g. `OPT_BODY_LAYER_EYESIGHT_VIEW_RADIUS_M`); otherwise shown greyed
    with "no value in petrobrain.env". Toggled on, it is passed as `--flag value`.
  - **flag already on the script's own command line** (found by text search of the script) →
    shown greyed as `[=]` "set in run script". Toggles reset each launch; no persistence.

  **Settings pane**: `petrobrain.env`'s `export KEY=value` lines, parsed (no shell expansion),
  shown read-only.

  **Log pane**: last 10 lines of combined stdout/stderr, ANSI codes stripped. On exit the launcher
  appends `[launcher] exited, code N` and the line turns red OFF — that is the "see if there's a
  problem" signal. Version line: `git describe --always --dirty` and the branch, since no project
  version exists and the branch is what the user wants to see.

  **Windows processes via WSL interop** (`python.exe`): the launcher sets `PYTHONUNBUFFERED=1` and
  appends it to `WSLENV` so their output reaches the pane line by line. **Unverified:** whether
  killing the WSL-side process group also ends the Windows `python.exe`. Checked in the acceptance
  run (Task Manager after Ctrl-C); if it survives, fall back to `taskkill.exe /T /F` on the
  service's Windows PID. Not built speculatively.

  **Steps** (one branch, `feature/launcher`):

  1. `launcher/` — `pyproject.toml` (stdlib only at runtime; ruff/mypy/pytest dev deps like every
     other subproject), `CLAUDE.md` with a Commands section, `src/launcher/`: `envfile.py` (parse),
     `helpparse.py` (argparse `--help` → options), `services.py` (table, command build),
     `procs.py` (spawn, pipe reader, stop), `ui.py` (curses: tree, keys, colours), `__main__.py`.
     Tests for the three pure modules; the curses layer is checked by running it.
  2. `run-scripts/`: add `"$@"` to `run-aircraft-layer.sh`, `run-audio-capture.sh`,
     `run-piper-mac.sh`, `run-piper-windows.sh`; new `run-chart-viewer.sh` (README's command,
     `--dcs-install "$(wslpath -w "$DCS_INSTALL_PATH")"`); new `launcher.sh` to start it; delete
     `start-mac`, `start-win`, `stop-mac`, `stop-win` (the idea this replaces).
  3. Keys per the 2026-11-17 spec: ↑/↓ move, Space toggles option / expands, Enter toggles
     service or expands, digit toggles service N, Ctrl-C stops all and exits. Green ON / red OFF.
  4. Checks for `launcher/`, merge on the user's word (testing-aid path, root `CLAUDE.md`
     "Workflow"), then an acceptance card naming `main`, one section per machine: autostart
     from `DEFAULT_SERVICES`, toggle an option and start, stop with a digit, kill one service from
     outside and see red OFF with its last lines, Ctrl-C and check Task Manager for leftover
     `python.exe`.

  **Out of scope here:** the deferred "connected" state; value editing in the UI; persisting
  toggles; running debug-view or REPL under the launcher.
