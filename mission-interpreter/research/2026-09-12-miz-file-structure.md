# .miz File Structure and Lua Parsing Approach

**Date:** 2026-09-12
**DCS version:** not verified locally — no DCS install/`.miz` sample reachable this session (Mac dev machine, `DCS_INSTALL_PATH`/`DCS_SAVED_GAMES_PATH` unset)
**Theatre:** n/a (format investigation, theatre-independent)

### Question
Resolve the internal structure of a `.miz` mission file for Mission Interpreter's planning: top-level zip contents, where briefing/task text and kneeboard images actually live, rough shape of the `mission` table's key subsections (groups/units, route waypoints, triggers/late-activation, weather, date, theatre), whether the Lua is standalone-parseable, and what prior-art parsers exist and how they parse it.

### Findings

- A `.miz` is a plain zip archive. Confirmed top-level members beyond `mission`: `options`, `warehouses`, `l10n/DEFAULT/dictionary`, plus `mapResource` and (when the mission author added them) a `KNEEBOARD/` tree and other loose resource files (scripts, sounds, images). — **evidence:** documented (multiple independent sources agree) — **source:** [Hoggit "Miz mission structure"](https://wiki.hoggitworld.com/view/Miz_mission_structure), pydcs `dcs/mission.py` (`loaddict('mission', ...)`, `loaddict('options', ...)`, `loaddict('warehouses', ...)`, `loaddict('l10n/DEFAULT/dictionary', ...)`), openflightschool.de mission-file doc.
- Briefing/task text is **externalized to `l10n/DEFAULT/dictionary`**, not inline in `mission`. Fields like `descriptionText` (situation), `descriptionBlueTask`, `descriptionRedTask`, `descriptionNeutralsTask`, and `sortie` in the `mission` table hold **`DictKey_...` string IDs**, not literal text; the actual strings live as `["DictKey_descriptionText_1"] = "..."` etc. in the dictionary file. This confirms the question's hypothesis exactly. — **evidence:** documented — **source:** ED forum thread ["Mission - Dictionary file not updated"](https://forum.dcs.world/topic/253142-mission-dictionary-file-not-updated/) (quotes actual DictKey examples), pydcs `dcs/mission.py` (`self._description_text = self.translation.get_string(imp_mission["descriptionText"])`, `Translation.set_string(sid, translation_dict[sid], 'DEFAULT')` sourced from `dictionary_dict["dictionary"]`).
- Kneeboard images are **embedded as real files** inside the zip archive, not just referenced by external path — under a mission-specific `KNEEBOARD/<AIRCRAFT_NAME>/IMAGES/` (or `Multiplayer/KNEEBOARD/IMAGES/` for MP-shared pages) tree, packaged in by the mission author via the Mission Editor's kneeboard folder. `mapResource` is the table that maps resource keys used elsewhere in `mission` (e.g. any in-mission asset reference) to these packaged file paths. — **evidence:** forum-claim-unverified (consistent across several community how-to pages, none of them ED-authoritative) — **source:** flyawaysimulation.com and steamcommunity.com kneeboard guides, openflightschool.de mission-file doc (mentions `mapResource` as "manages all additional mission resource files").
- `mission` table subsections relevant to Mission Interpreter, confirmed via pydcs's own reader code (which round-trips real DCS-authored `.miz` files, so its key names are a strong proxy for the true schema even though pydcs is unofficial):
  - **Group** (base, `dcs/unitgroup.py`): reads `hidden`, `hiddenOnPlanner`, `hiddenOnMFD`, `password`; writes `name`, `groupId`, `x`/`y`, `units` (dict), `route.points`. **`hidden`/`hiddenOnPlanner`/`hiddenOnMFD` are real, structurally-identifiable "mission-author-only" flags** — directly relevant to Mission Interpreter's stated job of filtering out author-only knowledge.
  - **MovingGroup** (adds to Group): `frequency`, `task`, `probability`, `tasks` (trigger-action list), `taskSelected`, **`lateActivation`** (bool), `start_time`. `lateActivation` is the mechanism behind "hidden ambush" groups — a group that doesn't exist in the world until a trigger spawns/activates it is structurally flagged this way, not merely inferred from absence.
  - **MovingPoint** (a `route.points[]` waypoint entry): `type` (e.g. `"Turning Point"`, `"Land"`, `"TakeOffGround"`), `action` (PointAction enum), `speed`, `alt`/`alt_type`, `ETA_locked`, `name`. (x/y position fields presumably present too but not directly quoted from the fetched excerpt — see Unresolved.)
  - **Theatre**: `mission["theatre"]`, a plain string.
  - **Date**: `mission["date"]` = `{Year, Month, Day}` (pydcs defaults to `{2011,6,1}` if absent, implying the key is optional/mission-editor-populated).
  - **Weather**: `mission["weather"]`, read as a sub-dict; Hoggit's page separately describes it containing wind-at-altitude, fog, clouds, visibility, temperature (Hoggit's wording, not independently cross-checked against pydcs code this session).
  - **Triggers**: two separate structures both present — `mission["triggers"]` (loaded by `Triggers.load_from_dict`, described by Hoggit as zone definitions: radius, coordinates, properties, vertices — these are **trigger zones**, i.e. `triggers.zones[]`) and `mission["trigrules"]` (loaded by `Rules.load_from_dict` into pydcs's `TriggerRule`/condition/action structures — these are the **trigger logic**, i.e. condition → action rules, which is where scripted spawns/ambushes are actually wired up). This is a real distinction the question's phrasing ("triggers, trig") slightly blurs — the zone geometry and the rule logic are two separate top-level keys.
  - — **evidence:** reproduced-locally-equivalent (pydcs source code read directly, not merely a forum description of it; pydcs is a widely-used, actively-maintained round-trip mission editor, so its field names are functionally validated against real ED mission files even without a live install here) — **source:** `dcs/unitgroup.py`, `dcs/mission.py` in [pydcs/dcs](https://github.com/pydcs/dcs) (master branch, fetched 2026-09-12).
- **Lua parsing approach across prior art:** pydcs does **not** use an embedded Lua interpreter (no `lupa`) or a generic Lua-table-to-Python library like `slpp`. It ships its own hand-written recursive-descent parser at `dcs/lua/parse.py` (plus `dcs/lua/serialize.py` for the reverse direction), with its own tokenizer-free character-by-character `Parser` class (`parse()`, `object()`, `string()`, `number()` methods). It handles: `[key]=` explicit-key table entries, nested tables, `true`/`false`/`nil`, scientific-notation numbers, `--` and `--[[...]]` comments. It does **not** appear to handle trailing commas before `}` robustly, and does not support Lua's long/multi-line bracketed strings (`[[...]]` string literals, as opposed to `--[[ ]]` comments) — only backslash-escaped strings. No explicit `mission = ` prefix-stripping logic was found in the fetched excerpt; `lua.loads()` is called directly on the raw file bytes and evidently handles the leading `<name> = ` assignment itself. — **evidence:** reproduced-locally-equivalent (source read directly) — **source:** `dcs/lua/parse.py`, `dcs/mission.py` in pydcs/dcs.
- A second, independent open-source parser exists: [`Ked57/dcs-mission-parser`](https://github.com/Ked57/dcs-mission-parser) ("A lib to extract, parse, modify and save .miz files... parse Lua content to JSON and back") — not read in depth this session, but its mere existence is a second data point that hand-rolled Lua-table parsing (not a full Lua VM) is the community-standard approach for this format. — **evidence:** forum-claim-unverified (found via search only, source not opened) — **source:** GitHub search result.
- `dcs-liberation` (the dynamic-campaign generator) builds entirely on pydcs for mission read/write rather than rolling its own parser — corroborates pydcs's `dcs/lua` parser as the de facto standard, not a one-off. — **evidence:** documented (dcs-liberation repo directly depends on and imports pydcs) — **source:** [dcs-liberation/dcs_liberation](https://github.com/dcs-liberation/dcs_liberation).

### Possible Approaches
- **Lua parsing for Mission Interpreter:** reuse pydcs's `dcs.lua.parse`/`dcs.lua.serialize` module directly (it's LGPL-3.0, already flagged reusable in `reference_pydcs_prior_art.md`), or depend on pydcs itself (`dcs.mission.Mission`) for the whole read path rather than re-parsing manually — pydcs already resolves DictKey → dictionary text, exposes `lateActivation`/`hidden` flags as typed attributes, and separates trigger zones from trigger rules, which is exactly the "filter author-only knowledge" boundary Mission Interpreter needs. A hand-rolled regex parser is not recommended: the format has real nested-table, comment, and numeric-edge-case handling that pydcs already solved and validated against years of real ED mission files.
- If full pydcs is too heavy a dependency (it ships large generated data files — `weapons_data.py` alone is ~450KB, `countries.py` ~1.3MB), the narrower `dcs.lua` subpackage alone (parse+serialize, no unit/weapon database) could be vendored or imported standalone, since Mission Interpreter's own semantic layer (route/trigger/group interpretation) is bespoke anyway and doesn't need pydcs's weapon/country catalogs.
- For briefing-image and kneeboard-image handling: treat `KNEEBOARD/` and any `mapResource`-referenced file as opaque binary assets to pass through to the Mission Understanding output (e.g. so a briefing map image can still be shown to the player-facing side), not to parse — Mission Interpreter's job is structured understanding, not image OCR (unless a future milestone explicitly wants VLM-based kneeboard text extraction, which is out of scope here).

### Unresolved
- **No independent confirmation from Eagle Dynamics documentation.** ED does not appear to publish an official `.miz`/mission-table schema; every source here is Hoggit wiki (community-maintained), ED forum posts (community, sometimes ED staff — not verified which here), or the pydcs source itself (unofficial third-party, LGPL). Treat the whole `mission` table shape as **community-reverse-engineered, not ED-documented**, and flag this to the Architect as an ongoing format-drift risk across DCS patches — pydcs itself has an open issue (#26) where a DCS content update (JF-17 payload data) broke its parser assumptions, showing the schema is not stable/versioned in a way third parties can rely on indefinitely.
- Exact `route.points[]` x/y/alt/speed field names were not directly quoted from source in this session (the fetch summarized rather than quoting the raw waypoint-position code) — worth a direct read of `dcs/point.py` and the `MovingPoint.load_from_dict`/`dict()` methods before Implementer writes any route-parsing code.
- `mission["weather"]` sub-key names (wind-at-altitude structure, cloud base/density fields) were only sourced from Hoggit's prose summary, not cross-checked against pydcs's own weather-loading code — worth a follow-up read of `dcs/weather.py` (if it exists) before relying on exact field names.
- Whether `triggers` zone entries carry enough geometry (polygon vertices vs. circle radius+center) to reconstruct arbitrary trigger-zone shapes, and whether `trigrules` action types are enumerable/closed (i.e. whether "spawn group" and similar author-only actions are a fixed, greppable set) was described only secondhand via Hoggit, not verified against pydcs's `dcs/action.py`/`dcs/condition.py` source directly.
- `Ked57/dcs-mission-parser` was found but not opened — worth a look if pydcs turns out unsuitable (e.g. if its Lua parser's lack of trailing-comma / long-string support ever breaks on a real mission file), as a second independent implementation to cross-check against.
