# .miz Structure Validated Against a Real Sample File

**Date:** 2026-09-12
**DCS version:** not stated in sample (mission `["version"] = 23`, a format-revision number, not a DCS build number)
**Theatre:** Afghanistan (community campaign mission, "Mission 02-Bagram.miz")

### Question
`mission-interpreter/research/2026-09-12-miz-file-structure.md` (prior note, hereafter "the prior note") established `.miz` structure entirely secondhand — Hoggit wiki prose, ED forum quotes, and reading pydcs's Python source, with **no real `.miz` bytes** to check any of it against. MI-0 requires validating those claims against an actual sample now that one exists at `mission-interpreter/research/samples/Mission 02-Bagram.miz` (gitignored, third-party campaign content — never committed, never quoted at length here).

### Findings

All findings below are **evidence: reproduced-locally** (bytes read directly from the sample this session via `unzip`/`grep`/`Read`) unless marked otherwise. Each cross-references the prior note's claim it confirms, corrects, or extends.

- **Zip top-level structure — confirmed with corrections.** Real listing (133 files): `mission`, `options`, `warehouses`, `theatre` (plain text, "Afghanistan" — an **11-byte top-level file**, not just `mission["theatre"]`; the prior note didn't know this file existed at the zip root), `l10n/DEFAULT/dictionary`, `l10n/DEFAULT/mapResource` (the prior note assumed `mapResource` was a bare top-level member; it is actually nested under `l10n/DEFAULT/`), plus a large flat pile of `.ogg` (radio voice-line audio) and `.png` (kneeboard/document images) files directly inside `l10n/DEFAULT/`, and a separate `KNEEBOARD/IMAGES/` tree (not `KNEEBOARD/<AIRCRAFT_NAME>/IMAGES/` as the prior note guessed from secondhand how-to guides — this mission's kneeboard folder is aircraft-generic, one flat `IMAGES/` dir). — **source:** `unzip -l`.
- **DictKey externalization — confirmed exactly.** `mission["descriptionText"] = "DictKey_descriptionText_1"`, `descriptionBlueTask = "DictKey_descriptionBlueTask_3"`, `descriptionRedTask = "DictKey_descriptionRedTask_2"`, `descriptionNeutralsTask = "DictKey_descriptionNeutralsTask_4"`, `sortie = "DictKey_sortie_5"`, and `l10n/DEFAULT/dictionary` resolves them 1:1 (`["DictKey_sortie_5"] = "Mission 2 - Operation 'Граница' (Part II)"`, etc.). This exactly matches the prior note's claim. — **source:** direct grep of `mission` and `dictionary`.
- **DictKey usage is far broader than briefing text.** `DictKey_...` references also appear as `DictKey_ActionComment_*`, `DictKey_ActionRadioText_*`, `DictKey_ActionText_*` — i.e. every piece of user-facing trigger-action text (radio calls, on-screen messages, comments) is externalized the same way, not just the four briefing/sortie fields the prior note focused on. Mission Interpreter's dictionary-resolution step needs to run generically over all `DictKey_*` values found anywhere in the tree, not just a fixed list of known field names. New finding, not anticipated by the prior note.
- **`hidden`/`hiddenOnPlanner`/`lateActivation` — confirmed present and used; `hiddenOnMFD` not observed.** `["hidden"] = true` appears (multiple groups), `hiddenOnPlanner` appears 9 times, `lateActivation = true` appears 5 times (ambush/late-spawn groups, as predicted). `hiddenOnMFD` has **zero occurrences** in this file — not falsified (this mission's author may simply not use it), but not verified real either; still resting on pydcs source alone. — **source:** grep counts on `mission`.
- **`route.points[]` field names — resolved, corrects a prior "Unresolved" item.** A real waypoint entry: `alt`, `action` (e.g. `"From Ground Area"`, `"Turning Point"` — a human-readable maneuver label), `alt_type` (`"BARO"`), `speed` (m/s), `task.id`/`task.params.tasks[]` (a `ComboTask` wrapping e.g. `EngageTargets` with `targetTypes[]` and `priority`), `type` (`"TakeOffGround"`, `"Turning Point"`, `"Land"`, `"TakeOffParking"` — distinct from `action`), `ETA`, `ETA_locked`, `y`/`x` (note: `y` key appears *before* `x` in file order, both present as plain numbers, DCS's native planar coordinate system, not lat/lon), `speed_locked`, `formation_template`. This confirms `type`/`action`/`speed`/`alt`/`alt_type`/`ETA_locked` from the prior note and adds the x/y position fields plus the full embedded-task shape it flagged as missing.
- **`mission["weather"]` sub-schema — resolved, corrects a prior "Unresolved" item.** Real block: `wind.{atGround,at2000,at8000}.{speed,dir}`, `enable_fog`/`fog.{visibility,thickness}`/`fog2.{mode,manual[].{thickness,time,visibility}}`, `season.temperature`, `qnh`, `cyclones` (array, empty in this sample), `dust_density`/`enable_dust`, `clouds.{thickness,density,preset,base,iprecptns}`, `atmosphere_type`, `groundTurbulence`, `halo.preset`, `type_weather`, `modifiedTime`, `name` (a human label, e.g. `"Winter, clean sky"`), `visibility.distance`. This is a materially richer and more specific schema than Hoggit's prose summary the prior note relied on — now a directly-quoted structural example rather than a paraphrase.
- **`triggers["zones"][]` geometry — resolved, corrects a prior "Unresolved" item.** Confirmed **two zone shapes coexist**, distinguished by `type`: `type = 0` is a circle (`radius` + center `x`/`y`); `type = 2` is a polygon, with vertices in a `["verticies"]` array (note: **this is the real, misspelled key name shipped by DCS** — "verticies", not "vertices" — a literal gotcha for anyone hand-typing a parser/schema). Each zone also carries `zoneId`, `name`, `color` (RGBA), `properties` (empty in this sample), `hidden`, `heading`. This confirms trigger zones carry real polygon geometry, not just circles, resolving the prior note's uncertainty directly.
- **`trigrules` — real schema is a `predicate`-based tree, richer and differently-shaped than pydcs's abstraction; the action vocabulary IS closed and cleanly enumerable.** Each rule: `{ comment, eventlist, rules[] (nested AND/OR conditions), actions[], predicate (the rule *kind*) }`. The rule-kind `predicate` values found: `triggerStart`, `triggerOnce`, `triggerContinious` [sic — DCS's own spelling], `triggerFront`. Condition predicates are prefixed `c_` (e.g. `c_flag_is_true`, `c_time_after`, `c_unit_in_zone`, `c_unit_altitude_higher`, `c_cockpit_param_equal_to`, plus a boolean-combinator `predicate = "or"` used inside nested `rules[]`). Action predicates are prefixed `a_` (e.g. `a_set_flag`, `a_clear_flag`, `a_activate_group`, `a_out_text_delay_s`, `a_out_sound`, `a_radio_transmission`, `a_cockpit_perform_clickable_action`, `a_remove_scene_objects`, `a_set_ATC_silent_mode`, `a_mark_to_coalition`, `a_add_radio_item`/`a_remove_radio_item`, `a_ai_task`). 39 unique `predicate` strings total across 85 top-level rules in this one file, cleanly namespaced (`a_`=action, `c_`=condition, `trigger*`=rule kind, `or`=combinator) — this directly answers the prior note's open question: **yes, the action/condition vocabulary is a closed, greppable set of `predicate` string literals**, and the raw file format itself (not pydcs's Python wrapper classes) is the more direct and complete source of truth for it. This corrects the prior note's characterization ("loaded by `Rules.load_from_dict` into pydcs's TriggerRule/condition/action structures") — pydcs's classes are a lossy-looking abstraction over this predicate/string schema, not a 1:1 mirror of it.
- **A third, previously-unknown trigger-adjacent top-level table exists: `mission["trig"]`.** Not mentioned anywhere in the prior note or in any secondhand source consulted before now. It holds `{ actions[], events, custom, func[], flag[], conditions[], customStartup, funcStartup }`, where `actions[]`/`conditions[]`/`func[]` entries are **literal generated Lua source-code strings** — e.g. `"a_out_text_delay(getValueDictByKey(\"DictKey_ActionText_21\"), 10, false, 0);a_out_sound_s(...);...c_start_wait_for_user(\"1\",\"999\"); mission.trig.func[2]=nil;"`. This looks like the Mission Editor's **compiled/flattened executable form** of `trigrules` — the same `a_*`/`c_*` predicates as literal Lua function calls with concrete argument lists, cross-referencing the same `DictKey_*`/`ResKey_*` string-table IDs. Practical value for Mission Interpreter: `trig.actions[]`/`trig.conditions[]` reveal the **real call signature** (argument order/types) of each `a_*`/`c_*` predicate, which the structured `trigrules` table alone does not spell out as unambiguously (e.g. confirms `a_remove_scene_objects(zoneId, mask)`, `a_set_ATC_silent_mode({airdromeId=N}, bool)`, `a_cockpit_perform_clickable_action(device, command, value, plugin)`). Whether `trig` is authoritative-and-executed-at-runtime vs. `trigrules` is uncertain — see Unresolved.
- **Group/unit container path in the tree — resolved, not stated at all in the prior note.** Groups live at `mission.coalition.<"blue"|"red"|"neutrals">.country[N].<category>.group[]`, where `<category>` is e.g. `helicopter`, `plane`, `vehicle` (by unit type, not by side — side is already selected via the `coalition` and `country` levels). Each coalition also carries `bullseye.{x,y}` and `nav_points` at the coalition level (not per-group). This is load-bearing for any parser and wasn't captured secondhand.
- **New top-level `mission` keys not anticipated by the prior note:** `requiredModules` (empty in this sample — likely aircraft/module dependency list), `date` ({Year,Month,Day} — confirms prior note's guess), `trig` (see above), `result` (unread — likely mission win/lose condition config), `maxDictId` (dictionary-ID counter, editor bookkeeping), `groundControl`, `pictureFileNameN`/`pictureFileNameServer`/`pictureFileNameR`/`pictureFileNameB` (per-side/server briefing map image filenames — these are the actual link between `mission` and `mapResource`/`KNEEBOARD` assets, not investigated further this session), `drawings` (unread — likely F10-map drawing markup), `map` (unread), `coalitions` (plural — distinct from the singular `coalition` tree holding groups; unread, likely just side membership/color config), `customFormations`, `goals` (unread — likely scoring/objective metadata, high relevance to Mission Interpreter, worth a follow-up read), `version` (=23, a mission-file-format revision counter, not a DCS build/patch version), `currentKey`/`failures`/`forcedOptions`/`start_time` (all unread, editor/session bookkeeping). None of these were in the prior note's list of "relevant subsections" — most look like editor bookkeeping, but `goals`, `drawings`, and the `pictureFileName*` family look substantively relevant to Mission Interpreter's job and are flagged for a follow-up read before MI-1 parsing work.
- **pydcs not installed in this environment** — `python3 -c "import dcs"` and `pip3 show dcs` both fail (package not found). The optional bonus sanity-check (parsing this file with pydcs) was not attempted; not required for MI-0.

### Reproducible Test
The exact commands run this session (safe to re-run against the same or any other sample `.miz`, since they only ever sample small `grep`/`Read` excerpts, never dump the full file):
```
unzip -l "mission-interpreter/research/samples/<file>.miz"
unzip -p "mission-interpreter/research/samples/<file>.miz" theatre
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -o 'DictKey_[A-Za-z_0-9]*' | sort -u
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -n '\["description'
unzip -p "mission-interpreter/research/samples/<file>.miz" l10n/DEFAULT/dictionary | grep -n 'DictKey_descriptionText'
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -c 'lateActivation\|hiddenOnPlanner\|hiddenOnMFD'
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -n '\["points"\]'   # then Read the surrounding block
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -n '\["weather"\]'  # then Read the surrounding block
unzip -p "mission-interpreter/research/samples/<file>.miz" mission | grep -o '\["predicate"\] = "[a-zA-Z_]*"' | sort -u
```
The mission file was extracted once to a scratch path (outside the repo, in the session scratchpad) to allow line-numbered `Read` on specific offsets rather than repeated full-file `unzip -p` pipes; that scratch copy was not retained anywhere in the repo.

### Possible Approaches
- Prefer parsing `trigrules` (structured, typed table) as the primary source for Mission Interpreter's semantic understanding of scripted mission logic, but keep `trig` available as a cross-reference for resolving a predicate's exact argument signature when `trigrules`' typed fields are ambiguous or when `trigrules` for some rule looks incomplete relative to `trig`.
- The `predicate` string vocabulary (`a_*`/`c_*`/`trigger*`) is closed and greppable per-file; a robust parser should still tolerate encountering an unrecognized predicate (log-and-skip) rather than fail hard, since this vocabulary is undocumented by ED and could gain values across patches — same format-drift risk the prior note already flagged for pydcs.
- The generic-DictKey-lookup finding (DictKey appears in trigger action text too, not just 4 briefing fields) argues for implementing dictionary resolution as a **tree-wide substitution pass** (walk the whole parsed `mission` table, replace any string matching `^DictKey_` by dictionary lookup) rather than a hardcoded list of known fields — simpler and future-proof against new DictKey-bearing fields ED might add.
- `goals`, `drawings`, and the `pictureFileName*`/`mapResource` link are still unread and look relevant to Mission Interpreter's briefing/objective understanding — worth a follow-up targeted read (same small-excerpt-only discipline) before or during MI-1, rather than a full separate investigation session.

### Unresolved
- Whether `mission["trig"]` is what DCS actually executes at runtime, with `trigrules` being purely an editor-side structured representation kept in sync by the Mission Editor (or vice versa, or both are executed) — matters for whether Mission Interpreter can rely on `trigrules` alone or must also parse `trig`'s embedded Lua strings for full fidelity. No source (ED, Hoggit, pydcs) mentions `trig` at all; this needs either an ED/Hoggit search specifically for `mission.trig` (not attempted this session) or cross-checking a second sample mission to see if the two tables are always in lockstep.
- `hiddenOnMFD` remains unverified against real bytes (zero occurrences in this one sample, not necessarily meaningful — this mission's author may not use the flag).
- `requiredModules`, `result`, `groundControl`, `drawings`, `map`, `coalitions` (plural), `customFormations`, `goals`, `failures`, `forcedOptions`, `currentKey` were located but not read — content unknown beyond the key name.
- Only one sample mission was examined (single author, single terrain, single DCS mission-format `version` = 23). Field presence/absence in this file doesn't prove universality across DCS versions or Mission Editor versions; a second sample from a different author/era would strengthen every "confirmed" claim above from "true in this file" to "true in general."
- pydcs itself was not exercised against this file (not installed in this environment) — the bonus cross-check from the task was not completed. If pydcs is ever installed in a future session, running it against this exact sample would be a strong, cheap way to catch any divergence between this manual reading and pydcs's own (widely-trusted) parser.
