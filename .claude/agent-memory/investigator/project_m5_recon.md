M5 ("First persistent model") recon, 2026-09-03, DCS 2.9.29.27278, Syria. Full findings: `world-model/research/2026-09-03-m5-recon.md`.

- `land.getSurfaceType(vec2)`: documented Mission Scripting-only (same env as getHeight), enum LAND=1/SHALLOW_WATER=2/WATER=3/ROAD=4/RUNWAY=5. Distinguishes road vs water in one call — but point-sampling only, no width/centerline; grid must be finer than road width or it aliases badly. Not reproduced locally yet.
- `land.getClosestPointOnRoads(roadType, x, y)` — plain numeric args (NOT vec2), roadType 'roads'/'railroads', returns two numbers. `land.findPathOnRoads(roadType, x, y, destX, destY)` — roadType for rail is **'rails' not 'railroads'** (documented ED bug, inconsistent with sister function — landmine for pipeline code). Both Mission-Scripting-only, added 2.5. No forum/community evidence found either way on nil/garbage behavior far from roads — untested, worth a smoke-test point.
- Big finding: `Mods/terrains/<theatre>/map/towns.lua` is a **plain, unencrypted, offline-readable Lua file** (no live mission needed, just `cat`/WSL probe) — a DCS-shipped name+lat/lon gazetteer. Syria: 1186 entries, mixes cities/villages/military bases/landmarks/POIs, point-only (no extent, no category field). This overturns the earlier "names come from OSM" assumption — DCS itself is authoritative for name+point of anything it chose to label; OSM still needed for settlement extent/polygon and for places DCS didn't label.
- `MissionGenerator/nodes.lua` (93 lines) + `nodesMap.lua` (1 line) exist in the same terrain tree, NOT yet read (only grepped for lat/lon keywords, no match — inconclusive since a node graph likely uses different key names). High-value cheap follow-up: could be a DCS-native road/waypoint topology source, offline-readable like towns.lua, potentially de-risking the live-mission road-extraction approach entirely. Do this before committing to Q2's live-mission mechanism as the only path.
- Probe scale: M4 proved 100 `land.getHeight` calls + io.write in one trigger, no issue. No documented hard watchdog limit found for many-quick-sequential-calls (distinct from busy-wait, which is documented to hang DCS). Standard community pattern for large loops: `timer.scheduleFunction` self-rescheduling chunker + incremental append-mode io.write, not one giant single-shot loop. Recommended: smoke test at n=100-200 before scaling to full 1,600-10,000 point grid.
- forum.dcs.world 403s WebFetch as always (see forum-dcs-world-fetch.md) — the "land.getSurfaceType small enhancement" ED wishlist thread unread, ask user to paste if it matters.
- towns.lua entry format (confirmed exhaustively, ~1182-1186 entries, no exceptions found): `["Name"] = { latitude = .., longitude = .., display_name = _("Name")},` — exactly 3 fields, no category/type/extent field ever. Coordinate space is decimal-degree lat/lon, consistent with beacons.lua's positionGeo frame (cross-checked Hama entry vs. M2's Wikipedia reference, ~1.3km/0.6km diff, same order as M1's known ~1-1.3km residual) but not proven identical via an independent DCS x/z ground truth.
- IMPORTANT caveat on towns.lua coverage: it is geographically uneven. Syria map's towns.lua entries span lat 31.07-37.88°N only — the Gemerek test region (39.09-39.28°N, the M1-M4 testbed) has ZERO towns.lua entries, ~130km north of towns.lua's northernmost entry. Do not assume towns.lua covers an arbitrary small test region on this map — always check coverage for the specific region before relying on it as a name source.
- towns.lua's exact table-opening declaration (variable/global name) and MissionGenerator/nodes.lua + nodesMap.lua full content are still UNREAD as of 2026-09-03 — grepped only, no full dump. `world-model/tools/wsl/probe_syria_terrain_lua.sh` was extended same-day to capture all three (nodes.lua full cat, nodesMap.lua bounded preview + size, towns.lua head/tail) but has not been re-run — needs one more Windows/WSL round-trip via win-mac-sync before these are resolved.
