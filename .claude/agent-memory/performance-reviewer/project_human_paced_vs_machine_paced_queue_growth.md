`body-layer`'s `CrewConsole._pending_positional_replies` (Stage 6,
`plans/voice-latency-instrumentation/plan.md`) has no explicit cap, unlike
`aircraft-layer/src/collector/audio_sender.py`'s `_MAX_QUEUE_LEN=64` on the
audio-playback queue (added in an earlier performance review specifically
because that queue *can* be fed by an automated producer — routine callout
lines generated by belief/event logic — faster than `winsound` drains it).

**Why the asymmetry is correct, not an oversight**: `_pending_positional_replies`
is only ever appended to from a dispatched player command (voice utterance or
F10 click), one human acting in real time. A flying session cannot realistically
produce more than a handful of positional commands within one channel-busy
window (a spoken readback is ~4-5s for an 8-word line) — the producer is
self-throttling because it's a person, not code.

**How to apply**: before flagging a list/queue with no cap as a risk, check
*what feeds it*. An automated/event-driven producer (belief state changes,
callouts, anything that can fire many times per poll without a human in the
loop) needs a bound, per `aircraft-layer`'s own `_MAX_QUEUE_LEN` precedent.
A producer that is one human's voice or clicks, in a single-player/LAN-only
project phase, does not need one yet — note it as MONITOR with the mirrored-
pattern fix named (oldest-dropped, same shape as `_MAX_QUEUE_LEN`) for if a
real flight ever shows otherwise, rather than demanding the cap now.
