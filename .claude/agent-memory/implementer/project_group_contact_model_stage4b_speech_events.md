Implemented `plans/group-contact-model/plan.md` Stage 4b (the count clause in `body-layer/src/belief/speech.py`/`events.py`/`contacts.py`/`tools.py`/`escalation.py`) on `feature/group-contact-speech`.

**A test the design's own inventory missed**: `body-layer/tests/test_console.py::test_console_module_contains_no_belief_logic` asserts every public (no leading underscore) `belief.tools` function name literally appears in `console.py`'s source -- a structural check that `console.py` stays a thin wrapper. The design named its new helper `estimated_units_lower_bound` (public); this broke the check immediately since no console command calls it directly (only `get_stats`/`get_situation`/`escalation.py` do). Fixed by renaming to `_estimated_units_lower_bound`, matching the established convention `_cardinality_facts`/`_classification_facts` already set for tools.py-internal-only helpers. Lesson: any new public `belief.tools` function needs either a real `console.py` caller or a leading underscore -- check this test before adding one; the grep-for-affected-tests step is easy to skip for `tools.py` since it "obviously" wasn't in the design's named list of touched test files.

**A design-anticipated existing-test conflict, correctly resolved by editing the test**: the design's own section 4 argued `_OP_CLASS_DISPLAY["OP_GROUPSOMETHING"]` was dead code and explicitly instructed checking `test_render_contact_report_maps_default_op_class_to_display_word` against that claim, calling a positive hit "a finding ... not a reason to keep the dead entry." The hit was real: the test's fixture forced `classification_level=2` ("class") directly via a raw `Observation`, bypassing the real `_op_class_of` resolver that makes the value structurally unreachable at that level in production. Per the design's own explicit permission, the fixture was corrected to `classification_level=1` ("presence", the level this value actually occurs at) rather than left unreachable -- this is the one documented exception to "editing an existing speech test's expected string means the guard failed," because it's a different code path (OP_GROUPSOMETHING removal) from the load-bearing singular/count-clause guard the task's stop condition was actually about. This is a concrete case where the plan's own prose pre-authorized the exact test edit needed -- worth distinguishing from a silent, unauthorized test change.
