# BL-6 Feasibility: Can Petrovich's scan behavior be commanded externally?

**Date:** 2026-09-10
**DCS version:** not verified locally this session — see below (file paths confirmed present in `world-model/data/raw/dcs/2026-09-02/DCS-files.txt`, a 2026-09-02 install file listing; no live probe run)
**Theatre:** n/a (module/cockpit question, not terrain)

### Question
Whether any DCS-exposed mechanism lets an external, install-unmodified process cause Petrovich to
scan/look at an area, bearing, or range — the blocking premise flagged in `plans/body-layer/plan.md`
§7 for BL-6 ("Commands and inspect-and-adapt").

### Findings

- **`Export.LoSetCommand` is a real, documented, historically-used numeric command-injection API**,
  distinct from and independent of the Sim_ControlAPI.md Hook/GUI-state mirror already in this
  repo's `aircraft-layer/research/reference/Sim_ControlAPI.md` — it is also available directly
  inside `Export.lua`'s own state (`LuaExportBeforeNextFrame`), which this project already deploys
  and controls. Signature is `LoSetCommand(commandID[, value])`, `value` in `[-1.0, 1.0]` for
  analog commands, omitted for discrete ones (e.g. `LoSetCommand(64)`). — **evidence:**
  forum-claim-unverified (ED forum thread titles/snippets only, `forum.dcs.world` 403'd this
  session — see `forum-dcs-world-fetch.md`; not independently reproduced against a live DCS
  install) — **source:** ED forum threads "LoSetCommand function in Export.lua" (topic/270552),
  "Need a full command macro list for LoSetCommand()" (topic/57769), "LoSetCommand() deprecated?"
  (topic/338836) — the last of these is itself a live open question about whether ED still honors
  it for modern modules, which directly bears on confidence here.
- **A dedicated in-cockpit Petrovich command UI exists and is a shipped, first-class module
  feature**, not something this project would need to invent: `Mods/aircraft/Mi-24P/Cockpit/
  Scripts/HelperAI/AI_Wheel/` (`AI_Wheel_indicator_noVR.lua`, `AI_Wheel_indicator_VR.lua`,
  `AI_Wheel_page_common.lua`, `AI_Wheel_page_noVR.lua`, `AI_Wheel_page_VR.lua`) plus a texture at
  `Mods/aircraft/Mi-24P/Cockpit/IndicationTextures/Petrovich/AI_Wheel.dds` — a radial "command
  wheel" UI literally namespaced under `Petrovich`. A second, related file group,
  `Mods/aircraft/Mi-24P/Cockpit/Scripts/AI/ControlPanel/` (`g_panel.lua`, `g_panel_definitions.lua`,
  `g_panel_page.lua`) and `Mods/aircraft/Mi-24P/Cockpit/Scripts/AI/AI_Gunners.lua` /
  `AI_Side_Gunner.lua` / `AI_utility.lua`, is a second, older-looking "gunner control panel"
  device — relationship between the two (successor/predecessor, or two different controls) is
  unresolved. — **evidence:** reproduced-locally, but path-existence only — file *paths* were
  confirmed against the 2026-09-02 install listing (`grep` run this session, see Reproducible
  Test), file **contents** were not read (not synced to this repo; no live DCS access this
  session). Classify the *existence* of the mechanism as reproduced-locally; its *behavior* (wheel
  options, whether "scan area/sector" is one of them, what command IDs it issues) is unread/unknown.
- **A separate input-binding profile exists specifically for this**:
  `Mods/aircraft/Mi-24P/Input/Mi_24P_AI_Menu/{keyboard,joystick,mouse}/default.lua` — a distinct
  input context from `Mi_24P_pilot` and `Mi_24P_Gunner`, strongly suggesting the AI Wheel is
  opened/driven by its own keybind profile, standard DCS practice for a modal radial menu. Not
  read (same reason as above).
- **`HelperAI_sound.lua`'s per-event sound catalogue (~100 events) contains state-transition names
  that would be exactly the right shape for scan-outcome verification if they were externally
  observable**: `observ_on`, `target_acq`, `still_searching`, `sight_blocked` (previously read in
  full, `2026-09-08-pb1-5-worldobjects-filter-and-ambient-detection.md`). **However these are
  one-`.ogg`-per-event audio triggers, not confirmed to correspond to any Lua-readable state
  variable, `get_param_handle`, or `list_indication` field** — no evidence either way that firing
  one of these events changes anything visible outside of the actual audio playback (which
  Export.lua cannot observe). — **evidence:** reproduced-locally that the events exist;
  inferred/unresolved that they are observable externally — **source:**
  `win-mac-sync/from-windows/` copy of `HelperAI_sound.lua` (prior session).
- **`list_indication(6)`'s target list is weapon-selection/attack-mode-gated, not an ambient "is
  Petrovich currently scanning" flag** (established prior session, forum thread topic/388039
  search-snippet: list is "generated by Petrovich AI when using missiles"). This means even a
  confirmed scan command would not necessarily make `list_indication(6)` populate on its own —
  scanning and target-list population may be two different Petrovich states. — **evidence:**
  forum-claim-unverified (search-snippet only, thread not independently re-read) — **source:**
  `2026-09-08-pb1-5-worldobjects-filter-and-ambient-detection.md`.
- No evidence, in this session or prior ones, of any **read-side signal that directly reports
  "Petrovich is scanning" vs "Petrovich found N contacts" vs "Petrovich is idle"** as a discrete
  state. The candidates are all either indirect (contact-count ambient callout text, itself
  event-triggered not polled — see `2026-09-08` session) or unconfirmed-observable (the sound
  events above).

### Possible Approaches
- **If `LoSetCommand` + a wheel command ID works**: aircraft-layer would add a small `POST
  /command/scan` (or similar) endpoint mirroring the existing `/text/push` shape — collector
  forwards a discrete command to Export.lua over the same loopback TCP channel already in place
  (no Hook script needed, since `LoSetCommand` is directly callable from Export.lua's own state
  per Sim_ControlAPI.md's namespace list). This is the cleanest and most in-keeping-with-existing-
  architecture path if it pans out.
- **If `LoSetCommand` is dead/deprecated for this module** (topic/338836's live question) but the
  AI Wheel itself is real: fall back to simulated keypress/joystick-button injection (Windows
  `SendInput`-equivalent) replicating whatever `Mi_24P_AI_Menu` keybind opens the wheel plus
  whichever bound key selects the "scan" option — a well-established technique in the flight-sim
  automation community (this is literally the mechanism VoiceAttack/VAICOM-style tools use under
  the hood for AI-command menus in modules with no scripting hook, though this project's own prior
  research confirmed VAICOM's actual Mi-24P profile is radio-only and excludes Petrovich
  specifically — so an existing precedent, not an existing ready-made tool, is what's available).
  This is coarser (keypress simulation, not parameterized "scan at bearing X range Y") and sits
  outside Export.lua's normal loopback-TCP channel — it would need a small separate Windows-side
  input-injection helper process, a new architectural surface for aircraft-layer.
- **If neither pans out**: fall back to the body-side-only "virtual scan" per the Architect's own
  Q4 framing — body-layer sets an attention-area bias that reprioritizes which already-detected
  `LoGetWorldObjects` contacts surface as "found," without ever touching DCS's own AI/sensor state.
  This is a real degradation (Petrovich never actually looks anywhere different), consistent with
  the plan §7 language ("body tracks intent and reports it can't be actioned").

### Unresolved
- **Whether the AI Wheel / g_panel actually offers anything resembling "scan this area/bearing"**,
  as opposed to only combat-mode commands (attack/hold fire/cover/engage) — this is the single
  biggest open question and is answerable only by reading `AI_Wheel_page_common.lua` /
  `g_panel_definitions.lua` (step 1 of the live probe above). If the wheel has no scan-specific
  option, BL-6's "scan this area" framing may need to be redefined around whatever commands
  actually exist (e.g. "attack this area" might be the closest real lever).
- **Whether `LoSetCommand` still functions for non-legacy/full-fidelity modules** — the
  topic/338836 thread title alone ("deprecated?") is a live community doubt, not resolved by this
  session; needs either a live test or a full (non-403'd) read of that thread.
- **Whether any Petrovich state-transition event (`observ_on`/`target_acq`/`still_searching`) is
  externally observable at all**, versus being pure native-to-audio with no corresponding readable
  variable — unresolved, would need either a live probe watching `list_indication` output across a
  known scan-triggering action, or new primary-source Lua reading a `get_param_handle`/indicator
  tie-in that hasn't been found yet.
- Relationship between the two candidate command surfaces (`AI_Wheel` vs `g_panel`/`AI_Gunners`) —
  whether they're the same feature exposed two ways, competing/legacy vs current, or genuinely
  different controls — unread, unresolved.
