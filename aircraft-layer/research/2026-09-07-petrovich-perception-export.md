# Petrovich (Mi-24P AI Gunner) Detection/Target State: Externally Extractable?

**Date:** 2026-09-07
**DCS version:** not verified locally — desk research only (Hoggit wiki, ED forums via search snippets, GitHub). forum.dcs.world 403s WebFetch directly (consistent with prior session finding, see `forum-dcs-world-fetch.md` in investigator memory); no probe was run against the installed DCS instance, which was not reachable this session (Mac-only tools). No Mi-24P install tree was found on this Mac (`find / -iname "*Mi-24P*"` returned nothing) — the DCS install lives only on the Windows box per the project's compute-topology.
**Theatre:** not applicable

### Question

PB-0 ("Proven inputs") is blocked on: what Petrovich (Mi-24P's AI gunner/copilot) detection/target state can actually be extracted from a running DCS mission, distinct from ownship telemetry (already solved by the aircraft-layer, see `2026-09-06-aircraft-layer-live-runtime-io.md`)? Specifically: HelperAI/Petrovich cockpit scripts, `list_indication()`, Export.lua visibility into AI target state, cockpit device/arg APIs, whether target IDs persist across frames, DCS-BIOS/community precedent, and prior community attempts to read Petrovich's target awareness externally.

### Findings

**1. Petrovich's UI lives in a distinct, real, on-disk script tree — SOURCE READ THIS SESSION — it renders, it does not itself publish structured data via any Lua-visible channel**
- The user retrieved four files directly from the Windows DCS install and they were read in full this session — **evidence: reproduced-locally, primary source, strongest evidence category in this report**:
  - `Mods/aircraft/Mi-24P/Cockpit/Scripts/HelperAI/HelperAI_indicator.lua` — a page router. Declares indicator metadata (`indicator_type`, `purposes` — HUD/screenspace-inside/outside-cockpit/auxiliary-sight render targets) and delegates all content to one page (`HelperAI_page.lua`).
  - `Mods/aircraft/Mi-24P/Cockpit/Scripts/HelperAI/HelperAI_page.lua` — delegates further, calling `create_and_add_elements(cross_size, compass_size, is_vr)` defined in the next file.
  - `Mods/aircraft/Mi-24P/Cockpit/Scripts/HelperAI/HelperAI_page_common.lua` (1080 lines) — the real payload. Declaratively builds every visual element of Petrovich's HUD-style overlay (crosshair, compass, countermeasures panel, and critically a **5-line scrolling target list**: `upper_upper_list_text`, `upper_list_text`, `middle_list_text` (selected), `lower_list_text`, `lower_lower_list_text`, plus a selection-arrow element `list_red_arrow`/`list_red_arrow_text` with offsets -2..+2) and a separate **crosshair/sight readout** (`hdg_text`, `az_text`, `el_text` — heading, azimuth, elevation of wherever the sight is currently pointed).
  - `Scripts/Aircrafts/_Common/Cockpit/elements_defs.lua` — shared, aircraft-agnostic rendering helper library (`CreateElement`, `Add`, circle/grid geometry math, blend-mode/clip constants). No data-fetch logic, no aircraft- or Petrovich-specific content at all.
- **Zero occurrences of `get_param_handle(` (or any other data-read/publish call) across all four files.** Every dynamic element instead carries a `controllers = {{'<name>', ...args}}` table (e.g. `{{'middle_list_text'}}`, `{{'az_text'}}`, `{{'list_red_arrow', -1}}`, `{{'show_hdg_az_el_red'}}`). This is DCS's standard cockpit-indicator architecture: Lua declares *what* to draw and *which named controller* supplies its live value each frame; the controller itself (the code that actually computes "is this list row currently a BMP-2 at bearing X" and turns it into `middle_list_text.value`) is **not implemented in Lua anywhere in this file chain** — it is resolved by the DCS engine's compiled/native indicator-controller dispatch, the same mechanism used for ordinary cockpit gauges (needle sweep controllers, etc.), which is not moddable or readable Lua source.
- **This materially downgrades finding 3's "get_param_handle lead" from unverified-plausible to tested-and-not-found-here.** The specific hypothesis — that HelperAI publishes target data via a named `get_param_handle()` value for Export.lua to read — is **falsified for this file chain**: nothing in Petrovich's own UI-construction code calls it. This doesn't rule out `get_param_handle` entirely (some *other*, non-HelperAI device could theoretically expose a related param under a different name — untested), but the most obvious, hypothesized path is closed.
- **The named `controllers` strings are themselves a positive, converging finding.** They read as a plausible match for what `list_indication()`/`list_cockpit_params()` are documented (per the forum content retrieved this session, see below) to query by name — DCS's Mission Editor "COCKPIT INDICATION IS EQUAL TO" trigger condition and its Lua equivalent are built exactly around reading a named indicator element's current rendered value off a cockpit device page, which is precisely what these controller-tagged elements are. If so, `middle_list_text`, `az_text`, `el_text`, `hdg_text`, and siblings are plausibly individually addressable via `list_indication(<device_id>)`, not one opaque display blob for the whole page — **inferred, moderate-to-high confidence given the architectural match, not confirmed by a live read**.
- **No range readout exists anywhere in this UI.** The crosshair/sight-readout group only exposes heading/azimuth/elevation angles (`hdg_text`/`az_text`/`el_text`) — there is no `range_text`-equivalent element anywhere in the 1080-line file. This is a substantive negative finding for PB-1's design: Petrovich's own displayed state does **not** carry a `range_m` field the way the `observation:` YAML in PETROBRAIN_RUNTIME.md wants — the Mi-24P's Petrovich sight has no laser rangefinder readout to draw. Range would have to be derived externally (ownship position + azimuth/elevation ray-cast against World Model elevation/terrain data, or against `LoGetWorldObjects` ground truth) rather than read directly off Petrovich's UI even in the best case where `list_indication()` works exactly as hoped.
- The five list rows being simultaneously present (not just the selected one) is notable: if individually readable, this is a genuine **list**, not a single "current target" value — matching the aircraft-layer/PB's desire for a target *list*, not just a lock state. What text each row actually contains (target type? bearing? both concatenated?) is unknown — the file only declares layout/positioning, not content format; this needs a live in-game read to see actual string content (see Reproducible Test).

**2. DCS-BIOS's actual, complete Mi-24P module definition exposes gunner-station cockpit *controls*, not Petrovich AI state**
- Fetched `DCS-Skunkworks/dcs-bios` `Scripts/DCS-BIOS/lib/modules/aircraft_modules/Mi-24P.lua` directly (raw GitHub content, successfully retrieved unlike forum.dcs.world) — **evidence: documented, reproduced-locally via WebFetch of the actual source file**.
- It defines extensive OPERATOR (gunner-seat) controls: I9K113 Shturm sight system (device 7, azimuth/elevation gauges, SHTV display), PUVL weapon system (device 6, station selection/fire control), ASP-17V sight (device 16), ASO-2V countermeasures (device 9) — all standard clickable-cockpit device/arg pairs (device index + argument number), the same mechanism as every other DCS-BIOS module.
- **No definitions for Petrovich AI, a target list, or HelperAI state exist anywhere in this module file.** This directly confirms finding 5 of the prior aircraft-layer investigation (`LoGetTargetInformation`/TWS-style functions are FC3-legacy and "we don't normally export these sorts of things" per an ED-Skunkworks maintainer) extends to Petrovich specifically, not just generic sensor/radar contacts — **evidence: documented (primary source file read), strong**.
- Issue `DCS-Skunkworks/dcs-bios#571` ("Mi-24 collective") and a recent changelog note ("fix to the parallel generator lamp argument") confirm the module is actively maintained and reasonably complete for switches/gauges — so the absence of Petrovich state is not merely "nobody got around to it yet," it reflects that DCS-BIOS only ever exposes clickable-cockpit device args, and Petrovich's target list is architecturally *not* implemented as one of those args (it's UI overlay rendering, a different code path) — **inferred, moderate confidence**.

**3. `GetDevice()` / `get_param_handle()` are real, confirmed-documented mechanisms, but neither has any confirmed Petrovich-specific channel**
- `GetDevice(device_id):get_argument_value(n)` / `:performClickableAction(n, v)` is the standard cockpit-device API, confirmed usable from Export.lua (`MainPanel = GetDevice(0)`) and reportedly also callable from a Mission Editor "DO SCRIPT FILE" trigger action (forum thread title corroborates this, content itself unread — see Unresolved) — **evidence: documented** (multiple independent forum/GitHub hits, consistent).
- `get_param_handle(name):get()`/`:set()` is a separate, name-keyed global-variable-like channel used for passing data *between* a module's own cockpit Lua devices (each device runs in its own isolated `lua_State`; param handles are the documented way they talk to each other, and to Export.lua) — **evidence: documented** (Hoggit-adjacent/community-modding-doc hits, consistent across sources).
- **This is the one theoretically live lead**: if Petrovich's HelperAI code internally publishes its detected-target state (bearing/range/classification/ID) through a named `get_param_handle()` value — the way it would need to if the rendered UI element is itself just reading a param to draw text — then that value would, in principle, be readable externally from Export.lua by any script that knows the exact param name. No source evidence was found this session confirming HelperAI actually does this (vs. computing and drawing the list entirely inside its own device's private state with no param handle at all). This can only be resolved by reading the actual `HelperAI_indicator.lua`/`HelperAI*.lua` source and grepping for `get_param_handle(` / `param_handle` calls — **inferred plausible mechanism, unverified — this is the report's central open lead**.

**4. `list_indication(n)` / `list_cockpit_params(n)`: confirmed usable outside pure trigger-condition context, per direct forum content retrieved this session (user pasted both threads manually after 403s)**
- `forum.dcs.world/topic/299113-possible-with-lua-to-read-an-indication/` ("Possible with LUA to read an indication?", Apr–Nov 2022 thread) — **evidence: documented, primary forum content, read in full this session** (previously listed as Unresolved/403'd; user retrieved and pasted it).
  - Marked-solution reply from **Bailey** (a recognized DCS export-tooling/VoiceAttack community author): *"Yes, it's possible. You can read args, indications, cockpit values, etc. See `list_indication` and `list_cockpit_params` for examples,"* linking to the **DCS-BIOS Lua Console docs** (`dcs-bios.readthedocs.io/en/latest/lua-console.html`), and stating they built exactly this kind of animation-argument-based read for a UH-60 campaign (an ED-user-files download, not independently inspected this session).
  - **PravusJSB**: doing this "dynamically" requires "a Hook on the backend" — i.e., a `Scripts/Hooks/*.lua`-context script (the same privileged, DCS-gRPC/Olympus-style environment noted in the aircraft-layer investigation), not a plain Mission Editor trigger.
  - **Jagohu** (earlier reply, before Bailey's): "Not that I found unfortunately. What you can do is set the trigger in the ME to read something and execute a script with that. Cumbersome, but it works" — i.e., the fallback if a direct read isn't available is proxying through a trigger-condition into a script variable.
  - Net reading: `list_indication`/`list_cockpit_params` are **real, callable functions with documented existence** (DCS-BIOS's own Lua console uses them), reachable from at least a Hook-script context and/or the DCS-BIOS Lua console mechanism — this is a materially stronger position than "trigger-condition-only," though still **not confirmed specifically Export.lua-callable** (Export.lua and Hook scripts are different privilege/lifecycle contexts per the aircraft-layer investigation's finding 6).
- `forum.dcs.world/topic/288960-petrovich-target-list/` ("Petrovich Target List", Dec 2021–Jan 2022 thread) — **evidence: documented, primary forum content, read in full this session**. No scripting/API content (it's a gameplay-support thread about a user unable to get a target list at all), but it independently corroborates finding 5 below with a **directly quoted ED changelog excerpt** (2.7.7.15038): *"Petrovich AI Target acquisition code refactoring (Petrovich now will not acquire targets in the night or dark enough environment. Petrovich will see targets in dark environments if illumination flares are used. Petrovich will see targets behind some obstructions that were blocking acquisition before but geometrically were not covering the target.)"* — this upgrades finding 5 from forum-claim/search-summary to a **directly-quoted primary changelog source**, confirming light-level-, illumination-, and obstruction-geometry-aware detection logic exists.
- Net conclusion for `list_indication`: no longer "nearly useless" as originally framed — it is a real, actively-used community technique (DCS-BIOS itself depends on it) for reading rendered cockpit-indicator text from outside pure trigger evaluation. Combined with finding 1's `controllers`-name discovery, the concrete next step is narrower than before: confirm (a) which device ID the HelperAI indicator page registers under, (b) whether a Hook-script (not Export.lua) is required, and (c) what `middle_list_text` et al. actually contain as strings in a live mission. Still returns **text, not typed fields** — no evidence anywhere this session of a structured-table return value.

**5. Confirms Petrovich has real internal target-tracking state — DCS's own changelog is evidence of *that*, but not of its exportability**
- A DCS 2.9 changelog/community note states Petrovich's target-detection *time* is now affected by the number of surrounding objects — this is only meaningful if Petrovich maintains some internal notion of candidate/detected targets with associated compute cost, i.e., there genuinely is internal state, not just a random timer — **evidence: forum-claim-unverified** (summarized via search, not read at the primary changelog source this session) — **use with the caveat that ED release-note wording claims like this were not independently verified against digitalcombatsimulator.com's changelog archive this session**.
- This is useful context (it rules out "Petrovich has no real target model at all, it's smoke and mirrors") but does **not** establish that the state is reachable outside the aircraft's own cockpit Lua.

**6. No community precedent found for reading Petrovich's target awareness externally**
- VAICOM PRO added native Mi-24P support, but explicitly **radio support only — does not include Petrovich functions** — **evidence: forum/product-description-claim, moderately strong** (consistent phrasing found describing the VAICOM Mi-24P integration limitation).
- No VoiceAttack/Petrovich integration found goes further than *sending* Petrovich voice-menu commands (i.e., driving Petrovich's existing menu/command interface, which is the documented player-facing command surface, not reading his perception back out).
- "VRS Helper for the Mi-24P" mod exists (title found, content/mechanism not read this session) — flagged as a possible additional lead, unconfirmed what it actually modifies.
- Net: **no prior art was found of anyone extracting Petrovich's target list programmatically for use outside the game** — this appears to be genuinely unexplored territory in the community, not a solved-and-forgotten problem.

**7. Target IDs: no evidence either way**
- No source found describing whether Petrovich's internally-tracked targets carry a stable ID persisting frame-to-frame, or are recomputed/re-rendered fresh each update with no identity concept. The DCS 2.9 changelog note (finding 5) implies *some* per-candidate bookkeeping exists during detection, but says nothing about whether that bookkeeping survives as an addressable ID once a target is "found," nor whether it's exposed anywhere. This is unresolved and can likely only be answered by reading the HelperAI source (finding 1/3) or a live in-mission Lua probe against `GetDevice`/`get_param_handle` calls made from a custom Export.lua while flying a real Mi-24P sortie with visible ground targets.

### Possible Approaches

The file-read evidence now points toward a hybrid design rather than a clean "extractable" or "not extractable" answer: Petrovich's UI genuinely renders a 5-row target list plus azimuth/elevation sight-pointing angles under stable, named controller keys — a real, non-trivial signal exists in principle — but (a) it is text/string-shaped, not a typed table, (b) it carries no range field, and (c) whether `list_indication()` can actually reach it from a live, continuously-running script (Export.lua or Hook) rather than only a one-shot trigger-condition context is still unconfirmed. Design PB-1 for graceful degradation across three tiers rather than a single assumed channel:

- **Tier 1 (best case, unconfirmed) — real Petrovich text signal via `list_indication`:** if the live probe (Reproducible Test step 2) confirms `list_indication(device_id)` returns per-controller text for `middle_list_text` and siblings, parse those strings for target-list content and treat `az_text`/`el_text` as a real bearing/elevation-to-current-sight-point signal (this satisfies `bearing_deg` in the `observation:` YAML directly, with real per-frame provenance from Petrovich's own belief, not a synthetic proxy). `range_m` still has no source in the UI (finding 1) — combine with ownship position via a LOS/terrain ray-cast against the World Model's elevation data (M4/M6) to estimate range along the confirmed real bearing, which is a meaningfully better-grounded estimate than a fully synthetic contact (real angle, inferred range) even though it isn't 100% "true Petrovich perception."
- **Tier 2 (Hook-script required) — same data, different access path:** if Export.lua cannot reach `list_indication`/`list_cockpit_params` (PravusJSB's forum comment suggests a Hook script is the more reliable path), the same parsing approach applies but requires the Hook-script `MissionScripting.lua`-adjacent setup already used by DCS-gRPC-style tooling (a different edit location than Export.lua, per the aircraft-layer investigation's finding 6/7) — architecturally heavier but not a new mechanism class.
- **Tier 3 (fallback, if step 1/2 above yield nothing usable) — the project's already-anticipated fallback, still valid:**

- synthesize a proxy "Petrovich perception" from `LoGetWorldObjects` ground truth filtered by a geometric/LOS/sensor-envelope heuristic (reusing World Model elevation/terrain-masking data from M4/M6), exactly as concluded in the aircraft-layer investigation's finding 5 for sensor contacts generally. This produces the `observation:` shape PB wants (classification/bearing/range) but it is **not** "what Petrovich actually perceived" — it's "what a plausible crew member could perceive," which the runtime doc's world-truth-vs-belief framing already anticipates as a fallback, not a violation of the "must not be omniscient" invariant, provided the filter is conservative (Petrovich's real detection is presumably *worse*, not better, than a generous LOS+range heuristic). Use this whenever Tier 1/2 are unavailable, and consider gating/timing it against Tier 1/2's `az_text`/list-row signal where available even if the full pipeline isn't — e.g. only surface a synthetic contact when Petrovich's own UI suggests he's actually looking at something, so the *timing* of Petrovich's belief is real even if the geometry is synthesized.
- **Not recommended, noted for completeness:** Helios-style pixel/OCR read of Petrovich's rendered indicator overlay. Given Tier 1/2's `list_indication` route is cheaper if confirmed live-callable, OCR should only be considered if the live probe conclusively shows `list_indication` isn't reachable from any usable script context *and* the geometric proxy above proves unsatisfying in practice later.
