# BL-16 M3 — terrain look-ahead grid and atmospheric-visibility clip, desk recon

**Date:** 2026-11-28
**DCS version:** not verified locally this session — no live probe run; every "reproduced-locally" finding below cites an earlier session's own flown evidence (dated), not a fresh check against this install. Context: Petrobrain is a hobby add-on for the DCS World flight-simulation video game (Mi-24P/Petrovich); nothing here controls real hardware.
**Theatre:** not applicable (desk recon only, per task scope)

### Question

For BL-16 M3 (terrain floor + terrain look-ahead, `aircraft-layer/dcs-export/Petrobrain/flight_control.lua`): can a 1 km × ±200 m terrain-elevation grid ahead of the nose be polled, and the grid range clipped to atmospheric visibility — and from *which* DCS environment/API, with what cost and latency shape? `plans/flight-lift-vector/explore-notes.md`'s M3 section already flags both `Export.LoGetAltitude`/`Export.LoGetHeightWithObjects` and the missing weather input as unverified — this is that verification pass.

### Findings

**1. `Export.LoGetHeightWithObjects` — ownship-only, not a point query.**
- Hoggit's `DCS_export` page lists it under the **"Ownship"** section ("Exports data about your own aircraft") — **evidence: forum-claim (Hoggit wiki, fetched this session), unverified against the actual install** — source: `https://wiki.hoggitworld.com/view/DCS_export`.
- `aircraft-layer/research/reference/Sim_ControlAPI.md` L548–551 groups it with `LoGetAltitudeAboveGroundLevel`/`LoGetRadarAltimeter` under the calls gated by `Export.LoIsOwnshipExportAllowed()` — **evidence: documented** (already in this repo's reference copy), consistent with the ownship-only reading.
- **Conclusion: does not fit "point query at an arbitrary grid cell ahead of the aircraft."** It reads as a radar-altimeter-like value for the aircraft's own current position only (and, per the name, counts objects/trees/buildings under it — the opposite of the "bare ground" requirement anyway). Not useful for M3's grid.

**2. `Export.LoGetAltitude` — plausibly `LoGetAltitude(x, z)`, a bare-terrain point query, but not confirmed against this install.**
- Hoggit groups it under **"Always"** (no `LoIsOwnshipExportAllowed()` gate) alongside pure utility/world functions (`LoGeoCoordinatesToLoCoordinates`, `LoGetWindAtPoint` — which itself takes a world point). `Sim_ControlAPI.md` L556–564 places it in the same ungated "always available" list. — **evidence: documented**, same two sources as above.
- Two independent old (FC2-era) ED forum threads, surfaced via WebSearch snippets (not independently re-fetched — both `forum.dcs.world` URLs returned **HTTP 403** to automated fetch this session, same site-wide block noted in prior investigator sessions), describe the signature as:
  `LoGetAltitude(x, z) -- (args - 2 : meters, results - 1 : altitude above terrain surface, meters)`
  — a world-coordinate point query returning **bare terrain surface height**, not ownship-only and not including objects. — **evidence: forum-claim-unverified**, two convergent sources, **neither independently re-read** (403'd) — source threads: `forum.dcs.world/topic/64217-generating-an-accurate-altitude-map-for-dcsfc` and a second thread surfaced the same way; titles and snippets only, via WebSearch.
- **If this signature is accurate, it is exactly the function M3 needs**, and it changes the whole shape of the feature: a bare-terrain point query, callable **directly from `Export.lua`'s own per-frame Lua state**, in the same `x`/`z` world-coordinate frame `LoGetSelfData().Position` already uses (see Finding 4) — no Hook bridge, no UDP round trip, no body-layer relay. ~18 calls/poll at a "slow poll rate" (user's own words) would be negligible either way.
- **This is the one load-bearing unresolved claim in this report.** It rests on two old forum threads neither of which could be re-read this session (403), and the function's name has not been grepped against the project's own install. **Trivially checkable, zero risk**: the function's own doc comment is almost certainly in the shipped `Scripts/Export.lua` file itself — this project already cites that exact file for `LoGetWorldObjects`'s documentation (`aircraft-layer/CLAUDE.md`'s own prior citation: "`Export.lua.reference-file-from-DCS-installation.lua` lines 624-629"). A one-line `grep -A3 "function LoGetAltitude" "<DCS install>/Scripts/Export.lua"` on the Windows box, no mission needed, settles this before Architect commits to either design fork below.

**3. Grid coordinate frame — `LoGetSelfData().Position`, x=north/y=up/z=east, heading in radians.**
- `aircraft-layer/research/2026-11-20-motion-telemetry-frames.md` L84–99 establishes (for this project's own prior probes) **x = north, y = up, z = east**, metres, the standard DCS world frame — **evidence: inferred** (by elimination/correlation against known headings, not an ED spec), already the project's working convention and already used by `send_ownship`/`flight_control.lua`'s existing `self_data.Position`/`.Heading` reads (`aircraft-layer/dcs-export/Petrobrain/telemetry.lua` L197–201, `flight_control.lua` L2483–2501).
- `self_data.Heading` is in **radians** (existing code does `math.deg(self_data.Heading)` — `flight_control.lua` L3640–3642).
- So the boresight unit vector in the (x,z) plane is `(cos(heading), sin(heading))` and the lateral (right) vector is `(sin(heading), -cos(heading))` under this convention (heading 0 = north = +x, heading 90° = east = +z) — **evidence: derived from the above, not independently flown**; sign of the lateral vector is exactly the kind of thing worth a one-line unit check against `flight_profile.lua`'s existing bank/turn-sign conventions before Architect locks the grid-cell layout in, since a sign error here silently probes behind the aircraft instead of ahead to one side.
- User's own settled simplification (`explore-notes.md`, follow-up answer 4): **use boresight as "ahead"** — no crab/drift correction. This removes any need to read `LoGetVectorVelocity`/ground track for the grid axis at all.

**4. Atmospheric visibility — `world.weather.getFogThickness()`/`getFogVisibilityDistance()`, confirmed live, but Mission-Scripting-only, never Export.lua.**
- `Export.lua` has **no** fog/visibility/cloud getter of any kind — confirmed by an exhaustive grep of the shipped reference file for `fog|visib|cloud|precip|light` (`aircraft-layer/research/2026-09-19-ed-native-detection-identification-gap-analysis.md` L259–261) — **evidence: documented** (a negative result from reading the actual shipped file, not a web claim).
- `world.weather.getFogThickness()` / `world.weather.getFogVisibilityDistance()` are real, Hoggit-documented getters (added DCS 2.9.10), but live **only in the Mission Scripting sandbox**, a separate Lua state from `Export.lua` — **evidence: documented** (Hoggit wiki fetch, same session that found the Export.lua negative).
- **Confirmed live, reproduced-locally**, a different session, through the existing Hook → `net.dostring_in("mission", …)` bridge (the same Hook-script pattern already production-proven for F10 commands via `net.dostring_in("scripting", …)`, but targeting the **`"mission"`** sandbox, not `"scripting"` — two different bridge targets, both now proven reachable from a Hook script): a real flight returned `getFogThickness() = 320`, `getFogVisibilityDistance() = 2300` — **evidence: reproduced-locally** — source: `aircraft-layer/research/2026-09-29-bridge-terrain-probe-results.md`, Finding 17.
- Fog **thickness is a vertical layer height referenced from sea level, not AGL** — two independent 2024/2016-era forum reports converge on this, plus a WebSearch-summarized "official scripting docs" citing a 100–5000 m thickness range and a clamp against cloud base — **evidence: forum-claim-unverified** (not independently re-fetched; same 403 pattern), but convergent. Practically: above the fog layer, visibility reads as unlimited; `getFogVisibilityDistance()` is the horizontal clip distance to use while inside/below it.
- **No API found that exposes *where* fog is spatially** — ED's own fog representation is a mission-wide time series (`fog2.manual = {{time, visibility, thickness}, …}`), and the project's own prior probe (`todo/backlog/X-B4`, closed 2026-10-01) explicitly flags this as the harder, unanswered half: *"Rain and clouds are not uniform in DCS... an ownship-local visibility figure is sampled in the right place but says nothing about whether the target sits under a squall."* **Decided fallback already on record**: read the ownship-local value and apply it scene-wide, stating the limitation rather than hiding it.
- **Nothing in body-layer consumes this today** — `body-layer/ROADMAP/BL-B138.md` (weather → detection-range falloff) is `#status/open`, not started; this would be the first real consumer of the getter anywhere in the codebase.

**5. The terrain grid's actual proven fallback, if `LoGetAltitude(x,z)` turns out not to exist in Export.lua: the already-flown Hook `probe_points` mechanism.**
- `plans/expected-area-look/plan.md` Stage 1 (`BL-B111`) already added a point terrain-height-plus-visibility query to the production LOS Hook (`petrobrain-line-of-sight-hook.lua`): for each of up to 6 points, `land.getHeight({x=px, y=pz})` then `land.isVisible(observer, {x=px, y=height+2, z=pz})`, fail-closed, answered over the existing 7796/7797 loopback-UDP channel.
- **Confirmed live, 2026-11-27** (`body-layer/ROADMAP/BL-B111.md`): Step 1 of the Windows card returned `clear: [true, false, true]` for three points chosen on a near slope / behind a crest / open ground — exactly the expected pattern from real `land.isVisible`/`land.getHeight`. — **evidence: reproduced-locally.** (Steps 2/4 were accepted by user assumption rather than flown, per the same entry; Step 3, paused-mission, was separately confirmed.)
- **This mechanism lives in Mission Scripting, reached via the Hook's `net.dostring_in("scripting", …)` bridge — a different `dostring_in` target from the fog bridge's `"mission"` target** (Finding 4), both already proven reachable from the same or a sibling Hook script, so one Hook poll could plausibly fetch both terrain heights and fog in the same tick if that turns out to be the needed design.
- `land.getHeight` itself is **Mission-Scripting-only**, confirmed separately (`.claude/agent-memory/investigator/project_m4_elevation_recon.md`) — not reachable from `Export.lua` directly, which is exactly why `probe_points` had to be built as a Hook-bridge mechanism rather than an `Export.lua` addition.
- A related finding worth flagging, not required for M3: `land.profile(from, to)` (Mission Scripting) returns a **whole terrain line in one call** — a flown 1 km probe returned 14 points at ~77 m spacing, in 1 ms (`aircraft-layer/research/2026-09-29-bridge-terrain-probe-results.md`, Finding 17) — cheaper than N separate `getHeight` calls for the boresight row, **but** it did not start exactly at the requested `from` (first point was 160 m in) and its spacing is mesh-resolution-driven, not the requested clean 200 m steps — would need resampling if used, and still would not cover the ±200 m lateral offset rows by itself (those would need their own `land.profile`/`getHeight` calls).

**6. The architectural fork this creates for Architect — not a detail, the central design decision.**
If `LoGetAltitude(x,z)` is confirmed to work as the forum describes (Finding 2), the entire terrain-grid read can happen **in-process, inside `Export.lua`'s own per-frame Lua state**, on its own slow timer — no round trip, no body-layer involvement, symmetrical with how `flight_control.lua` already reads `LoGetAltitudeAboveGroundLevel`/`LoGetRadarAltimeter` locally every frame.

If it is **not** available (Finding 1's ownership-gated sibling is the only ownship reading, and no Export.lua point-query exists at all), the only proven route is the Hook `probe_points`-style bridge (Finding 5) — which answers to the **collector/body-layer**, not back into `Export.lua`'s own Lua state. There is no existing direct Hook→Export.lua channel (grepped: `Export.lua`'s only inbound UDP listener is its own command channel from the collector, distinct from the Hook script's 7796/7797 socket). In that case the terrain-floor computation would need to happen in **body-layer**, reading the Hook's grid answers (and/or fog) over the LAN API, and relaying a bounded floor/limit **down** to `Export.lua` via the existing `POST /command/flight_lease`'s `limits` field — the same pattern already used for `floor_agl_m`-style bounds — rather than `flight_control.lua` polling the grid itself. This is a materially different design (who owns the computation, what latency the law tolerates, whether the "slow poll" the user accepted is ~1 Hz Hook-bridge-bound or faster in-Lua) and should not be assumed either way before Finding 2 is settled.

**7. World-model's own DEM/terrain data is the wrong source for this, and the project's own invariant already says so.**
`world-model/`'s terrain pipeline is explicitly offline/pre-built and augmentative; "DCS geometry is always authoritative, external GIS augments, never overrides" (root `CLAUDE.md`). M3's terrain floor must reflect the live simulated world under the aircraft *right now*, in the installed terrain module's own resolution — a batch-built DEM store (even DCS-derived, per `world-model`'s own M7 finding that terrain-mesh files can supply offline elevation) is a different, slower-moving, differently-registered copy of the same ground truth DCS itself can answer live. Not flagged as a live question — this is a restatement of an existing invariant, included because a planner reaching for `world-model`'s store here would be a real, avoidable mistake.

### Possible Approaches

- **Preferred, pending Finding 2's confirmation:** `Export.lua`-local polling via `LoGetAltitude(x,z)` for the terrain grid, entirely inside `flight_control.lua`'s own per-frame state, at a slow (e.g. 1–2 Hz) internal timer — no new wire protocol, no body-layer involvement, matching the user's "slow poll rate is ok" framing literally.
- **Fallback if `LoGetAltitude` doesn't fit:** extend the existing, already-flown `probe_points` Hook mechanism (Finding 5) with a grid-shaped batch (up to the Hook's own point cap, currently 6 — would need raising for 15–18 points, or splitting across polls), with body-layer computing/relaying the resulting floor via the existing `flight_lease`/`limits` channel. Costs a UDP round trip and a body-layer hop the first design avoids, but the mechanism and its "fails closed" posture are already proven in production.
- **Fog clip, either design:** read once per Hook-bridge poll (whichever cadence the terrain grid ends up using, since both are "slow" and both go through the same kind of bridge if Finding 2 fails), clip the grid's forward extent to `min(configured_max_m, getFogVisibilityDistance())`, and treat "no fog getter reachable this poll" the same fail-open/fail-closed way the rest of this project's Hook-bridge calls do (explicit decision for Architect — the LOS probe fails closed on `getHeight`/`isVisible`; whether a missing fog reading should fail open (treat as unlimited visibility) or closed (treat as the configured max, conservatively) is a real choice, not yet precedented for *this* kind of reading).
- **Do not build spatial fog modeling** — no API exposes it (Finding 4), and the project's own prior probe already settled on the scene-wide ownship-local fallback with the limitation stated. Revisiting this would be rediscovering a closed question.
