# 9K113 AI-slew-axis obedience: prior art and a leading hypothesis for the intermittent gate

**Date:** 2026-10-22
**DCS version:** 2.9.30.28738 (from the probe log headers in `docs/acceptance/2026-10-22-9k113-ai-latency-probe.md`, runs 1–8)
**Theatre:** not applicable (cockpit/device-level question, not terrain)

### Question

Under what conditions does DCS obey external writes to the 9K113's AI slew axis (`SetCommand(3061, ...)` / `SetCommand(3060, ...)` on device 7), and has anyone in the community driven the 9K113 — or an analogous AI-operated sight in another DCS module — from Lua, with documented conditions for obedience vs. ignoring?

### What the 8 probe runs already established (not re-derived here)

See `docs/acceptance/2026-10-22-9k113-ai-latency-probe.md` in full. Summary, to frame what prior art would need to explain:

- The AI axis is a **rate command** (not position, correcting the 2026-09-21 reading), gated by `axis_use_velocity=true` in `Devices_specs/9K113.lua`.
- Obedience is **intermittent and all-or-nothing per command**: short windows of 1–3 responding commands, then 4–100+ s of being ignored, **independent of boresight proximity** (run 7 refuted the earlier "near-boresight" reading).
- No cockpit arg in 0..3000 tracks the gating state. The LAUNCH PERMITTED lamp (962) and the stick-park toggle (3055) both correlate with *some* runs and are refuted or weakened by others (run 8: 42 toggles, zero effect).
- No native getter is reachable from Lua on device 7 (`SetCommand`/`listen_command`/`listen_event`/`performClickableAction` only — confirmed exhaustively, run 5).

### Findings

1. **This project's own prior `/explore` decision already names the mechanism most likely to explain the gate, and it was decided before any of these 8 runs were flown.** `docs/acceptance/2026-10-15-9k113-sight-direction.md` §6, user direction, verbatim: *"OBSERV ON only on pilot command — if OBSERV is ON, then Petrovich can use the 9K113 autonomously, like he uses binoculars."* — **evidence: documented (this project's own recorded decision)** — **source:** `docs/acceptance/2026-10-15-9k113-sight-direction.md:115-129`.

   Every probe run in the 2026-10-22 card requires OBSERV ON as setup (it is how the gyro-alignment lamp Л5/898 gets lit at all). If Petrovich's native AI logic treats "OBSERV is ON" as license to use the 9K113 autonomously — exactly as decided — then **the native AI and the probe's external `SetCommand` writes are two independent writers to the same device**, and whichever one the engine applies last on a given frame wins. That produces exactly the observed signature: all-or-nothing per step (a whole command either lands or is overwritten the same frame, every frame, for the duration of one "episode"), no cockpit arg tracking it (the native AI's internal scan/dwell state machine is not exposed to Lua at all — confirmed in run 5's exhaustive device-method enumeration), and no correlation with boresight (an autonomous scan sweeps the whole FOV, not just near centre). This has **not** been tested directly against the logs — see "Possible Approaches" / cheapest test below.

2. **Eagle Dynamics has publicly documented, in an official newsletter, that Petrovich's native AI actively slews the sight's FOV as background behaviour when not given an explicit order.** Quoted verbatim from the fetched newsletter: *"Petrovich AI will move his Field Of View (FOV) in different directions to scan for potential threats"*, part of "threat awareness and idle mode behaviour," gated by background activity ("when not busy blowing stuff up with ATGMs"). — **evidence: documented (ED's own newsletter, but gameplay-level language, not source-level)** — **source:** `https://www.digitalcombatsimulator.com/en/news/newsletters/f8e32e08192f89a9c593861366a211b2/` (fetched successfully, unlike forum.dcs.world). This independently corroborates finding 1 from ED's side rather than the user's: the native AI really does drive the sight's direction on its own, unprompted, as a documented feature — not a bug being worked around.

3. **No one in the DCS community has published a working Lua/Export recipe for driving the 9K113's (or any AI-operator sight's) axis externally, and no one documents an obedience condition for `SetCommand` against an AI-owned device.** Searched: ED forums (`forum.dcs.world`) via WebSearch (direct `WebFetch` 403'd on every thread tried — see below), Hoggit wiki (no hits for `GetDevice`/`SetCommand`/AI-priority terms), GitHub (`DCS-Skunkworks/dcs-bios` — no Mi-24P 9K113 module found; a code search for `av9K113`/`isCaged`/`getSightAzimuth` returned nothing on GitHub), r/hoggit (search engine returned only `forum.dcs.world` threads, no Reddit hits). — **evidence: absence is itself the finding (negative search), confidence: medium** — this is a genuinely unexplored corner of the community's scripting knowledge, not a solved problem we failed to find.

4. **George AI (AH-64D) and Jester AI (F-14) are the module-specific names for the same "AI copilot operates a device" pattern**, confirmed to exist by forum consensus (*"George is commanded through various simple 'AI' interfaces... George AI, Petrovich AI, and Jester AI are the implementations for the Apache, Mi-24, and F-14"*), but **no example was found of anyone driving George's or Jester's controls from `Export.lua`/`GetDevice`/`SetCommand`** — the one on-topic project found (`forum.dcs.world/topic/339243`, "LuaMoose class ApacheGeorgeAI") builds on MOOSE mission-scripting (group/task level), not device-level `SetCommand`, and could not be read past the WebSearch snippet (403 on direct fetch). — **evidence: forum-claim-unverified** — **source:** `https://forum.dcs.world/topic/339243-luamoose-class-apachegeorge-ai/` (403'd; snippet only, via WebSearch).

5. **Community forum threads independently describe the 9K113's gyro-stabilized sight losing/regaining responsiveness, but at the maneuver/alignment level, not the external-command level** — consistent with, and not contradicting, this project's own findings:
   - Gyros "topple" and the sight must be closed above roughly 30° bank / 60° turn rate, with realignment taking several minutes if genuinely toppled (distinguish from the probe's observed ~10–13 s gyro-alignment-after-OBSERV-ON delay, which is a different, much shorter event, confirmed directly in this project via Л5/arg 898 in run 7/7b/8). — **evidence: forum-claim-unverified** — **source:** WebSearch snippets of `forum.dcs.world/topic/335694`, `/topic/282320`, `/topic/274749` (titles: "29 — Peterovich AI cannot correctly identify the target", "reset ATGM gyros in flight", "question about the optical sight stabilisation"); all three 403'd on direct `WebFetch`.
   - A developer comment (relayed secondhand on the forum, not independently verified) describes the sight as "meant to be stabilized relative to the ground... with a fix planned to make it hold its aim during maneuvers below a certain turn rate" — consistent with this project's own confirmed gyro-world-hold finding (runs 2/3/5/6), but gives no information about external-command obedience. — **evidence: forum-claim-unverified**.

6. **`list_indication(10)` (the AI command wheel, confirmed readable in `mi24p-command-surface.md` §5) already exposes Petrovich's own state as text — `SEARCHING` / `TRACKING` / `WAITING`.** This channel has never been logged alongside an AI-axis probe run. If finding 1's hypothesis is right, this text should visibly change (e.g. to `SEARCHING`) during exactly the windows the AI axis is ignored. — **evidence: documented (already-confirmed read channel, not yet cross-correlated)** — **source:** `aircraft-layer/research/mi24p-command-surface.md:364-421`.

None run in this session (recon only). The cheapest test to confirm/refute finding 1 is below.

### Possible Approaches

Ranked by cost, cheapest first — all are things Architect/the next probe run should weigh, not a decision made here:

1. **(Cheapest — no new probe, reread existing logs) Check whether `list_indication(10)`'s state text was already being logged in any of runs 1–8.** It was not part of the `WATCH_ARGS`/lamp set in any run's card (`docs/acceptance/2026-10-22-9k113-ai-latency-probe.md` never mentions it), so this is a pure addition, not a reanalysis. If it isn't in the existing logs, this becomes a run-9 line item: add `list_indication(10)` to the per-frame log and look for `SEARCHING` coinciding with ignored windows and `WAITING`/no text with obedient windows.
2. **Test the OBSERV-autonomy hypothesis directly: run the azimuth-only probe (run 2/3's script) a second time with OBSERV left OFF the whole flight**, if the sight can be commanded via the AI axis at all with OBSERV off (gyro alignment may require it — unverified). If the gate disappears or changes character with OBSERV off, that is strong confirmation; if the gate persists identically, finding 1's hypothesis is weakened (though a residual "Petrovich always watches when the sight is powered" background mode is still possible per ED's newsletter wording "when not busy... searching for targets").
3. **Ask the user directly** (pilot already answered several of these verbatim in the acceptance card) **whether giving Petrovich an explicit order first (e.g. `HOLD FIRE` or any wheel command that puts him into a named state other than idle) changes the gate's character** — the design decision in §6 only says OBSERV-on licenses autonomy "like binoculars"; it does not say whether an explicit order suppresses that autonomy the way it would for a human operator handing control back. This is a question only the pilot/designer can settle, not a probe.
4. **If 1–3 together show the native AI is indeed the second writer**: the fallback this project would need is not "fix" the gate (it's native-code behavior, out of bounds to patch — licence), but **architectural**: either (a) treat the AI axis as cooperative rather than authoritative — poll 565/566 (the real ASP-17 mark, confirmed in runs 2–5) and only claim the slew succeeded when it visibly moved, retrying/backing off rather than assuming a single write lands, or (b) find and command whatever native state switches Petrovich out of autonomous idle (an explicit wheel order, is the current best candidate per item 3) before relying on the AI axis for anything time-critical like BL-B67's ATGM run.
5. **No community prior art exists to lean on (finding 3)** — if the gate is confirmed to be native-AI contention, this project would be first to document a workaround, so whatever is found should go into `mi24p-command-surface.md` §4.2 as new ground truth, not just into this dated note.
