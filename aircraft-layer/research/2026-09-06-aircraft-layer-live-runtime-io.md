# Aircraft Layer: Live-Runtime DCS I/O (Export environment, DCS-BIOS, commanding, LAN transport)

**Date:** 2026-09-06
**DCS version:** not verified locally — this investigation is desk research (Hoggit wiki, ED forums, GitHub) plus general architecture knowledge; no probe was run against the installed DCS instance on the Windows box. See "Unresolved" for what still needs a hands-on run there.
**Theatre:** not applicable (runtime I/O question, not terrain-specific)

### Question

What does DCS World actually let a separate, LAN-connected process (the planned Mac-side Petrobrain brain) do *during a live mission*: read aircraft kinematic state, cockpit switch/instrument state, and sensor contacts; and send commands back (switches, controls, or higher-level actions)? What's the real process/sandbox architecture, and which existing community tools already solve the transport problem? This determines the shape of the aircraft-layer plan (process boundary, transport, data model, command surface) that Architect needs to write next.

### Findings

**1. Export.lua exists and is a live, callback-driven, ownship-scoped API**
- Confirmed via GitHub example scripts (`jboecker/dcs-export-core`, `sprhawk/dcs_scripts`) and Hoggit wiki (`DCS_export`, `DCS_Export_Script`) — **evidence: documented**.
- Lifecycle callbacks: `LuaExportStart()` (once, before mission start), `LuaExportBeforeNextFrame()` (every sim frame, pre-frame), `LuaExportAfterNextFrame()` (every sim frame, post-frame, for reading state), `LuaExportStop()` (once, on mission end) — **documented**.
- The real file lives at `Saved Games\DCS\Scripts\Export.lua` (user-writable; the read-only copy under the install tree at `Scripts\Export.lua` is the stock/reference version) — **documented**.
- This runs **per DCS client install**, not per mission — i.e. it is not sanitized/reset the way Mission Scripting trigger code is, and it is active regardless of which mission is loaded (it just has nothing meaningful to export before a mission starts) — **documented, moderate confidence** (Hoggit wiki phrasing; not independently reproduced this session).
- Ownship data functions confirmed present: `LoGetSelfData` (full self state, explicitly *not* gated by the anti-cheat/labels setting — this is called out specifically in Hoggit docs as a contrast to other functions), `LoGetADIPitchBankYaw` (pitch/bank/yaw), `LoGetMagneticYaw`, `LoGetAltitudeAboveSeaLevel`/`LoGetAltitudeAboveGroundLevel`/`LoGetRadarAltimeter`, `LoGetTrueAirSpeed`/`LoGetIndicatedAirSpeed`/`LoGetVectorVelocity`/`LoGetVerticalVelocity`, `LoGetEngineInfo`, `LoGetPayloadInfo`, `LoGetMechInfo` — **evidence: documented** (Hoggit wiki `DCS_export`). This directly satisfies the "pitch/bank/yaw/heading/speed/alt" part of the aircraft-layer's stated inputs.
- `LuaExportActivityNextEvent` lets the script schedule its own next callback at an arbitrary future model-time instead of running full-rate every frame — this is the documented mechanism for throttling export/network load rather than a hard frequency cap — **documented**.
- **Evidence gap:** no source found stating an explicit polling-rate ceiling (e.g. "max 20 Hz"); the practical ceiling is simulation frame rate (typically 30–90+ Hz) unless throttled via `LuaExportActivityNextEvent`.

**2. Export.lua ships with LuaSocket and unrestricted io/lfs by default — it is NOT the same sandbox as Mission Scripting**
- The stock Export.lua template includes worked TCP client/server examples (`Listener.lua`/`Talker.lua` pattern) using `socket = require('socket')`, and DCS ships LuaSocket 2.0 binaries specifically for this purpose under `Scripts/LuaSocket` — **evidence: documented** (Hoggit `DCS_Export_Script`).
- `io.open()` and `lfs` are usable from Export.lua without any edit — **documented**.
- This means the `MissionScripting.lua` sanitization edit already made for World Model Builder probes (`world-model/research/2026-09-03-m4-elevation-recon.md`) is **irrelevant to Export.lua** — that edit desanitizes the per-mission trigger/Mission Scripting environment (`os`/`io`/`lfs`/`require` disabled by default there for anti-cheat/anti-malware reasons because mission files are untrusted and shared over the internet). Export.lua is a separate file, loaded from the user's own `Saved Games` folder (trusted, local), and was never sanitized in the first place — **evidence: documented, inferred conclusion from combining two documented facts**.
- Practical implication: Export.lua can open a raw TCP or UDP socket to a LAN host directly, no proxy/bridge/file-polling needed, and no client-side edit beyond writing to `Saved Games\DCS\Scripts\Export.lua`.

**3. DCS-BIOS is a separate mechanism from Export.lua/LoGetSelfData, and it IS bidirectional**
- DCS-BIOS is *itself implemented as* an Export.lua script — it exports **cockpit control/indicator state** (switch positions, gauge needle values, indicator lights) via the clickable-cockpit "arg" mechanism, not via `LoGetSelfData`/kinematic functions — **evidence: documented** (DCS-Skunkworks developer guide).
- It is bidirectional: an external process can send newline-terminated plain-text commands (`CONTROL_ID VALUE\n`) to manipulate cockpit controls — confirmed via the developer guide's command-channel description — **documented**.
- Transport: UDP multicast `239.255.50.10:5010` on loopback by default for export data, configurable unicast UDP, and TCP port 7778 for commands+export together; serial bridging exists via `socat`/DCSBIOSBridge for hardware panels — **documented**. All of these are LAN-reachable if the multicast/unicast target is pointed at the Mac's IP instead of loopback (multicast needs the router/switch to pass it, or unicast avoids that entirely).
- **Conclusion for the aircraft layer:** DCS-BIOS and Export/`LoGetSelfData` are two *complementary, not overlapping* mechanisms. The aircraft layer's stated requirement ("switch positions AND pitch/bank/yaw/heading/speed/alt AND sensor contacts") needs **both**: kinematic/attitude state comes from a custom Export.lua script using `LoGetSelfData`-family calls; switch/indicator state comes from DCS-BIOS (or a hand-rolled equivalent reading the same clickable-cockpit arg values, since DCS-BIOS is itself just an Export.lua script — nothing stops writing one script that does both).

**4. Mi-24P DCS-BIOS support: exists, but completeness is unverified/likely partial**
- GitHub issue `DCS-Skunkworks/dcs-bios#571` ("Mi-24 collective") exists and was opened 2024-04-21 — its mere existence confirms a Mi-24(P) module definition is present in DCS-BIOS's `aircraft_modules`, since a per-control bug report presupposes the module exists — **evidence: forum/GitHub-claim, weakly verified** (issue's title/existence confirmed; full issue body failed to load twice via WebFetch, so the specific nature of the collective-control defect is unconfirmed).
- No official aircraft-module completeness list was retrievable this session (control-reference.html landing page doesn't enumerate modules; needs to be opened live in DCS/DCS-BIOS install to see the actual generated module list) — **unresolved, needs local check** (see below).
- Mi-24P is a third-party (Eagle Dynamics in-house, but a " study-level-ish" and comparatively niche) module; DCS-BIOS coverage for niche modules is typically maintained by community volunteers and often lags flagship modules (A-10C, F/A-18C, F-16C) in completeness — **inferred, general community pattern, not Mi-24P-specific verification**.

**5. Sensor contacts: no evidence of a genuine "what does this aircraft's sensor currently detect" export — LoGetWorldObjects/LoGetTargetInformation are the wrong tool, and DCS-BIOS maintainers explicitly decline to add this**
- `LoGetWorldObjects` returns coalition-scoped(?) ground-truth object data (position, heading, country, coalition) for objects in the mission — it is *not* documented anywhere found as being filtered by what any particular aircraft's sensors have actually detected — **evidence: documented that the function exists and returns broad object data; the detection-filtering question is forum-claim-unverified** (a 403-blocked ED forum thread `forum.dcs.world/topic/133284-logetworldobjects` likely discusses exactly this — blocked by WebFetch, not independently confirmed this session; user should paste its content if this needs firming up).
- `LoGetSelfData` is explicitly documented as "not dependent on anti-cheat setting" — the wording implies, by contrast, that *other* world-object-visibility functions ARE gated by DCS's anti-cheat/labels-and-visibility mission-difficulty settings, which is a separate axis from "did this specific aircraft's sensor detect this contact" — **inferred from documented wording, not independently reproduced**.
- `LoGetTargetInformation`/`LoGetLockedTargetInformation`/`LoGetTWSInfo` are legacy functions scoped to **FC3 (Flaming Cliffs 3) modules' radar/TWS systems** — a DCS-Skunkworks maintainer stated in GitHub discussion #1217 that these functions "are generally for the FC3 modules," that modern/third-party modules often don't populate them, and explicitly: **"we don't normally export these sorts of things"** regarding raw sensor/radar detection state, further noting that with modern radar modeling "it's not even guaranteed what you're tracking is an actual target" — **evidence: documented** (maintainer statement in a public GitHub discussion, strong-but-not-primary-source evidence).
- The same discussion's recommended workaround for anything RWR/sensor-display-like is **Helios** — i.e. exporting/rendering the actual in-cockpit MFD/RWR display image and reading it visually (screen-scrape / pixel-level approach), not structured contact data — **documented**.
- Net conclusion: **PETROBRAIN_SYSTEM.md's anticipated fallback is correct and is the only realistic path.** There is no confirmed API that hands back "what Petrovich/the Mi-24P's sensors currently perceive" as structured data. The only two realistic approaches are (a) pull `LoGetWorldObjects` ground truth and apply an external geometric/range/LOS/RWR-envelope heuristic filter (visibility, terrain masking via the World Model's elevation data, sensor cone, detection range by contact type) to approximate what the crew could plausibly perceive, or (b) attempt a Helios-style visual read of the actual in-game optical/thermal sight or RWR display, which is far more complex and almost certainly out of scope for this phase.

**6. Commanding DCS beyond switches: no evidence of direct flight-control state injection via Export.lua**
- Export.lua's `LuaExportBeforeNextFrame` is documented as usable "for input commands," but every example found in the community scripts is about **timing** (deciding when to sample/send), not about **injecting control axis values (cyclic/collective/pedals) directly** — no `LoSetCommand`-equivalent for raw flight control surfaces was found documented anywhere in this session's research — **evidence: absence of evidence, not a confirmed negative; flagged as unresolved**.
- The two confirmed command surfaces are: (a) DCS-BIOS's plain-text command channel, which manipulates **cockpit controls** (i.e. moves the same clickable-cockpit "arg" a mouse click would move — switches, levers, and yes, this includes cyclic/collective/pedal trim-type controls *if* the module exposes them as DCS-BIOS controls) — this is the realistic path for "flight control input," working through the cockpit rather than around it; and (b) DCS-gRPC / Olympus-style **Hook-script** environments (`Scripts/Hooks/*.lua`), which run in a different, more privileged scripting context available to a locally/server-run DCS instance and can call broader mission-scripting-equivalent functions (spawn, teleport, trigger actions) but are oriented at *mission/world* manipulation (spawning units, moving AI-controlled groups) rather than *player-aircraft flight-control* injection — **documented for DCS-gRPC's own use case, inferred as not fitting "manipulate own aircraft's flight controls smoothly"**.
- Practical implication for the "pitch/bank/yaw control direct input" item marked "defer" in `division-or-responsibility.md`: the state of the art among reviewed community tools is command-through-cockpit-controls (DCS-BIOS-style), not a raw control-surface API. This is consistent with the project's own decision to defer flight-control manipulation.

### Reproducible Test

None of this session's findings were reproduced against the installed DCS instance — the Windows DCS box was not reachable from this session (Mac-only tools: WebFetch/WebSearch). No probe script was written this session because every question here is answerable in principle by *reading* already-existing scripts/docs rather than needing a bespoke probe — except where flagged "Unresolved" below, which does need a live run.

The one exception worth calling out: verifying steps 1–3 (that `Saved Games\DCS\Scripts\Export.lua` can open a real LAN TCP socket and stream `LoGetSelfData` + attitude data every frame to a listener on the Mac) is a **cheap, ~30-minute hands-on probe** on the Windows box:
1. Copy DCS's own `Scripts/Export.lua` template LuaSocket example (`Listener.lua`/`Talker.lua` pattern referenced in Hoggit `DCS_Export_Script`) into `Saved Games\DCS\Scripts\Export.lua`.
2. Point it at the Mac's LAN IP and a free port.
3. Run `nc -l <port>` (or a 5-line Python socket listener) on the Mac.
4. Start any Mi-24P mission (even the default training mission), confirm data arrives at real-time rate.
5. Separately check `Saved Games\DCS\Scripts\DCS-BIOS\lib\modules\aircraft_modules\` (or equivalent path for the installed DCS-BIOS version) for a Mi-24P `.lua` file, and open `control-reference.html` with the Mi-24P loaded to see the actual generated control list and judge switch-coverage completeness.

This is exactly the kind of probe the `wsl-probe-sync` skill is set up to shuttle to/from the Windows box.

### Possible Approaches

- **Minimal viable transport (recommended starting point):** a hand-written `Saved Games\DCS\Scripts\Export.lua` using `LoGetSelfData`/`LoGetADIPitchBankYaw`/altitude/airspeed calls, serialized (JSON via a small pure-Lua encoder, or a simple delimited text line) and pushed over a raw UDP or TCP socket via LuaSocket to the Mac, at a throttled rate via `LuaExportActivityNextEvent` (e.g. 10–20 Hz, well under frame rate, plenty for crew-cognition purposes which don't need flight-control-loop rates). This directly satisfies kinematic/attitude/altitude/speed requirements with no new dependency and no `MissionScripting.lua` edit.
- **Switch/indicator state:** either adopt DCS-BIOS wholesale (if Mi-24P coverage proves adequate on the hands-on check) and consume its UDP export + command channel from the Mac, or extend the same custom Export.lua script to also read the specific clickable-cockpit "arg" values the Mi-24P model exposes (DCS-BIOS's own source for the Mi-24P module, if it exists, is the fastest way to discover which arg numbers matter — reuse it as a reference even if not reusing the runtime).
- **Commanding:** route all cockpit-state changes through DCS-BIOS's command channel (or a hand-rolled equivalent using the same clickable-cockpit "perform_click"-style Lua calls DCS-BIOS uses internally) — i.e. "body" layer commands look like cockpit-switch actuations, matching `division-or-responsibility.md`'s own stated model ("body translates brain intent to switch/instrument actions"). Direct flight-control-axis injection remains unresolved/unsupported by anything reviewed and should stay deferred, consistent with the existing plan.
- **Sensor contacts:** implement the anticipated fallback explicitly — pull `LoGetWorldObjects` (or a Hook-script/mission-scripting equivalent for broader mission truth if needed) and run it through a detection-approximation filter built from World Model data already proven in M4/M6 (line-of-sight via elevation, terrain masking, plausible visual/optical range by target size and Mi-24P sensor type, time-of-day/weather if available). This is squarely "body layer" work per `division-or-responsibility.md`'s own architecture, not something to expect DCS to hand over pre-filtered.
- **Process boundary:** given Export.lua ships LuaSocket and needs zero MissionScripting.lua edits, the simplest architecture is: DCS process → Export.lua (in-process Lua callback, socket client or server) → LAN socket → Mac-side aircraft-layer process. No file-polling, no Dropbox-symlink workflow needed for this — that workflow should be understood as strictly for *offline* World Model extraction, not live telemetry, confirming the calling Architect's suspicion.
- If DCS-BIOS's Mi-24P coverage turns out to be too thin, a fallback within the same architectural family is to fork/extend a DCS-BIOS-style module definition for Mi-24P rather than inventing a new protocol — the wire protocol and command-channel design are already proven at scale across dozens of other modules.
