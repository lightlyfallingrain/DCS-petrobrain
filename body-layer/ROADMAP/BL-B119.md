# BL-B119 — `altimeter_qnh_sync`'s QNH clamp holds NaN/Infinity safely only by accident

- [ ] **BL-B119 — `start_altimeter_qnh_sync`'s `_clamp(qnh_mmhg, 670.0, 790.0)` is not documented or
  tested against a non-finite `qnh`, and the fact that it stays bounded anyway is an accident of
  Python's `min`/`max` argument order, not a designed guard.** #status/open

  Found 2026-11-16, `[[BL-B118]]` security deep analysis (`plans/bl16-qnh-mission-start/
  security.md`).

  `_clamp(value, lo, hi)` is `max(lo, min(hi, value))`. For `value = float('nan')`:
  `min(hi, nan)` returns `hi` (Python's `min(a, b)` keeps `a` unless `b < a`, and every comparison
  with NaN is `False`), so the result is `hi` (790.0) — bounded, not NaN-propagating, but only
  because `hi` is the clamp's *first* argument to `min`. `+inf`/`-inf` both clamp correctly too
  (`+inf` → 790.0, `-inf` → 670.0), verified directly (`min(790, float('inf'))`/`min(790,
  float('-inf'))` and the follow-on `max`). **Nothing in the module asserts this; it falls out of
  the specific `max(lo, min(hi, value))` argument order, which is not `min(lo, max(hi, value))` or
  any other equally-plausible rewrite that would NaN-propagate instead.** Same shape as the
  already-documented `position_belief.py`/`clamp_fold_displacement` incidental-guard pattern
  (`.claude/agent-memory/security/project_nan_comparison_incidental_guards.md`): "a comparison that
  happens to be False for NaN followed by a further false branch," not an `math.isfinite` guard by
  design.

  **Why this is low severity, not blocking**: a non-finite `qnh` can only reach
  `_maybe_start_altimeter_qnh_sync` by evading `isinstance(event_qnh, bool) or not isinstance(
  event_qnh, (int, float))` (NaN/Infinity *are* `float` instances in Python, so this check does not
  reject them — this is itself worth noting, not a gap in that check's stated contract, which is
  type, not finiteness) and by not being produced by the normal DCS mission-weather model (a
  mission file would have to set `env.mission.weather.qnh` to a literal NaN/Infinity, which the
  mission editor UI does not offer). Even if it happened, the clamp result stays inside
  `[670.0, 790.0]` and the closed loop's own iteration/duration bounds and `ALTIMETER_QNH_MAX_STEP`
  clamp (confirmed in the deep analysis, both branches, Reviewer's own re-review) still hold — no
  runaway write, no crash, no NaN written to the cockpit.

  **Fix, when touched next**: add `math.isfinite(qnh_mmhg)` to `start_altimeter_qnh_sync` (treat a
  non-finite `qnh` the same as a missing one — clear to `None` rather than clamp) or at minimum a
  one-line comment + a direct test (`start_altimeter_qnh_sync(float('nan'), ...)`,
  `start_altimeter_qnh_sync(float('inf'), ...)`) documenting that the clamp's NaN/Infinity
  behaviour is asserted, not coincidental. Low probability × low impact — not fixed in `[[BL-B118]]`
  itself; filed per this review's own "every finding gets an ID or an explicit refusal" rule rather
  than left in prose.
