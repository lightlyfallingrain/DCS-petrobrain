# BL-B133 — Petrovich does not start talking while the player keys ICS or RADIO

- [x] **Petrovich does not start talking while the player holds the ICS or RADIO trigger.** #status/done #needs-flight Merged to main 99820e66 (branch feature/bl-b133-ptt-speech-hold, 2026-11-24). Filed 2026-11-20 by user direction, to do after the 2026-11-20 BL-16 flight-mode fixes: *"when player presses ICS / RADIO trigger, while either is pressed, Petrovich does not start talking. This prevents him speaking while I'm speaking."* The trigger state already exists on the wire: `aircraft-layer`'s `GET /ptt/latest` (`schema/ptt.py`) carries both seats' triggers (args 738 and 856) as an OR, `intercom`/`radio`; its one consumer today is `audio-adapter`'s `ptt_source.py`, and body-layer does not read it. Shape to decide at build time: hold the start of a new utterance (the `SpeechWorker` queue or `CrewConsole._print`'s gate, beside the existing SPU-8 intercom hold) while either trigger is down; the two-stage trigger's 19-32 ms intercom transit on a full pull needs the same debounce `ptt_source.py` already applies. **Decided 2026-11-20** (user, verbatim): *"1 - say urgent ones even when I hold trigger 2 - let it play"*. So urgent lines (`urgent=True`, e.g. a forced "You have controls!") are never held; a line already playing when the trigger goes down plays to the end. Only the *start* of a routine line waits.

  **Built** (`plans/bl-b133-ptt-speech-hold/implementation.md`): the actual wire endpoint is
  `GET /ptt/state` (the item's own "`GET /ptt/latest`" names the shape, not the real route —
  `aircraft_client.AircraftLayerClient.get_ptt_state_latest` is the new client method). The hold
  lives in `belief.speech_worker.SpeechWorker._run`/`_wait_for_ptt_release`, not `CrewConsole.
  _print` — `_run` is already the one place that decides *when* a queued line's `push_speech` call
  actually starts, on its own background thread, so blocking there adds no change to `_print`'s
  synchronous `enqueue` contract and blocks neither the poll thread nor whichever thread calls
  `_print`. The hold/debounce/staleness decision itself is `belief.ptt_hold.PttHoldGate.is_held()`,
  a new module. Two new tunables (`belief.ptt_hold.PTT_RELEASE_DEBOUNCE_S` = 0.1s,
  `PTT_FEED_STALE_AFTER_S` = 120s, both `status="agreed-guess"`) through `tuning.py`, regenerated
  into `config/defaults.toml`. An urgent arrival (`interrupt()`) now also wakes a routine item still
  waiting on the gate, so it is dropped rather than delaying the urgent line behind it.

  **Review fixes** (`plans/bl-b133-ptt-speech-hold/review.md`, both REQUIRED, now resolved): (1)
  staleness was originally keyed to the PTT sample's own `received_wall_clock_s`, which ages
  identically for a genuinely held trigger (send-on-change `Export.lua` line) and a dead collector
  — now keyed to `GET /telemetry/latest`'s own freshness instead (sent every tick regardless of PTT
  value; `body.py`'s poll loop already reads it, no second request), and `PttHoldGate.reset_for_
  new_mission()` is also wired into `body._reset_mission_state` so a genuine DCS mission (re)start
  clears a stuck `held=True` state at the actual lifecycle event. (2) a real race in `SpeechWorker.
  _wait_for_ptt_release`: an `interrupt()` landing between `_run` dequeuing a routine item and the
  wait actually starting could be silently lost (confirmed by direct repro) — `_gate_wait_active`/
  `_gate_wait_superseded`, both lock-protected and scoped to exactly one item's wait at a time,
  replace the bare `Event`'s clear-then-check as the source of truth.

  The hold/debounce/staleness logic is directly tested (a controllable fake gate for
  `SpeechWorker`, a real loopback server plus fake clocks for `PttHoldGate`); whether the debounce
  window and the 2-minute telemetry-staleness bound feel right in the cockpit — in particular, a
  long radio call during which telemetry itself also happened to stall past 2 minutes would let
  Petrovich start talking over it by design (see `belief.ptt_hold`'s own module docstring for the
  tradeoff) — is unverified and will need `#needs-flight` once merged.
