  **Why it earns a milestone**: today a mission reload inside one service run carries the previous
  mission's whole belief into the next one (`[[BL-B68]]`, diagnosed 2026-10-15), and the only
  workaround is restarting body-layer between missions. Petrovich reporting contacts from a mission
  that no longer exists is the clearest possible break of "never omniscient". Stage 2 then closes
  the gap between the Mission Interpreter, which is done (`MI-0`–`MI-6`), and a sortie, where
  nothing runs it unless the user does so by hand.

  ## Stage 1 — clean slate and theatre

  - **Detection — DECIDED 2026-10-19: the Hook's `onSimulationStart`.** User: *"onSimulationStart
    is good for mission start detection."* Not `t_sim` going backwards (the false-reset risk below).
  - **Reset belief** — every item in `[[BL-B68]]`'s "Everything that carries over" table, not just
    `ContactStore`. That table is the checklist; a reset that clears contacts alone leaves the
    quieter bugs it names (a live `attack_run_state` on a stale target id, a carried-over
    `scan_plan`, both perception sources' dedup maps).
  - **Reset mission memory** — `body-layer/src/mission_memory/` (`[[BL-8]]`), so nothing from
    the previous mission can be recalled in this one.
  - **Theatre** — read the theatre from the running mission and point world-model queries at that
    theatre's store. Today `logger.py` derives theatre/store from a loaded mission-understanding
    artifact, with a mismatch guard (root `ROADMAP.md`, multi-theatre row); this makes the live
    mission the source instead of whatever the operator passed in.

  ## Open questions, for `/explore` and the investigator — not answered here

  - **Which detection signal.** Candidates already in the codebase or research: the Hook's
    `onSimulationStart` callback, which the F10 menu Hook already uses to re-register per mission
    (`[[BL-B7]]`; `aircraft-layer/research/2026-09-13-f10-radio-menu-command-input.md`), and a
    backward jump in `t_sim`, which is how the `[[BL-B68]]` diagnosis spotted the reload.
    `[[BL-B68]]` already warns that `t_sim` going backwards may also fire on a pause, a time-accel
    change or a reconnect — and **a reset that fires mid-flight wipes real belief, which is worse
    than the bug it fixes.** An explicit signal from aircraft-layer is likely more trustworthy, but
    it means changing more than one subproject.
  - **Where the theatre and mission filename come from** (Hook API, mission scripting environment,
    or the export stream) — unverified, so it goes to the investigator before a plan depends on it.
  - **What "cached" is keyed on** — the file path alone goes stale when the author edits the
    mission and keeps the name; a content hash does not.
  - **Interpreter run time against when the pilot needs it.** If an interpretation takes minutes,
    "briefing ready" may arrive after take-off; that decides whether this is useful in flight or
    only on a cold start.
  - **Who runs the interpreter**, given the compute split (DCS on Windows, models on the Mac) and
    the module-independence rule: body-layer calling mission-interpreter over HTTP, or a separate
    process watching for the mission-start signal.
  - **What "briefing ready" leads to.** Today nothing in flight reads mission phase (`[[BL-W19]]`,
    deferred to the brain), so the pilot should get something they can use after hearing it.
