# BL-B122 — A rejected/failed `ai_pilot_goal` write is marked sent and never retried

- [ ] **BL-B122 — `body.py`'s `_apply_ai_pilot_wheel_goal` advances `runner.ai_pilot_goal_
  last_sent_seq` even when `aircraft_client.write_ai_pilot_goal` raised `AircraftLayerError`,
  so a goal that failed to transmit (collector hiccup, LAN blip, aircraft-layer restart) is
  treated as delivered and is not retried on a later poll.**
  #status/open Filed 2026-11-17 during BL-16 Stage P2 (`feature/bl16-p2-voice-goals`) DoD, from
  Security's deep-analysis finding (`plans/flight-control/security-p2.md`), not blocking that
  merge per the main loop's recommendation.

  **What it is.** `body.py`, `_apply_ai_pilot_wheel_goal`:

  ```python
  try:
      aircraft_client.write_ai_pilot_goal(...)
  except AircraftLayerError:
      logger.warning("ai-pilot-goal write failed (continuing)", exc_info=True)
  runner.ai_pilot_goal_last_sent_seq = final_goal.goal_seq
  ```

  The seq bump happens unconditionally, outside the `try`. The "send on change" guard
  (`final_goal.goal_seq != runner.ai_pilot_goal_last_sent_seq`) compares against this same
  field, so once it is advanced past a failed attempt, nothing re-triggers a resend for that
  `goal_seq` — the same bug shape in `write_ai_pilot_goal`'s `hvrt_step` branch just below
  (`runner.ai_pilot_goal_last_sent_seq = bumped_seq`, also unconditional).

  **Concretely**: the pilot speaks "heading 090", the readback is spoken immediately on
  acceptance (per `plans/flight-control/plan.md`'s Readbacks section — readback is not gated on
  the write succeeding), but the `POST /command/ai_pilot_goal` to aircraft-layer fails once
  (collector restart, LAN drop). The heading goal is now silently stuck: `active_param` stays
  `"heading"` in body-layer's own belief, Lua never received the command so it never reports
  `"settled"`, and — when heading is the *only* outstanding goal — no rotation ever fires
  (Stage P2's own rule: "when only one parameter is outstanding, no slice limit applies"), so
  there is no second attempt until the pilot either repeats the command or speaks a *different*
  target for the same parameter (which replaces in place and resends immediately, per the
  Co-moving Fields table). A multi-goal session self-heals sooner, since rotation re-promotes
  and resends on every slice boundary regardless of prior send state.

  **Why this did not block the P2 merge:** the failure window is a transient LAN/collector
  condition, not a normal-flight path — every full-suite test run and the three subprojects'
  own fast/full suites pass clean against the ordinary (non-failing) write path, and the pilot
  retains a recovery action (repeat or replace the goal) once they notice nothing is happening.
  It is not silent in the sense of giving a false "done" signal: the readback already said what
  was *heard*, not what was *achieved*, matching this project's existing E-P3/E-P4 posture of
  never narrating settlement.

  **What would close it.** A small design choice, not just a one-line fix: naive
  "retry every poll on failure" would hammer a genuinely down aircraft-layer every ~0.2s with no
  backoff; naive "never retry" is the status quo. The shape to build: retry on a *transient*
  `AircraftLayerError` (connection refused/timeout — the collector-hiccup case), but surface
  "unable" once and stop retrying on what reads as a *permanent* rejection (a malformed request,
  a 4xx the collector itself returned) rather than polling it forever. Needs a decision on
  which `AircraftLayerError` subtypes/attributes distinguish the two before implementation.
