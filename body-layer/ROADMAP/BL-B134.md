# BL-B134 — One readback rule for every command: "stand by", then confirm on execution

- [ ] **Every command readback follows one rule: "stand by" when accepted but not yet acting, the confirmation when it actually executes, "unable" only when it cannot be done.** #status/open Filed 2026-11-23 by user direction, from the LV-0 sortie (`docs/acceptance/2026-11-23-sortie-feedback.md`): "turn heading 000" got "unable, not ready" and the aircraft turned 2 s later. User, verbatim: *"Expected: not "unable" if able, if just needs to wait a little. "Unable" only when action is not possible (currently)."* Then, on what to say while a command waits: *"if unable to act immediately, but command was accepted -> "stand by"; command confirmation on command execution. This is the general rule for readback that should apply to any command readback (own BL item about making it work everywhere)."* So: accepted and acting at once → the readback as now; accepted but waiting (Lua ack pending, an effector sequence still running, a busy scheduler) → "stand by", then the readback when it executes; refused → "unable, <because>" ([[project-say-again-vs-unable]] wording). Scope is every command family, not only BL-16 flight commands; [[BL-16]] applies it to its own `flight` channel first. Open at build time: what a "stand by" that never resolves says (no execution, no refusal, ack lost), and which existing deferred-readback paths (`_speak_or_defer`, the wait-for-Lua readback, effector `petrovich-says`) fold into it.
