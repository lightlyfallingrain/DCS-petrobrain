# BL-B117 — The AI wheel's parked flag and overlay fields are not reset on `LuaExportStop`

- [x] **BL-B117 — Reset `ai_pilot_parked_active` and the AI-wheel overlay fields on
  `LuaExportStop`, so a stale "parked" or stale readback can never survive a mission end or
  restart.** #status/done Filed 2026-11-16 by user direction, as a BL-16 sub-item (`[[BL-16]]`).
  Implemented per plan (`plans/bl-b141-single-command-seq/plan.md`): `on_stop()` in
  `aircraft-layer/dcs-export/Petrobrain/ai_pilot_wheel.lua` now also clears `ai_pilot_parked_
  active`/`ai_pilot_mode_text`/`_course_text`/`_alt_text`/`_alt_add_text`/`_speed_text`/`_last_
  press`, with a real-Lua harness test (`test_ai_pilot_wheel_lua.py::TestOnStop::test_the_parked_
  flag_and_overlay_text_are_reset`).

  **The gap.** Found by Architect while planning `[[AC-B12]]` (`plans/ac-b12-export-modules/plan.md`,
  "A second, adjacent gap, not in AC-B13's scope"): `ai_pilot_parked_active`,
  `ai_pilot_mode_text`, `_course_text`, `_alt_text`, `_alt_add_text`, `_speed_text` and
  `_last_press` in `aircraft-layer/dcs-export/Export.lua` are cleared only on the in-flight unpark
  branch inside `run_ai_pilot_wheel`, never by `LuaExportStop`. Same reasoning as `[[AC-B13]]`,
  which covers only the open press and the takeover table that the security analysis found.

  **Why it matters.** The parked flag decides whether the takeover sequence sees a rising edge.
  A flag left `true` across a mission restart could swallow the next mission's real takeover,
  and the status push would report a readback from the previous mission until the first tick
  overwrote it. Both are low likelihood: they need the export environment to persist across the
  restart, which has not been verified either way.

  **Fix.** Clear these fields in the AI-pilot-wheel module's stop hook, next to `[[AC-B13]]`'s
  reset, with a test. Small enough to land in the same place once `[[AC-B12]]` has created that
  module; kept as its own item because the user asked for it separately rather than folded in.
