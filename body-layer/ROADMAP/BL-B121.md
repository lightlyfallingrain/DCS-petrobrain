# BL-B121 — Untested same-poll pending-restart double-speak for a speaking sequence row

- [ ] **BL-B121 — A same-poll pending-restart (D1) of a sequence whose row carries a non-empty
  `petrovich-says` may speak the same line twice within one poll; no test currently covers this
  combination, and it is not reachable by any sequence shipped today.**
  #status/open Filed 2026-11-16 during `BL-B119` (`feature/effector-says`) DoD, from the
  Reviewer's own optional-refinement note (`plans/effector-says/review.md`, "Optional
  Refinements").

  **What it is.** `effector_engine.py`'s own module docstring documents that a same-poll
  pending-restart "may write once for the run that just finished and once more for the one that
  restarts." Since `BL-B119`, a restarted run's row-0 self-check-skip now also *speaks* when that
  row's `petrovich_says` is non-empty — so the restart path could, in principle, speak the same
  line twice in one poll. `test_pending_restart_may_execute_the_same_poll` (pre-existing, untouched
  by `BL-B119`) exercises exactly the restart mechanics but only against `_SEQUENCES`' fixture
  rows, which all carry an empty `petrovich_says` by construction — so this interaction is
  currently unverified by any test, in either direction.

  **Why it is not exploitable today, confirmed at DoD by re-reading the trigger wiring (not just
  the reviewer's claim):** every speaking sequence shipped in `config/sequences/mi-24p/*.md`
  (`observ-on`, `observ-off`, `weapons-arm`, `weapons-safe`) is single-row, carries no `WaitRow`,
  and each trigger fires from a one-shot `CrewConsole` field consumed exactly once per poll in
  `body.py`. A same-poll double-fire of a *speaking* trigger has no real command path to reach it
  today.

  **When this stops being theoretical.** This project's own "step by step" plan for `BL-B119`
  (more effector triggers gaining `petrovich-says` lines over time) is exactly what would give a
  speaking row more than one row, or a `WaitRow` — the shape that makes a restart land on a
  *different*, possibly-still-non-empty row rather than collapsing silently into the no-op the
  single-row case gets today.

  **What would close it:** either a one-line note on `EffectorRunState.spoken`'s own docstring
  (so the next sequence author reads the risk before shipping a multi-row speaking sequence), or a
  dedicated test exercising a same-poll pending-restart against a *custom* sequence with a
  non-empty `petrovich-says` row (mirroring how `test_body.py`'s own new end-to-end speaking test
  had to build a custom sequence, since the shipped fixture directory predates the pilot's speech
  strings — see `plans/effector-says/implementation.md`, "Notable Discoveries"). Either closes it
  before the next multi-row speaking sequence lands; neither is required before this merge, since
  nothing reachable today exercises the gap.
