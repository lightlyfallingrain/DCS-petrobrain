# BL-B100 — A wake-prefixed question still defeats `parse_utterance`'s own grammar

- [ ] **BL-B100 — `[[AA-B7]]` makes a wake-prefixed transmission reach brain escalation instead of
  "say again", but the transcript it escalates is never stripped of the wake-word prefix, so
  `belief.utterance.parse_utterance`'s start-anchored patterns (`^where(?:'s| is| was)\s+...`,
  `^status\s+...`, `^watch\s+...`) reject it too.** #status/open Found by DoD during `[[AA-B7]]`,
  2026-10-25, by running `parse_utterance` directly rather than reading it — no review document
  held this (the Reviewer verified the routing chain, `verb_anchored=False` -> `"fallthrough"` ->
  `handle_line`, but not what `parse_utterance` does with the surviving prefix).

  Measured directly:

  ```
  parse_utterance(store, "Petrovich, where is mark one?", 0.0).matched_intent  -> None
  parse_utterance(store, "where is mark one?", 0.0).matched_intent             -> "describe_contact"
  ```

  So the exact sentence named in `[[AA-B7]]`'s own log evidence and sortie feedback F2
  (`"Petrovich, where is mark one?"`) now reaches brain escalation (progress — it no longer says
  "say again"), but `structural_unable_reason` sees `matched_intent is None` and returns
  `NO_SUCH_COMMAND`, so the brain replies `UNABLE NO_SUCH_COMMAND` -> **"Unable, no such command."**
  Not a regression (the pre-`[[AA-B7]]` behaviour for this sentence was "say again", also not an
  answer) but not the fix either: the pilot still does not get an answer to "where is mark one?"
  after this prefix, only a different wrong response.

  **Separately, "where are we?" (the other F2 example) has no matching pattern at all, prefixed or
  not** — `parse_utterance`'s two intents (`set_attention`, `describe_contact`) are both
  contact-referential; there is no ownship-position question in body's deterministic grammar or in
  `brain-layer`'s closed reply vocabulary (`PICK`/`ASK`/`CONFIRM`/`UNABLE` — none of which is free
  prose, see `brain-layer/src/decider.py`'s own module docstring). That gap is bigger than this
  entry and is not re-filed here.

  **What this blocks**: card item A14 flown literally against `"Petrovich, where is mark one?"`
  will not show "the brain answering in his own words" even once `--brain-url` points at the Mac —
  it will show `"Unable, no such command."` A flight test against this exact sentence will read as
  AA-B7 having failed when the routing fix is in fact working as designed; the unmet expectation is
  this entry, not AA-B7's scope.

  **Fix shape, not decided**: strip the leading `[hey, ]petrovich` (and its comma) from the
  transcript before it reaches `parse_utterance`/escalation — the same text
  `command_matcher.opens_with_wake_word` already recognises, but that recognition result
  (`verb_anchored=False`) currently carries no stripped transcript back across the wire, only a
  routing decision. Where the strip belongs (audio-adapter, returning an already-stripped
  transcript alongside the match result; or body-layer, stripping on the `"fallthrough"` branch
  before `handle_line`) is an open question for whoever picks this up — same kind of place-this-
  decision note `[[AA-B4]]` already carries for positional anchoring.
