# BL-B125 — Document/tighten the rule engine's real instruction-count budget

- [ ] **BL-B125 — `rules/engine.py`'s `RULE_LOAD_INSTRUCTION_BUDGET` (2,000,000) and
  `RULE_DISPATCH_INSTRUCTION_BUDGET` (200,000) are counted in `debug.sethook` *hook firings*, not
  raw Lua VM instructions — `sandbox.py`'s `run_with_budget` arms the hook with `count=1000`
  (`debug.sethook(lua_hook, "", 1000)`) and decrements the budget by 1 per firing, so the actual
  number of VM instructions a runaway/pathological rule can execute before `RuleBudgetExceeded`
  fires is **~1000× the named constant** — up to ~2×10⁹ for a load, ~2×10⁸ for a dispatch.** Filed
  2026-11-17 by the Security agent's Mode 2 deep analysis of `[[BL-17]]` Stages 0/1b/2
  (`feature/speech-rules`, `plans/speech-rules/security-stage0-2.md`), as a non-blocking suggestion
  — not required for that batch's PASS verdict.

  **Why this matters.** `RuleSandbox` is one shared `lupa.LuaRuntime` ("a single shared runtime is
  safe across threads... the instruction cap bounds how long any one caller can hold it",
  `sandbox.py` class docstring) — while one caller's dispatch/load runs, the Lua-level lock is held
  for the whole call, so a rule that is slow-but-not-infinite (e.g. an expensive but bounded loop a
  future rule author writes, or an accidental near-infinite one that trips the budget only near the
  very end) can block every other thread that wants the sandbox — the poll thread and the crew-text
  REPL thread alike — for however long ~10⁸–10⁹ real instructions actually take wall-clock, not the
  few-hundred-microseconds the named constants suggest at a glance. `engine.py`'s own comment
  ("Generous for any plausible rule file -- the budget exists to catch a genuine infinite loop, not
  to ration ordinary rule logic") reads as if the constant were counted in real instructions; the
  1000× hook-count multiplier was found and demonstrated in `body-layer/research/
  2026-11-17-lupa-sandbox.md` (`debug.sethook(hook, mask, count)` fires every `count` VM
  instructions) but the multiplier itself is not called out where the budget constants are chosen.

  **Not blocking** because: only one rule ships this stage (`turn_heading_relative`,
  `config/rules/flight.lua`), its handler runs a handful of instructions, and the two budgets were
  each exercised and confirmed to fire (`test_rules_sandbox.py`,
  `test_a_runaway_handler_is_aborted_and_reported_as_error`) — the mechanism works, this is about
  the *scale* of the stop condition, not whether it exists.

  **Recommended fix, when a later rule-porting stage adds rules complex enough for this to matter:**
  either lower the named constants by ~1000× to mean what they say, or add a one-line comment at
  each constant naming the real multiplier, and measure actual wall-clock time for a
  budget-exhausting dispatch on real hardware before relying on it as a latency bound for the poll
  loop.
