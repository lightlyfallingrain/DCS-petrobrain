# BL-B128 — `drain_pending_rule_dispatch`'s unconditional clear can drop a concurrent REPL hold

- [ ] **`CrewConsole.drain_pending_rule_dispatch` (`src/belief/crew_console.py`, `[[BL-17]]` D16
  hold-and-retry) reads `self.pending_rule_dispatch` into a local, runs `check_gate`, then —
  in every branch except "still HOLD, not timed out" — writes `self.pending_rule_dispatch = None`
  unconditionally, without checking that the field still holds the same entry it read.
  `handle_command`/`_handle_rule` (which sets a new hold on a gate `HOLD` verdict) is reachable
  from both the poll thread (voice) and the REPL thread (typed input, `body.py`'s own comment at
  the `_request_effector_write` closure: "`handle_command` is reachable from both the poll thread
  ... and the REPL thread"). If the REPL thread sets a *new* hold in the narrow window between
  this drain call's read and its own clear, that new hold is silently wiped — never dispatched,
  never timed out, no line spoken — and the typed command is lost with no indication to the
  player beyond having to repeat it.** #status/open Filed from the `[[BL-17]]` Stages 3a/3b/3d/4
  security deep analysis (`plans/speech-rules/security-stage3-4.md`), 2026-11-17.

  **Not a security boundary issue** — same-process, same-user concurrency, not attacker-reachable,
  no data/credential exposure. Filed because it is the same race *shape* (`pending_rule_dispatch`'s
  own unconditional clear vs. a concurrent `_handle_rule` write) that `[[BL-17]]`'s own Stage 3d
  fix round 2 already fixed once, for `pending_effector_writes`/`PendingEffectorWrite`
  (`project_bl17_fix4_rollback_races_fix1_drain.md`) — buffer-then-commit there, still plain
  read-then-clear here. The window is a handful of pure-Python bytecode instructions
  (`check_gate`/`current_crew_state` do no I/O and release no GIL deliberately), so this needs a
  true scheduler-timed coincidence, not a slow call to race against — low probability in the
  steady state (requires a voice command *and* a typed REPL command to both gate-`HOLD` in the
  same poll's drain window), not merely "low because the failure mode is rare."

  **Suggested fix, mirroring the pattern this feature already applied once**: in
  `drain_pending_rule_dispatch`, only clear when `self.pending_rule_dispatch is pending` (identity
  check against the locally-read reference) rather than unconditionally — if a newer hold has
  replaced it since the read, leave that newer one in place for the next poll's drain instead of
  discarding it.
