# BL-B106 — Async speech: the mouth never blocks the eyes and arms

- [x] **BL-B106 — Move `CrewConsole._print`'s synchronous `speech_client.push_speech` call off
  body-layer's poll thread onto a bounded-FIFO `SpeechWorker`, so Petrovich keeps looking and
  acting while a line is being spoken.** #status/done #needs-flight (merged to `main` as
  `820f8b34`, 2026-11-12; flight card
  `https://claude.ai/artifact/BAS1PHv5BuaWiPipkNFp3Q`, branch `main`)

  From `docs/acceptance/2026-10-20-sortie-feedback.md` §"F8 — speaking must be asynchronous"
  (user, verbatim): *"Speaking must be asynchronous. Generally the different layers should not need
  to wait on each other... Petrovich cannot speak two things at one time, he only has one mouth. But
  mouth is independent of eyes and arms."*

  **What was built.** A new `SpeechWorker` (`body-layer/src/belief/speech_worker.py`), mirroring
  `aircraft-layer`'s `AudioPlaybackSender` (bounded FIFO + one background daemon thread, not
  `BrainLayerClient`'s single-slot newest-wins shape — speech must preserve order and never
  silently skip a queued line). `CrewConsole._print`'s speech branch enqueues and returns
  immediately instead of blocking on `push_speech`; the worker times the call and deposits a
  result, and a new `CrewConsole.drain_speech_results` (polled once per poll, same spot as
  `drain_events`/`drain_brain`) calls `speech_log_sink` **on the poll thread** — closing a
  cross-thread read hazard in `_speech_log_sink`'s closure that a direct worker→sink callback
  would have opened. `stop_talking` and mission-restart detection both route through
  `SpeechWorker.interrupt()` rather than `speech_client.stop()` directly.

  **Key decisions.** (1) Reuse `AudioPlaybackSender`'s shape, not `BrainLayerClient`'s — ordering/
  no-skip is a hard requirement for speech, unlike brain escalation's "newest question only."
  (2) `_print` is a worker-vs-fallback split so none of the ~53 pre-existing
  `FakeSpeechClient`-based tests needed to change. (3) A performance-review NOW finding
  (`plans/async-speech/performance-review.md`) caught that `SpeechWorker.interrupt()`'s
  `client.stop()` shared `push_speech`'s 5.0s timeout, so `stop_talking` — the one command whose
  whole point is to react immediately — could stall the poll thread for a full 5s against a
  wedged (not merely down) audio-adapter; fixed with a dedicated `stop_timeout_s = 1.0` on
  `AudioAdapterClient.stop()`, re-reviewed and re-approved (`review.md`'s "Fix review").

  **Live-acceptance results: PENDING (live).** Full DoD mechanical check passed
  (`plans/async-speech/dod-check.md`) on `main` at the merge commit; a sortie has not yet
  exercised this. What the next flight needs to verify (test card to follow): a long callout no
  longer freezes scan/9K113 slew while speaking; `stop talking` cuts speech within ~1s; speech
  order is unchanged with no overlapping lines; a mission restart does not speak a stale
  pre-restart line; with the audio-adapter down, body-layer keeps ticking and logs one
  "disconnected"/"connected" transition pair.

  **Second-order effect.** `plans/voice-latency-instrumentation/performance-review.md`'s own
  Stage-6 finding ("`drain_pending_positional_replies` bounded to at most one poll interval")
  assumed the poll itself reliably took ~1s — a slow `push_speech` call could stretch that same
  poll's wall-clock duration arbitrarily, so this milestone is what makes that already-stated
  bound actually true rather than merely modeled. It also makes the voice-latency
  instrumentation's own `push_sent_wall` timestamp more honest (post-queue, not merely
  post-`_print`-invocation). `[[BL-B116]]` (body resource arbitration, minted on a separate
  docs branch) builds on the now-asynchronous speech path; no assumption here needs revisiting
  for it to proceed.
