# BL-B135 — Guard non-finite floats at aircraft-layer wire boundaries (telemetry `received_wall_clock_s` and siblings)

- [ ] **Harden numeric fields parsed from `aircraft_client`'s `GET .../latest` JSON responses against `NaN`/`Infinity`/`-Infinity`, not just non-numeric/bool types.** #status/open Filed 2026-11-24 by the security deep analysis of `BL-B133` (`plans/bl-b133-ptt-speech-hold/security.md`, Finding 1). `body.py`'s `run_once` parses `telemetry.get("received_wall_clock_s")` with `isinstance(x, (int, float)) and not isinstance(x, bool)` — the same guard already used for `last_ias_kmh`/`ias_mps` — then stores it unchanged for `PttHoldGate._is_stale` to compare against `time.time()`. Python's `json.loads` accepts the non-standard `NaN`/`Infinity`/`-Infinity` literals by default, and both pass this `isinstance` check. Unlike the `int()`-conversion gap already tracked in agent memory (`project_nan_infinity_int_conversion_at_lan_boundary.md`, from `BL-B104`), this one never raises — it silently produces a wrong *comparison* result: an `Infinity` (or `NaN`) value for `received_wall_clock_s` makes `_is_stale()` report "not stale" forever, so a `held=True` PTT reading cached from an aircraft-layer collector that has since gone silent (or a malicious LAN host impersonating it) is trusted indefinitely instead of releasing after `PTT_FEED_STALE_AFTER_S` — Petrovich stays muted until the next genuine DCS mission (re)start (`PttHoldGate.reset_for_new_mission`). Low probability (requires a rogue/impersonating host on the LAN, this project's threat model already treats as realistic but low-likelihood single-user), low impact (denial of routine speech only, self-recovers on mission restart, no crash/no code-exec/no data exposure) — not blocking `BL-B133`. Recommended fix, when picked up: add a `math.isfinite()` guard alongside the existing `isinstance` check at this and the sibling wire-boundary parses (`last_ias_kmh` has the identical gap, pre-existing), same spirit as `line_of_sight.py`'s `agl_m` parse already gets right for `int()`-conversion sites. A scan of every numeric field parsed off an aircraft-layer `GET` response for the same gap would be a reasonable scope, not just the two found so far. **Third instance filed separately as `[[BL-B137]]`** (`BL-B124`'s security deep analysis, 2026-11-25) — `schema.firing.MissionClockSample.abs_time_s`, where the consequence is worse than either instance above: traced through `perception.light_level.sun_elevation_deg`'s formula, NaN/Infinity resolves to a concrete `90.0` deg sun elevation (not a bare mis-comparison), forcing full daylight optic performance with no error logged — the one outcome that feature's own design explicitly forbids. **Two more instances, 2026-11-27** (`BL-16` security deep analysis, `plans/flight-lift-vector/security.md` on `feature/bl16-lift-vector-law`): `belief/flight_control.py` and `belief/ai_pilot_wheel.py` each carry their own `_as_optional_float` that accepts `NaN`/`Infinity` off the wire. Both predate the BL-16 batch, so they were left alone there; the batch's own copy in `belief/flight_authority.py` was fixed (`dc60120f`, `math.isfinite` → `None`) and is the pattern to copy. Note the three near-identical helpers — one shared finite-float parser is the natural scope when this is picked up.
