# BL-B137 — `mission_clock` NaN/Infinity propagates to a forced *full-daylight* light factor, silently

- [x] **Guard `MissionClockSample.abs_time_s` against NaN/Infinity — it silently resolves to full
  daylight, the one outcome `BL-B124`'s own design explicitly forbids.** #status/closed Filed
  2026-11-25 by the `BL-B124` security deep analysis (`plans/bl-b124-light-level/security.md`,
  Finding 1); closed 2026-11-25, same day, on `feature/bl-b124-light-level`. A third instance of
  the gap `[[BL-B135]]` already generalises — see that entry for the pattern and prior instances
  (`BL-B104`'s `int()`-conversion shape, `BL-B133`'s comparison shape). This one is the worst
  instance found so far: it does not merely raise or mis-compare, it silently produces the exact
  forbidden fallback the feature's own docstring names (user Q6: *"mission should always have both
  readable. Error if not."*), with zero logging.

## Finding

`aircraft-layer/src/schema/firing.py`'s `MissionClockSample.from_wire` parses the `abs_time_s`
sub-field with `float(abs_str)`, which does not raise on the strings `"nan"`/`"inf"`/`"-inf"` —
unlike `year`/`month`/`day`'s `int()` calls, which do raise on those. `body-layer/src/body.py`'s
`_parse_mission_clock_dict` then accepts a NaN/Infinity `abs_time_s` through its `isinstance(x,
(int, float))` guard (the same general shape as
`.claude/agent-memory/security/project_nan_infinity_int_conversion_at_lan_boundary.md` and its two
siblings) — `isinstance` is satisfied; non-finiteness is never checked.

**Confirmed by direct calculation, not speculation**: feeding `abs_time_s = float('nan')` (or
`float('inf')`) into `perception.light_level.sun_elevation_deg` propagates NaN through every
intermediate (`total_hours_utc`, `d`, `g`, `ecliptic_longitude`, `declination`,
`local_hour_angle`, `sin_altitude`). The final clamp, `sin_altitude = max(-1.0, min(1.0,
sin_altitude))`, does **not** hold NaN clean the way `project-nan-comparison-incidental-guards.md`
documents for other clamps in this codebase — `min(1.0, nan)` returns `1.0` (NaN comparisons are
always `False`, so `min`/`max` keep their *first* argument whenever the comparison is NaN), and
`max(-1.0, 1.0)` then returns `1.0`. `math.degrees(math.asin(1.0))` is exactly `90.0` — the sun
directly overhead. `light_factor()` then takes the `sun_elevation_deg >=
EYE_FULL_DAYLIGHT_SUN_ELEV_DEG` branch and returns `(1.0, 1.0, 1.0)`: **full clear-day
performance for every optic**, the one outcome `body.py`'s own `_resolve_sun_elevation_deg`
docstring says this feature must never produce from a bad reading (user Q6: *"mission should
always have both readable. Error if not."*).

**Worse, it is silent.** `_resolve_sun_elevation_deg`'s own staleness/error machinery
(`light_level_unavailable_since_wall`/`light_level_error_logged`, the Required Fix from
`plans/bl-b124-light-level/review-stages-4-5.md`) is bypassed entirely: a malformed sample is
taken as "fresh" whenever it **differs** from the previously stored tuple, and `nan != nan` is
`True` in Python, so a NaN-bearing tuple compares as "different" against itself on every single
poll. The sample is treated as a brand-new valid reading every time — never reaching the
"unavailable past `MISSION_CLOCK_MAX_AGE_S`" branch that would log the one `ERROR` this feature
was built to guarantee.

## Reachability

The UDP channel that carries `mission_clock` into the collector
(`collector.firing_receiver.FiringEventsReceiver`, default host `127.0.0.1`) is **loopback-only**,
unlike `api.server`'s `GET /firing/latest` (`0.0.0.0`, LAN-facing but read-only — there is no
write path for a LAN peer to inject a crafted `mission_clock` over HTTP). So triggering this
requires either a process already running locally on the same box as the DCS/aircraft-layer
collector (a more severe compromise than the stated "infected computer scanning LAN ports" model),
or a genuine upstream anomaly in the Lua `timer.getAbsTime()`/`env.mission.date` read — the latter
not observed and not expected in normal operation.

## Severity

**Probability:** low — no LAN-reachable write path; requires local code execution on the DCS box
itself. **Impact:** low-medium — Petrovich's simulated light-dependent perception silently
defaults to full daylight (the explicitly-forbidden direction) for as long as the bad sample keeps
winning the race against genuine Hook polls; self-heals the instant a genuinely different, finite
sample arrives. No code execution, no data exposure, no crash.

## Recommended fix

`MissionClockSample.from_wire` (`aircraft-layer/src/schema/firing.py`): after `abs_time_s =
float(abs_str)`, add `math.isfinite(abs_time_s)` to the success condition (raise
`FiringParseError` otherwise, same as the existing `ValueError` path) — mirrors the `float()`-not-
`int()` precedent `line_of_sight.py`'s `agl_m` parse already sets, extended with the explicit
finite check this feature's own "error if not readable" design goal requires. Optionally also
range-check `year`/`month`/`day` (e.g. `1 <= year <= 9999`) to close the separate, lower-severity
`OverflowError`-from-an-absurdly-large-digit-string path into `_julian_day`'s float arithmetic —
already caught by `body.py`'s poll-cycle `except Exception`, so that one is cosmetic by
comparison.

## Status

**Closed 2026-11-25**, same disposition it was filed under: not blocking `BL-B124`'s DoD, fixed as
a small, mechanical change rather than deferred. Two guards, matching the recommended fix above
plus the defence-in-depth the finding's own "treat a non-finite input or result as unavailable"
framing called for:

1. **At the wire** (`aircraft-layer/src/schema/firing.py`, `MissionClockSample.from_wire`) —
   `math.isfinite(abs_time_s)` added to the success condition; non-finite raises `FiringParseError`
   the same way the existing `ValueError` path does, and `FiringEventBatch.from_wire`'s existing
   `except FiringParseError` drops it to `mission_clock=None` without failing the rest of the
   batch (same posture as any other malformed sub-wire).
2. **In body-layer**, two independent layers deep, since `abs_time_s` is also reachable via a
   locally-extrapolated value that never passes back through the wire parser:
   `body._parse_mission_clock_dict` rejects a non-finite `abs_time_s` the same way it rejects a
   wrong-typed one (returns `None`), and `perception.light_level.sun_elevation_deg` itself now
   raises `ValueError` on a non-finite `abs_time_s` or a non-finite `sin_altitude` intermediate,
   checked *before* the clamp that was silently resolving NaN to 90.0 — `body._resolve_sun_
   elevation_deg`'s call site catches that `ValueError` and falls through to the same
   beyond-grace/forced-dark/logged-error path as a failed `dcs_to_wgs84` coordinate projection,
   never returning a daylight figure.

Tests (`aircraft-layer/tests/test_firing_schema.py`, `body-layer/tests/test_light_level.py`,
`body-layer/tests/test_body.py`) prove each guard is load-bearing, including one test that removes
the guard and demonstrates the exact silent-90.0 failure mode directly against the bare clamp.
`[[BL-B135]]`'s own entry already cross-links this one; no change needed there.
