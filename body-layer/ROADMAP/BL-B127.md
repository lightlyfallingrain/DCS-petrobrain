# BL-B127 — `effector.write` has no coupling to the calling rule's category/seat

> **Deferred 2026-11-17 by the user:** *"BL-B127 - for now that is rule writer's responsibility. No
> need to guard against that for now."* A rule that writes an effector is responsible for writing
> only effectors that fit its own category/seat; no code guard is built.

- [>] **`rules.actions._write_effector`/`body.py`'s `_request_effector_write` validate an
  `effector.write(name, value, says)` call against the curated `effectors.toml` registry only
  (does this effector/value exist at all) — never against the *calling rule's* declared category
  (`when.speech`'s third argument, `rules.gates.GATE_REGISTRY`). Every `ACTION_NAMESPACES` table
  (`flight`, `effector`) is built once and handed to *every* rule file's environment
  (`rules.engine._make_env_builder`) regardless of that file's own rules' categories — category
  only gates whether a matched rule's *handler* is allowed to run at all (`rules.gates.check_gate`,
  D16), never which actions/effectors that handler may call once it does run.** #status/open
  Filed from the `[[BL-17]]` Stages 3a/3b/3d/4 security deep analysis (`plans/speech-rules/
  security-stage3-4.md`), 2026-11-17.

  **Not exploitable today** — `GATE_REGISTRY` only has `"always"`/`"flight_control"`-family
  categories (no seat-specific category exists yet; the module's own docstring says further
  categories, e.g. `"copilot_sight"`/9K113 or a pilot-seat-tools category, are "declared when those
  rule groups are ported — not stubbed in now for commands that do not exist yet"), and no shipped
  rule calls `effector.write` yet (`rules/actions.py`'s own comment: "built now, as foundation...
  no shipped rule calls this yet").

  **Becomes a real gap the moment both of these land** (both already planned, same roadmap entry,
  "Rules can write effectors, from the start" / "Category gates, before any rule runs"): a
  seat-restricted category (e.g. `"copilot_sight"`) *and* a seat-restricted effector in
  `effectors.toml`. At that point a rule declared under a pilot-facing category (e.g.
  `"flight_control"`) could still call `effector.write("<copilot-only-effector>", ...)` and
  succeed, because nothing checks "is this effector's seat the same as the calling rule's
  category's seat." The user's own decision already anticipates this for *dispatch* ("likewise,
  copilot rule cannot execute when Petrovich is in pilot seat and vice versa," `BL-17.md`,
  "Category gates, before any rule runs") but that decision is about which *rule* runs, not which
  *effector* a running rule may write — this gap is the second half nothing currently enforces.

  **Recommended fix shape, for whoever plans the seat-gating stage**: either (a) curate
  `effectors.toml` entries with their own seat/category tag and have `_request_effector_write`
  check it against the calling rule's category (threaded through `ActionContext` or a parameter on
  the closure), or (b) scope `ACTION_NAMESPACES`/the action tables a rule file's environment
  receives by category, so a pilot-category rule never even sees a copilot-only effector action.
  Not designed here — this entry exists so the gap is not silently assumed away once the seat work
  starts.
