# BL-17 — Spoken commands as Lua rules

- [~] **BL-17 — Every spoken command becomes a Lua rule: a fixed-wording pattern with typed slots,
  and a handler that calls exposed actions and writes its own readback. Parsing, matching and the
  actions themselves stay in code.** #status/in-progress Started 2026-11-17 by user direction,
  `feature/speech-rules`. Promoted from `[[BL-B95]]`, which keeps the wider event-driven scripting
  concept; this milestone is its first concrete slice. The explore conversation, the user's three
  pseudocode examples and every answer, verbatim: `plans/behaviour-trees/explore-notes.md`,
  "2026-11-17: speech commands as Lua rules".

  > *"This would move lot's of hardcoded actions to config lua. We'd need exposed tool set to call.
  > But then creating and modifying actions (and user speech commands) would become easy."*

  ## Settled in the explore (2026-11-17)

  - **Fixed wording is the fast path.** *"to get the deterministic (=fast) path, I use fixed
    wording"*. Patterns are for fixed phrases; loose speech is the brain's.
  - **Typed slots, defined in code** (`heading`, `bearing`, `oclock`, `distance`, …), each owning its
    spoken shape and number collapse ("315" = "3 1 5" = "three one five"). A slot that does not parse
    means the rule did not match.
  - **The direction's type is always spoken, and fixes the digit count.** `heading`/`bearing` +
    exactly three digits; `<1–12> o'clock`. *"numeric direction value must specify what type it
    is"*.
  - **Bearing = ownship-relative degrees, 0 = boresight. Heading = compass degrees**, magnetic or
    true by application. Existing code that says "bearing" for a compass direction is renamed,
    spoken vocabulary included (*"Change the naming in existing code to reflect this."*).
  - **Each rule writes its own readback.**
  - **Target choice stays in code.** "Engage tanks two o'clock" gets one unit or `nil` from code; the
    rule reports "no contact" on `nil`.
  - **Marks are numbered, referenced later by number, append-only** — *"Only ever add marks, edit
    and delete are not supported."* A mark is a point to come back to: a scan reference or a flight
    waypoint.
  - **All existing commands move to rules**, grouped by what they do, split into files as needed.
  - **`lupa` (MIT) approved** as a new dependency.

  ## Sequencing (user, 2026-11-17)

  > *"build the scructure first, then take one or two rules and port them. Then test flight is in
  > order. Then we can schedule porting the rest in stages."*

  1. The rule engine structure, and the bearing/heading rename.
  2. One or two existing commands ported.
  3. Test flight.
  4. The remaining commands, ported in scheduled stages.

  - **Magnetic vs true: the existing convention in code**, unchanged (user, 2026-11-17: *"use
    existing convention in code"*).
  - **No ×5 checksum on any direction** — *"allow any three digit value"*. The checksum on today's
    "scan bearing" goes with the rename.

  ## Open, for planning
  - Rules span two subprojects: patterns are needed where speech is recognised (`audio-adapter`,
    which also builds the recogniser bias list from them), handlers run in body-layer.
  - Adding a pattern can change how another matches (`vocabulary.py:645`, "attack" vs "tanks"), so
    rule loading needs a collision check.
  - The actions rules call should be the brain's surface too (`TOOL_SET`, `[[BR-2]]`, in flight on
    `feature/br2-free-text`) rather than a second one.
