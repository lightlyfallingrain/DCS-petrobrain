  ## A failed action throws "unable" (user, 2026-11-18)

  > *"Every function has duplicate `if not r.ok then say(unable(r.reason)) return end`. That
  > looks like a place for either a funtion that handles that or to throw exception from
  > flight.some_funtion() on error. A common catch clause in code that run there rules would then
  > do that say(unable(r.reason))."*

  Built on `refactor/rule-action-unable-throw`, ahead of BL-16 mode 1. DoD PASSED and merged
  `85272e9d` (2026-11-18; `plans/speech-rules/dod-unable-throw.md`). A helper could not do it:
  a Lua function cannot return out of its caller. So a failed action raises `RuleUnable`, and
  `run_rule` logs it and speaks `unable(reason)`. Lines the handler already said stay spoken;
  the user said *"let's not put much effort in error recovery. Log errors certainly, but let the
  spoken lines be"*. Rules cannot catch it (no `pcall`). A bad call, meaning a wrong argument
  count, type or range, is now a rule bug: "Action file error." and a log line, where it used
  to be a plain "Unable.". `ActionContext.on_rejected_call` is gone, because the rule checker
  reads the error message instead. `flight.lua` lost all 17 checks.

  ## Settled in the explore (2026-11-17)

  - **Fixed wording is the fast path.** *"to get the deterministic (=fast) path, I use fixed
    wording"*. Patterns are for fixed phrases; loose speech is the brain's.
  - **Typed slots, defined in code** (`heading`, `bearing`, `oclock`, `distance`, …), each owning its
    spoken shape and number collapse ("315" = "3 1 5" = "three one five"). A slot that does not parse
    means the rule did not match.
  - **The direction's type is always spoken, and fixes the digit count.** `heading`/`bearing` +
    exactly three digits; `<1–12> o'clock`. *"numeric direction value must specify what type it
    is"*.
  - *(Superseded 2026-11-18, see "Parked": existing wording stays.)* **Bearing = ownship-relative degrees, 0 = boresight. Heading = compass degrees**, magnetic or
    true by application. Existing code that says "bearing" for a compass direction is renamed,
    spoken vocabulary included (*"Change the naming in existing code to reflect this."*).
  - **Each rule writes its own readback.**
  - **Target choice stays in code.** "Engage tanks two o'clock" gets one unit or `nil` from code; the
    rule reports "no contact" on `nil`.
  - **Marks are numbered, referenced later by number, append-only** — *"Only ever add marks, edit
    and delete are not supported."* A mark is a point to come back to: a scan reference or a flight
    waypoint.
  - **All existing commands move to rules**, grouped by what they do, split into files as needed.
  - **`lupa` (MIT) approved** as a new dependency.

  ## Directives are part of the command, and fuzzy; only values are exact (user, 2026-11-17)

  Refines "fuzzy forgives words, never values" — the goal check had counted left/right as values:

  > *""Turn left 30" I would read it like "Turn" is base command, "Left" is sub part of command,
  > "30" is value. Or "Scan ahead 3 km": "Scan" main action, "Ahead" directive, "3 km" value. I'd
  > want fuzzy matching for "turn left" and "scan ahead". Even more so because the command base word
  > and its directives form a short sentence that makes it easier to match against something that
  > was kinda almost heard properly."*

  So the base word plus its directives are matched together as a short phrase, with near-miss
  tolerance ("turn lift 30" → turn left 30); only the value (number, distance) must be heard exactly.
  A heard directive equally close to two alternatives is still "say again", never a guess.

  What counts as a value, same day: *"Values would be numeric values, unit class/type, landmark name
  etc. things that can be truly arbitrary instead of like one of five options."* So a small closed
  set of options is a directive (fuzzy); an open, arbitrary value — numbers, unit class/type,
  landmark names — is exact. A property of the slot type, so new value types are exact by default.

  **Refined (user, 2026-11-17):**

  > *"when Petrivich is in pilot seat and has controls, flight commands are expected. If not
  > flying, normal scan (eyes and binoculars) responses to "describe", answers to queries, etc.
  > Regardless of state, Petrovich must answer to questions about believed state and what mission

  Three layers:

  1. **Always expected, any seat, any state:** questions about what he believes and what mission
     memory holds (reports, recall, "describe").
  2. **Action commands, limited by seat** — only the aircraft tools that seat has (9K113 is copilot
     only, `[[BL-B123]]`) — **and by state** — hands/eyes busy or free. Flying keeps his hands busy,
     so no sight operation; eyes stay free for naked-eye scanning.
  3. **Priority:** while he has the controls, flying and flight commands come first; otherwise
     scanning and detection come first.

  | Petrovich | has controls | not flying |
  |---|---|---|
  | either seat | flight commands (priority), queries, describe | scan (eyes, binoculars), describe, queries, that seat's tools; "you have controls" |
  | copilot seat, extra | — | 9K113 / sight operation |

  Rules therefore carry the seat and state they apply in. Ties to `[[BL-16]]` (who has controls) and
  `[[BL-B123]]` (seats). Supporting reason beyond speed (main loop, unverified): whisper's prompt is
  capped (believed ~224 tokens), so a vocabulary that keeps growing would eventually be cut off
  unless it is narrowed.

  **A command spoken in the wrong state** (e.g. "turn left 30" while he is not flying): narrow only
  the speech-to-text hint, keep matching every command, and answer "unable, <reason>" — "say again"
  means *not understood*, "unable" means *understood but unavailable*. User: *"As you recommended, I
  agree with that."*

  **For the re-plan:** "priority" is recorded as stated; what it changes in code (tie-break between
  near-equal matches, order of the speech-to-text hint, what he attends to first) is the

  > category) rules, before getting executed, must pass the gate. In flight control case, Petrovich
  > must have controls, otherwise it's unable before any rule even executes. Likewise, copilot rule
  > cannot execute when Petrovich is in pilot seat and vice versa."*

  So every rule belongs to a category, each category has one gate (a named check over what the crew
  can see: who has the controls, which seat, hands/eyes busy), and a matched rule whose gate fails
  never runs: the gate answers "unable, <reason>". The state it reads is the same state the
  speech-to-text hint follows. Actions still validate their own arguments.
